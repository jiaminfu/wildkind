流程能跑通、账目能对上、越权挡得住、前后台同一份数据。

**后台巡查查什么**（`tools/admin-sweep.js`，这是本轮补上的关键一环）：

| 检查项 | 判定方式 | 为什么必须真点 |
| --- | --- | --- |
| 掉回登录页 | 点完菜单后 URL 是否仍含 `#/admin/<模块>` | 接口测不出「令牌被复位接口清掉」这类问题 |
| 路由未切换 | 面包屑/标题是否更新 | 前端路由分支漏写时会静默停在原页 |
| 内容为空 | 主区域是否有 `table tbody tr` 或表单控件 | 数据在、页面空，接口测试全绿也发现不了 |
| 横向溢出 | `scrollWidth > clientWidth` | 只在真实视口宽度下才成立 |
| 泄漏元素 | 桌面侧栏在移动端是否仍可见 | 媒体查询漏写 |
| console 报错 | 收集 `Runtime.exceptionThrown` 与 `console.error` | 用户看到"点了没反应"的常见根因 |
| 4xx 请求 | 拦截 Network，记录非 2xx 的 `/api/` | 接口测试单独调用正常，页面上参数拼错就 4xx |

巡查额外跑三个场景：订单行点击进详情、后台状态写操作（点按钮 → 核对接口结果）、会话过期后的提示文案。

移动端用 CDP 设备模拟而非缩小窗口——headless 窗口有约 470px 最小宽度，直接改尺寸会被裁切，测出来的溢出量是假数据。

**对账方法**：逐个 SKU 取流水中最后一条的 `balanceAfter`，与该 SKU 的 `stock` 比对。这条不成立，就说明有库存变动绕过了流水入口——是缺陷，不是"数据不准"。

### 5.5 缺陷分布说明

```
加购 → 下单 → 退款 链路  ████████████ 7 个 S1（全在此）
后台可用性（登录态/详情）  ██ 2 个（D-022、D-023）
数据一致性              ███ 3 个
UI 适配与显示            ██████████ 10 个
文档与实现不符           ██ 2 个
功能缺失                ███ 3 个（内容页 404、看板错链、三模块缺位）
```

**7 个 S1 全部集中在同一条链路上**，不是巧合：这条链路状态最多、跨页面最多、也最容易"看起来跑通了"。这正是把「能跑通」和「算得对」分成两个验收层级的原因。

**v1.2 补的 8 个缺陷有一个共同点**：全部来自"真实点击 + 真机宽度"，没有一个是接口测试能发现的。这也说明为什么单靠接口套件报"全绿"是不足的——它证明不了用户点得动。

**v1.1 补的 5 个缺陷有一个共同点**：都不是核心链路，而是"边上没人走的地方" —— 页脚链接、登录页、看板跳转、窄屏下的 KPI。这类缺陷单看每一处都很小，但它们全部落在用户真实会点到的地方，上线后被投诉的概率不比 S1 低。所以回归不能只跑主流程。
