---

## 1 什么算缺陷

满足任一条即为缺陷：

| 类型 | 判定 |
| --- | --- |
| 功能不符 | 实际行为与 FRD 描述不一致 |
| 数据错误 | 金额、库存、客户、券出现不自洽（**最高优先**） |
| 契约不符 | 接口行为与 API 文档 / SDD 第 16 节不一致 |
| 越权 | 权限位没有挡住本应挡住的写操作 |
| 崩溃 | 抛未捕获异常、白屏、500 |
| 布局 | 横向溢出、元素重叠、内容被裁切 |
| 性能 | 单次接口 > 1s，或页面首屏 > 3s（本项目暂未纳入） |

### 1.1 不算缺陷的几种情况

| 情况 | 归类 |
| --- | --- |
| 文档写清楚了，实现也一致，但用户觉得不好看 | **设计改进**，走 UI 评审，不算缺陷 |
| 文档没写，实现也没做 | **需求缺口**，走需求变更，不算缺陷 |
| 只在测试环境出现、生产不可复现的配置问题 | 环境问题，记录但不占缺陷指标 |
| 已知未覆盖项（见测试计划 2.2） | 不在本期范围 |

> 这条边界很重要。把所有"不满意"都记成缺陷，会让缺陷率失去意义，也会让开发疲于应付主观项。

---

## 2 严重程度（Severity）

严重程度由**测试**判定，只看客观影响，不看修起来难不难。

| 等级 | 定义 | 判定标准 | 典型例子 |
| --- | --- | --- | --- |
| 🔴 S1 致命 | 资金 / 库存 / 数据错，或功能完全不可用 | 会造成实际损失，或账目无法对账 | 超卖、退款不补库存、单号重复、伪造价格可低价下单 |
| 🟠 S2 严重 | 主流程阻断，但有绕过办法 | 用户走不下去 | 结算页报错、优惠券永远校验失败 |
| 🟡 S3 一般 | 非主流程出错，或局部显示错 | 影响体验，不影响成交 | 后台某个筛选项无效、日期显示成 ISO 串 |
| 🟢 S4 轻微 | 文案、间距、图标 | 观感问题 | 图标空白、数字与文字粘在一起 |

---

## 3 优先级（Priority）

优先级由**产品（你）**决定，看"什么时候修"，与严重程度不是一一对应。

| 等级 | 含义 | 处理时限（本项目约定） |
| --- | --- | --- |
| 🔴 P0 | 立即修，修完才能继续 | 当天 |
| 🟠 P1 | 本次迭代必修 | 本轮结束前 |
| 🟡 P2 | 下个迭代修 | 排期 |
| 🟢 P3 | 有余力再修 | 进待办池 |

### 3.1 常见错配

| 情形 | 严重度 | 优先级 | 为什么 |
| --- | --- | --- | --- |
| 后台某报表数字格式难看 | S4 | P3 | 不影响决策 |
| 演示数据下才会超卖 | S1 | P0 | 严重度看影响，不看触发概率 |
| 只在 Safari 上布局错位 | S3 | P1 | 若 Safari 流量占比高，就该提前修 |

## 4 缺陷生命周期

```
 发现
  │
  ▼
[新建 New] ──► 测试补充复现步骤
  │
  ▼
[已确认 Confirmed] ──► 开发确认是缺陷（否则退回"非缺陷"并说明）
  │
  ▼
[修复中 In Progress]
  │
  ▼
[待验证 Resolved] ──► 开发说明改了什么、影响范围
  │
  ├──► 验证通过 ──► [已关闭 Closed]
  │
  └──► 验证不通过 ──► [重新打开 Reopened] ──► 回到"修复中"
```

### 4.1 各状态的准入条件

| 状态 | 进入条件 | 谁来推动 |
| --- | --- | --- |
| 新建 | 测试已本地复现至少一次，且有明确预期 | 测试 |
| 已确认 | 开发认可这是缺陷（不是环境问题、不是需求缺失） | 开发 |
| 修复中 | 已定位到具体代码或配置 | 开发 |
| 待验证 | 开发已改完并在本地自测通过 | 开发 |
| 已关闭 | 测试按原步骤复现通过，**且回归相关用例全绿** | 测试 |
| 重新打开 | 按原步骤仍能复现，或修完引入了新问题 | 测试 |

### 4.2 关闭的硬条件

**必须同时满足**：

1. 按原用例步骤复现，行为已符合预期。
2. **相关回归用例全绿**——不能出现"这个修好了、那个坏了"。
3. 若缺陷涉及数据（库存、金额），必须附上"修复前 / 修复后"的实际数值对比。
4. 若缺陷源于测试脚本自身的缺陷（如测试不可重复），必须补一条防止复发的检查。

第 4 条来自本轮的教训：`D-013`（接口测试不可重复）本身就是缺陷，修完必须补上复位机制，否则同一个坑会反复踩。

## 5 缺陷报告模板

每条缺陷必须含以下字段，缺任何一项都会被打回：

```markdown
### D-XXX 缺陷标题（一句话说清"什么场景下出了什么错"）

| 项 | 内容 |
| --- | --- |
| 严重程度 | S1 / S2 / S3 / S4 |
| 优先级 | P0 / P1 / P2 / P3 |
| 发现阶段 | 需求评审 / 设计评审 / 单元测试 / 接口测试 / E2E / 适配测试 / 验收 |
| 影响范围 | 哪些功能、哪些页面、哪些数据 |
| 关联需求 | FR-xxx / BR-xx / SDD x.x |
| 状态 | 已关闭 / 待验证 / 修复中 |

**复现步骤**

1. 前置：……
2. 操作：……
3. 观察：……

**预期**（引用文档原文，不要凭感觉）

**实际**（附实际返回、实际数值、截图路径）

**根本原因**（一句话，指向具体代码位置或设计缺口）

**修复方案**（改了什么，为什么这样改）

**验证结果**（复现步骤重跑的结果，附关键数值）
```

### 5.1 好标题与坏标题

| 坏 | 好 |
| --- | --- |
| 库存有问题 | 库存 2 件时下单 3 件仍生成订单，库存被扣成 0 而非拒单 |
| 退款不对 | 后台退款后库存未回补、券未释放，客户累计消费不减 |
| 后台样式有问题 | 后台看板在 390px 视口下横向溢出 186px |

判断标准：**看完标题就知道要不要现在修**。

## 6 分级响应与沟通

| 严重度 | 响应方式 |
| --- | --- |
| S1 | 立即告知，不等到日报；同步给架构判断是否属设计漏 |
| S2 | 当天汇总，随下一轮修复一并处理 |
| S3 / S4 | 进缺陷池，按优先级排期 |

### 6.1 谁决定"带缺陷上线"

**只有你能决定**。测试提供三项输入：

1. 缺陷的严重度与影响范围
2. 是否有绕过办法
3. 不接受上线的风险（会发生什么、多大频率）

测试**不建议**"这个可以先上"——那是产品判断，不是质量判断。

## 7 复盘机制

### 7.1 何时复盘

满足任一条件即复盘：

- 出现 S1 缺陷
- 同一模块在 2 轮内出现 3 个以上缺陷
- 缺陷在测试环境没发现、上线后才发现（漏测）

### 7.2 复盘要回答的三个问题

| 问题 | 目的 |
| --- | --- |
| 为什么会写错？ | 找根因，不是找责任人 |
| 为什么测试没早发现？ | 补用例或补手段 |
| 同类问题还有几处？ | 一次改一片，不是改一个 |

第 3 条是本轮最有效的做法：发现「退款只改状态」后，立刻去查「取消订单」「状态流转」有没有同样问题，结果查出退款和取消两个入口都要统一。**一个缺陷往往代表一类缺陷。**

### 7.3 复盘的产出

| 产出 | 落到哪 |
| --- | --- |
| 新增/修改用例 | 测试用例文档 + 自动化脚本 |
| 需要补的检查 | 自动化脚本（如对账脚本） |
| 需要改的文档 | FRD / SDD 对应章节 |
| 流程改进 | 本文档 |

## 8 本项目的缺陷统计口径

| 指标 | 定义 |
| --- | --- |
| 缺陷密度 | 缺陷数 / 用例数。本项目 16 / 289 = 5.5% |
| 修复率 | 已关闭 / 总数 |
| 重开率 | 重开次数 / 已关闭数。**这个指标比修复率更能反映修复质量** |
| 漏测率 | 上线后发现 / 总缺陷。本项目暂无（未上线） |

> 修复率 100% 但重开率 30%，说明修复是敷衍的。所以两个指标要一起看。
