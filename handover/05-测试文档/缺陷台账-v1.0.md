# LASTGROVE 缺陷台账

*文档编号* LG-DEF-001　 *版本* **v1.2**　 *建立日期* 2026-11-16　 *维护人* 产品 / 唯一开发者

> **这份文档和测试报告的分工**
> 测试报告（v1.1–v1.8）是**版本留档**：某一轮跑了什么、结果如何，写完就不动。
> 台账是**活动清单**：一条缺陷从被发现到关闭的全过程，状态会变，可以追加。
> 缺陷不再只散落在测试报告的「发现」章节里 —— 那样下次要看「现在还有几条开着」，得翻八份文档数。
>
> **严重度沿用测试方案 v2.0 的四级**：🔴 亏钱 / 丢数据；🟠 客户可见；🟡 内部麻烦；🟢 观感。
>
> **v1.0 → v1.1 改了什么**：追加第二轮 12 条（DEF-015 ~ DEF-026）。这一轮换了打法 —— 先把库清空，再以运营身份从零建货、以客户身份真下单，然后四类测试一起上（功能 / UI / 兼容 / 性能）。结果是 **11 条里没有一条能被功能测试抓住**：图片变成竖条、按钮和页脚连成一块、320px 整站横滑，这些在 DOM 里全是「存在且可点」。见 §6。
>
> **v1.1 → v1.2 改了什么**：把 §6.4「都不阻塞上线」那四项**逐条关闭**（不再以「占比低」为由留下），并顺手查出 9 条新缺陷 —— 其中 2 条是 🔴（首屏要发两次请求、字体走外部 CDN 把访客 IP 交给第三方）。上线条要求：**台账里没有一条「已知未修」**。见 §7。

### DEF-001　券的「过期」与「发满」混为一谈　🔴　**已修**

| 项 | 内容 |
|---|---|
| 发现 | 2026-11-16，核对 `SUMMER20` 时发现：`used=640 / limit=640` 且 `endsAt=2026-08-31`，列表徽章显示 `expired`，KPI「Live now」却把它算成活的 |
| 现象 | ① 后台券列表直接渲染存储的 `status` 字段；② 该字段只在运营**手工**改时才变，「过期」和「发满」是随时间与用量自己发生的，没人会回去改；③ 于是列表会长期撒谎；④ 一张券同时过期又发满时，只显示其中一个原因 |
| 根因 | 券状态**没有派生逻辑**，把「人工快照」当成了「事实」。`resolveCoupon` 里另写了一套判定，两套各走各的 |
| 定性 | **产品问题，不只是技术问题**（用户 2026-11-16 判定）：过期就是过期，发完就是发完，状态必须区分，且同时成立时要同时可见 |
| 修复 | `pricing.couponState(c, now)` 为唯一事实来源，返回 `{ state, reasons[] }`；优先级 `expired > disabled > exhausted > scheduled > active`（expired 排第一是客户视角：说「过期」他知道自己来晚了，说「不再有效」他会以为拿错了码）；`resolveCoupon` 改为复用它，消除双套判定；`GET /admin/coupons` 附带派生 `state`/`reasons`；列表徽章显示主状态 + `also exhausted` 副行；KPI 改成 `Live now / N scheduled · M closed` |
| 回归 | `api-test.js` §9f：断言 `SUMMER20` 的 `state==='expired'` 且 `reasons` 含 `exhausted`；造 `limit=1` 的券真用掉一次，断言第二次报 `COUPON_EXHAUSTED` 而非 `COUPON_EXPIRED` |
| 遗留 | 存储的 `status` 字段保留未删（写接口还在用）。**新增券时它仍会被写，但已不参与任何展示与校验** —— 这是有意的，删字段会让老数据与导入脚本一起崩 |

### DEF-013　退款金额没有上限，`amount: 9999` 会真的退 9999　🔴　**已修**

| 项 | 内容 |
|---|---|
| 发现 | 2026-11-16，补 §6.2 空洞第 8 条「退款金额不超过净额」时，先手工打了一发：一张 **$97.90** 的订单，`POST /refund {amount: 9999}` —— **系统照收**，`status` 直接变 `refunded`，`refundedTotal` 冲到 $10096.90 |
| 危险点 | 这条路径不对账、不校验、不看剩余额。运营手滑多打两个 0，或者任何拿到后台令牌的人，都能把一笔订单退成十倍金额。**这是这套系统里唯一能单次直接亏钱的接口** |
| 根因 | `applyRefund` 里 `const amount = b.amount != null ? b.amount : o.total - o.refundedTotal` —— 传什么就退什么，`b.amount` 从未与订单总额比较过 |
| 修复 | ① 上限：`amount > 剩余可退额` → 422 `REFUND_EXCEEDS_REMAINING`（带 `remaining` / `requested`）；② 全额路径不允许只退一部分（否则订单标了 `refunded` 其实没收尾，客户、账、报表三处都会错）→ 422 `REFUND_AMOUNT_MISMATCH`，要退部分金额请明确传 `items[]`；③ `amount <= 0` → 400；④ **单位修正**：首版修复写成 `toD(b.amount)`，而 `toD` 的入参是「分」，于是 9999 被当成 99.99 放过去了 —— 单位混用不报错，只算错 |
| 回归 | `api-test.js` §7c 九条：超额拒 / 拒绝幂等（不留副作用）/ 超剩余额拒 / 整单路径只退一部分拒 / 退 0 拒 / 整单退只退剩余 / 金额等于剩余时结清 |
| 教训 | 「金额上限」这种校验，只要不写用例就永远不会有人去做 —— 因为它不影响正常流程，正常流程里没人填 9999 |

### DEF-014　一次写盘失败后，数据库永远不再落盘（进程照常应答）　🔴　**已修**

| 项 | 内容 |
|---|---|
| 发现 | 2026-11-16，验证 DEF-013 时发现：接口返回了订单号 `#LG1147`，但 `db.json` 里最大单号还是 `#LG1145`，文件 mtime 停在几分钟前的复位那一刻 |
| 现象 | 进程正常运行、所有接口 200、内存里数据完全正确 —— **只有磁盘上的文件不再更新**。重启一次，这几分钟内的订单/退款全部消失 |
| 根因 | `flush()` 的实现是 `writeQueue = writeQueue.then(...)`。**这个链条一旦有一环 reject（磁盘满、`.tmp` 被占、rename 跨设备），后续每一次 `.then` 都会被跳过**，而且没有人 `catch` —— 只在 stderr 留一条 unhandled rejection，业务侧毫无感知 |
| 为什么危险 | 它伪装成「一切正常」。没有报错、没有告警、盘点时才发现少单。而且这轮之前**没有任何测试会碰它**：所有用例只断言接口返回，没人断言「写进文件了」 |
| 修复 | ① 每次拼接前 `.catch(() => {})` 把链条拉回 resolved，一次失败不再永久卡死；② 失败必须留痕：`lastWriteError` + `console.error` + `GET /health` 暴露 `storage.ok`；③ 成功一次自动清空错误 |
| 回归 | `/health` 返回 `storage:{ok:true,lastWriteError:null}`；下单 + 部分退款后核对 `db.json` 的 mtime 与单号确实变了（手工验证，见下） |
| 遗留 | 没有自动化用例断言「写盘成功」。做法：在 §0 复位之后加一条「跑完整套后文件 mtime 必须变化」。**下一轮补** |
| 教训 | 「没有报错」不等于「成功了」。持久化层的失败必须自己喊出来，不能指望调用方去检查 |

### Q2　券的 `status` 字段：它到底表示什么，要不要改　✅ 已决策并已实施（2026-11-16 下午，见 DEF-026）

> **落地情况**：取值已缩到 `active` / `disabled` 两值，`expired` / `scheduled` 全部由 `couponState()` 按日期派生；补了 `PATCH /api/v1/admin/coupons/:code` 与后台每行的 Enable/Disable 开关；建券与 PATCH 传 `expired` 一律 400；种子与 `store.normalize()` 双路把老库归一到两值。以下为当初的分析，保留作为决策依据。

**先纠正一个误会：字段没被删，还在库里。** 上一轮说的是「不再参与展示与校验」，不是「删除」。它现在的实际状况是：

| 问题 | 事实 |
|---|---|
| 有哪些取值 | `active` / `scheduled` / `expired` / `disabled`，四个 |
| 谁写入 | 只有建券接口 `POST /admin/coupons` 写一次：`status: b.status \|\| 'active'` |
| 谁能改 | **没人能改**。券的接口只有 GET / POST / DELETE 三个，**没有 PATCH**。建完就冻结 |
| 所以它表示 | 不是「券现在怎么样」，而是**「建券那一刻，运营希望它怎么样」**。一张 11 月建的 `active` 券，到 12 月过期了、名额发满了，字段还是 `active` |
| 谁在读 | 只剩 `couponState()` 一处，读它来判断「运营是不是主动标了作废/停用/排期」。前端列表、查询、校验全部改用派生的 `state` |

**它原本的用途**（据实现反推）：让运营能手动干预三种情况——提前作废（`expired`）、临时停用（`disabled`）、预排未来档期（`scheduled`）。设计意图没错，错在**这三种情况有两种根本不是「状态」，是时间的函数**：

- `expired` 与 `endsAt < now` 是同一个事实，人工再标一遍只会产生矛盾（改 `endsAt` 时忘了改 `status`，两个字段互相打脸）
- `scheduled` 与 `startsAt > now` 同理
- 只有 `disabled` 是真正的人工意图：「与时间无关，我现在就想关掉它」

**还有一半更尴尬**：因为没有 PATCH 接口，**运营连「手动干预」都做不到**。想停用一张已建的券，只能把 `Ends` 改成昨天，或把 `Limit` 改成当前 `Used`——两个都是绕路。也就是说这个字段设计了人工干预的能力，但没给人工干预的入口。

**我的建议**：把字段缩窄成纯人工开关，只留 `active` / `disabled`（或直接改名 `enabled: true/false`），`expired` / `scheduled` 一律交给时间派生，**同时补一个 `PATCH /admin/coupons/:code` 用来切换启用状态**。这样字段名不再撒谎，运营也真的能停券。代价：种子数据的 4 张券要改（`BF30` 的 `scheduled` 靠 `startsAt` 已能表达，`SUMMER20` 的 `expired` 靠 `endsAt` 已能表达），加接口与后台按钮，约 1 小时。

**如果决定保留现状也可以**：`couponState()` 已经把两者合并，只要没人手动改库，行为是对的。风险是以后有人直接改 `db.json` 时以为改 `status` 有用，以及教程里「要停用就改状态」这句话是错的（已在教程 §6.1 改为如实说明「没有停用按钮」）。

**两条 🔴 的共同点**：都不是业务逻辑写错，而是「测试设施自己会破坏数据」。这类缺陷最危险 —— 它让后续所有测试结论都建立在被篡改的数据上，而且看起来一切正常。

**DEF-017 / DEF-018 是同一个根因**：`U.pic()` 生成的 `<img>` 带 `width="900" height="900"` 属性。这两个属性不是"占位提示"，而是生效的 CSS 尺寸；只要某处 CSS 只收窄了 `width`，属性里的 `height:900px` 就原样生效，`aspect-ratio` 根本没机会参与。逐处打补丁修了两次之后改成从根上治：

```css
:where(img[width][height]){height:auto}
```

`:where()` 把特异性压到 0 —— 任何 CSS 明确写了 `height` 的地方（`.card__media img{height:100%}` 这类真正需要拉伸裁切的）照旧覆盖它；只写了 `width` 的地方，高度就按图片自带比例走，不会再出现竖条。全站 10 个页面 × 2 视口扫描确认：竖条 **0** 处。

### 6.5 一条测试方法上的教训（不是产品缺陷）

「购物车抽屉换页不收起」最初被判成产品缺陷，截图里抽屉确实盖在结账页上。查到底发现是**测试脚本自己抄了近路**：脚本用 `location.hash = href` 直接改地址，绕过了那个链接的点击处理器，于是"关抽屉"的副作用没执行。改成真点链接后行为完全正常。

| DEF-029 | 首页发**两次** bootstrap（10KB + 19KB，串行）。`boot()` 不带 `with=home`，渲染时发现缺 home 数据再补一次 | 🟠 | 已修：落地页判定后一次取全 |
| DEF-030 | 第一个 API 请求要等 11 个 JS 文件下完才发出（Fast 3G 实测 1.4 秒），LCP 整段卡在后面 | 🟠 | 已修：`index.html` 内联预取，`bootLoad()` 认领该 Promise |
| DEF-031 | 首屏大图靠 JS 插进 DOM，2.1 秒才开始下载 | 🟠 | 已修：`<link rel=preload as=image imagesrcset>`，与 `<picture>` 同一套 srcset 去重 |
| DEF-032 | 首屏之下的三张 mood tile（820w，合计约 252KB）只加了 `loading=lazy`，仍在懒加载预取半径内，与首屏大图抢同一条 1.6Mbps 连接 | 🟡 | 已修：`fetchpriority=low`，实测这些图不再计入首屏传输（711KB → 436KB） |
| DEF-033 | 手机菜单里没有 Account / Wishlist，这两个入口只存在于头部两枚图标里 —— 而它们恰好是最小的两个热区 | 🟡 | 已修：菜单补两条 |
| DEF-034 | `--ckh` 只在渲染时算一次，转屏或拉窗口后过期（竖屏 100px 的量到横屏仍按 100px 留白） | 🟢 | 已修：resize（防抖）/ orientationchange 重算 |
| DEF-035 | `index.html` 里 `TG_API_BASE` 那段内联脚本复制了两遍 | 🟢 | 已修：删掉重复 |
| DEF-036 | 轮播指示条是 `<i>`，没有可聚焦控件的语义，键盘与读屏都到不了 | 🟡 | 已修：随 `<button>` 改造一并解决 |

**DEF-028 值得单独说一句**：它不是「性能优化」，是合规问题。此前 CSP 明确放行了 `fonts.gstatic.com`，等于在策略层给这个外传开了口子。现在两条外链都删了，CSP 也收窄 —— 以后谁再贴回一段 Google Fonts 的 `<link>`，浏览器会当场拦下并报错，而不是悄悄把访客 IP 发出去。

### 7.3 性能前后对比（同一个脚本、同一台机器、Fast 3G + 4x CPU）

| 指标 | 改前 | 改后 |
|---|---|---|
| FCP | 984ms | 1012ms |
| LCP | **4596ms** | **2312ms** |
| Load | 1415ms | 1446ms |
| 传输 | 711KB | **436KB** |
| 首屏大图开始下载 | 2065ms | **209ms** |
| bootstrap 请求次数 | 2（串行） | 1（解析 HTML 时即发出） |

FCP 与 Load 基本没动是有原因的：这个站的首页是**客户端渲染**，骨架要等 11 个 JS 文件下完，所以「第一个像素」的时间由 JS 决定，压不下来。真正被改掉的是 LCP —— 它原来等的是「JS 跑完 + 再取一次数据 + 再下 117KB 大图」，现在大图与数据都在解析 HTML 时就并行开始了。

**下一步该怎么办（不属本轮范围）**：把首页做成服务端渲染，FCP 才能进到 1 秒内。这是架构改动，需要单独排期，不在「上线前收口」里做。
