## 2 逐条

### DEF-001　券的「过期」与「发满」混为一谈　🔴　**已修**

| 项 | 内容 |
|---|---|
| 发现 | 2026-11-16，核对 `SUMMER20` 时发现：`used=640 / limit=640` 且 `endsAt=2026-08-31`，列表徽章显示 `expired`，KPI「Live now」却把它算成活的 |
| 现象 | ① 后台券列表直接渲染存储的 `status` 字段；② 该字段只在运营**手工**改时才变，「过期」和「发满」是随时间与用量自己发生的，没人会回去改；③ 于是列表会长期撒谎；④ 一张券同时过期又发满时，只显示其中一个原因 |
| 根因 | 券状态**没有派生逻辑**，把「人工快照」当成了「事实」。`resolveCoupon` 里另写了一套判定，两套各走各的 |
| 定性 | **产品问题，不只是技术问题**（用户 2026-11-16 判定）：过期就是过期，发完就是发完，状态必须区分，且同时成立时要同时可见 |
| 修复 | `pricing.couponState(c, now)` 为唯一事实来源，返回 `{ state, reasons[] }`；优先级 `expired > disabled > exhausted > scheduled > active`（expired 排第一是客户视角：说「过期」他知道自己来晚了，说「不再有效」他会以为拿错了码）；`resolveCoupon` 改为复用它，消除双套判定；`GET /admin/coupons` 附带派生 `state`/`reasons`；列表徽章显示主状态 + `also exhausted` 副行；KPI 改成 `Live now / N scheduled · M closed` |
| 回归 | `api-test.js` §9f：断言 `SUMMER20` 的 `state==='expired'` 且 `reasons` 含 `exhausted`；造 `limit=1` 的券真用掉一次，断言第二次报 `COUPON_EXHAUSTED` 而非 `COUPON_EXPIRED` |
| 遗留 | 存储的 `status` 字段保留未删（写接口还在用）。**新增券时它仍会被写，但已不参与任何展示与校验** —— 这是有意的，删字段会让老数据与导入脚本一起崩 |

### DEF-002　库存「不够」与「卖光」共用同一个顶层错误码　🟠　**已修**

| 项 | 内容 |
|---|---|
| 发现 | 2026-11-16，读 `pricing.js:102` 时看到：无论剩几件，顶层一律 `throw E.unprocessable('OUT_OF_STOCK', …)`，真正的 `INSUFFICIENT_STOCK` 塞在 `details[0].code` 里 |
| 危险点 | **测试镜像了实现**：`unit-core.js:113` 断言 `r.code === 'OUT_OF_STOCK'`，与错误实现完全一致，所以这条断言永远是绿的。这是最坏的一类绿灯 —— 它不只没抓到问题，还替问题背书 |
| 影响 | 前端只显示 `error.message`，客户无感；但任何**按 code 分支**的调用方（后台、第三方、以后的移动端）都会走错分支：把「改个数量就能买」当成「彻底没货」 |
| 修复 | 顶层码跟随 `problems[0].code`；`prototype/core.js` 同步（原来也是统一 `OUT_OF_STOCK`）；`unit-core.js` 拆成两个场景分别构造：库存 3 要 5 → `INSUFFICIENT_STOCK`，库存 0 要 1 → `OUT_OF_STOCK` |
| 回归 | `api-test.js` §8b 用负数补货把库存清到 0，先测 `OUT_OF_STOCK`，再补 3 件测 `INSUFFICIENT_STOCK`，最后补回原值 |

### DEF-003　订单号前缀与品牌不一致（存量 90 单全是 `#TG`）　🟠　**已修**

| 项 | 内容 |
|---|---|
| 发现 | 2026-11-16，用户指出「新品牌已更新，数据和文档都要用最新的」 |
| 现象 | 代码里 `nextOrderNumber()` 返回 `'#TG' + n`；SKU 早在改名时批量换成 `LG-`，**订单号漏了**；库里 90 单全部 `#TG10xx`，客服照单号查、客户报单号都对不上品牌 |
| 修复 | `checkout.js` / `core.js` / `seed.js` / 前端占位符 `#TG1041` 全部改 `#LG`；存量数据迁移：90 个 `orders[].number` + 141 处零散引用（审计日志、内容页、历史文案）统一改为 `#LG`；`db.seed.json` 基线同步，否则复位一次又变回去 |
| 回归 | `api-test.js` 断言 `/^#LG\d+$/`；`unit-core.js` 断言单号前缀 `#LG`；`accept-ui.js` 订单页断言 `/LG/` |
| 备份 | `app/server/data/db.bak-before-lg-2026-11-16T04-16-13-940Z.json` |
| 注意 | 审计日志里的历史单号也一起改了。**这是刻意的**：日志的用途是「这笔操作发生在哪一单上」，不是「当时那单叫什么」。改了才能用现在的单号搜到当时的操作 |

### DEF-004　`limit: 0` 建券被系统悄悄改成 1　🟡　**已修**

| 项 | 内容 |
|---|---|
| 现象 | `admin.js` 建券：`Math.max(1, parseInt(b.limit, 10))`。运营想建一张「名额已用完」的券，存进去变成「还剩 1 个名额」 |
| 为什么是问题 | 系统自己改了运营的意思。且这个「改」是不可见的 —— 保存成功后看到的是 `1`，不是 `0`，没人会怀疑 |
| 修复 | 改为 `Math.max(0, …)`；前端表单 `min="1"` → `min="0"`，标签改成 `Usage limit (blank = ∞, 0 = closed)` |
| 回归 | `api-test.js` §9f：`limit=0` 必须建成功且 `limit===0`，随后校验立刻报 `COUPON_EXHAUSTED` |

### DEF-005　测试数据污染基线（`AU Test Necklace` 进了 `db.seed.json`）　🔴　**已修**

| 项 | 内容 |
|---|---|
| 发现 | 2026-11-16，复位后商品数仍是 38，其中一个是 `AU Test Necklace N6K21`（2026-11-15 由 UI 验收脚本创建） |
| 危险点 | 基线是**所有回归的起点**。基线里混进一个测试商品，意味着此后每一次「复位再跑」都在一个假数据上跑，而且它会被当作真实商品进 sitemap、进商品列表、进导出 CSV |
| 根因 | `accept-ui.js` 会真建商品，跑完没有清理；某次跑完后又执行了「刷基线」，把测试残留一起写进了基线 |
| 修复 | 从 `db.json` 与 `db.seed.json` 同时删除该商品及其 2 条库存流水（无订单、无评价关联，删除安全）；商品数回到 37 |
| 提醒 | **刷基线之前必须先清测试数据**。这条以前踩过一次（`db.seed.json` 落后 2 款新品，见测试报告 v1.6），这次是反方向 —— 多进来一个。两个方向都只能靠「刷之前先核对商品数」防 |

### DEF-006　`ops` 账号权限位落后于角色预设，看不到新模块　🟠　**已修**

| 项 | 内容 |
|---|---|
| 发现 | 2026-11-16，补完侧栏门控后发现 `ops` 登录看不到 `Articles`，但 `ROLE_PRESETS.ops` 里明明有 `posts:write` |
| 根因 | `effectivePermissions()` 只对 `owner` 做「恒为全权限」兜底，其他角色**读库里存的数组**。`ops` 的权限是几天前 seed 时写进去的，博客上线新增的 `posts:write` 不会自动追加 |
| 影响 | 角色预设升级后，**已有账号静默失去新功能**，且没有任何提示 —— 用户只会觉得「这个功能好像没有」 |
| 修复 | ① 把 `db.json` / `db.seed.json` 里 `owner`(10→13)、`ops`(9→10) 的权限位补齐到当前预设（只加不删，保留人工追加项）；② `seed.js` 本来就引用 `ROLE_PRESETS`，无需改 |
| 遗留 | 这是个**结构性风险不是一次性 bug**：以后每加一个权限位，老账号都要手动补。后台「员工」页改权可以做到，但没人会主动做。**建议**：在 SDD 里把「新增权限位 = 同步内置账号」写成发版检查项 |

### DEF-007　侧栏只有 2 项按权限门控，其余 14 项点了才 403　🟠　**已修**

| 项 | 内容 |
|---|---|

### DEF-008　库存补货只有写死的 `+20`　🟡　**已修**

| 项 | 内容 |
|---|---|
| 现象 | `Inventory` 每行只有一个 `+20` 按钮。进 15 件也点 +20，进 100 件要点 5 次，盘点少了 2 件只能再手工核减 |
| 根因 | 界面把接口能力关掉了 —— `POST …/restock` 一直支持任意整数（含负数），只是没人传 |
| 修复 | 每行加数量输入框（默认 20）+ `Add` 按钮；点击读同行输入框的值；允许负数（核减），输入 0 或非数字直接拦下并提示 |
| 回归 | 截图核对 70 行都有输入框；`api-test.js` §8b 用 `qty:-N` 把库存清零验证负数路径 |

### DEF-009　评价审核没有拒绝理由输入　🟡　**已修**

| 项 | 内容 |
|---|---|
| 现象 | 点 `Reject` 直接拒，理由无处可写。事后有人问「这条为什么被拒」，只能翻审计日志看一个 status 变更，等于没有记录 |
| 修复 | 拒绝时弹输入框（可留空 —— 垃圾评论一眼可判，逼着填只会写出「spam」）；`rejectReason` 存库、进审计日志；卡片上以灰字 + 左侧竖线回显；**改回 approved 时自动清空**，避免下一个人以为被否过两次 |
| 回归 | 手工造一条带理由的 rejected 评价，截图核对回显样式 |

### DEF-010　`pages.journal` 是死键，能改但改了没用　🟡　**已修**

## 3 本轮同时修掉的文档与实际不一致
