## 一、结论

**功能基本闭环，但不能开卖。** 阻断项不在功能，在支付、邮件、域名、备份四项基础设施。

| 维度 | 结论 | 依据 |
|---|---|---|
| 核心购买链路 | ✅ 走通 | 真下 6 单，含优惠券、赠品、幂等、超卖、退款回补 |
| 后台运营链路 | ✅ 走通 | 建/改/上架/导入/发货/退款/补货/审计全部真实执行成功 |
| 空库可用性 | ✅ 可用 | 0 商品、0 集合、0 订单时无白屏、无报错、无 NaN |
| 搜索 | ❌ 不可用 | 搜 "ring" 返回 0 件，站内有 3 件 |
| 导航 | ❌ 一半死链 | 下拉菜单 10 个子项 × 5 个类目全部 404 |
| 支付 | ❌ 假支付 | 订单创建即标记 paid，钱从未进入 |
| 邮件 | ❌ 完全缺失 | 全代码库无任何发信实现 |
| 性能 | ⚠️ 不达标 | 首屏 6.5 s，图片全部载完 16.6 s |
| SEO | ❌ 近乎为零 | 无 sitemap、无 robots、无结构化数据、title 全站恒定 |
| 数据安全 | ⚠️ 有脚本无计划 | `backup.sh` 存在，但 crontab 为空，从不自动执行 |

**一句话**：这套站能演示、能内测、能录屏，但收到第一笔真实订单前，必须先解决 **D-101 支付** 与 **D-104 备份**。

### 3.2 真实执行过的关键动作

这些不是点击看反应，是真的产生了业务结果：

- **真下单 6 笔**：含用券单、触发赠品单、被取消单、被退款单、完成单

## 四、缺陷清单

按「影响开卖」排序。共 28 项：P0 四项、P1 六项、P2 九项、P3 九项。

### P0 · 阻断开卖

| 编号 | 缺陷 | 证据 | 影响 |
|---|---|---|---|
| **D-101** | **支付是模拟的** | `checkout.js:229` 写死 `payment.mode:'simulated'`，订单创建即 `status:'paid'`，`last4` 默认 4242；全代码库无 Stripe SDK、无 webhook、无退款调用 | 顾客填完地址点提交，订单直接变「已付款」，但**一分钱没收到，货会照发** |
| **D-102** | **邮件完全缺失** | 全代码库无 `resend`/`mailer`/`sendMail` 任何实现 | 下单确认、发货通知、退款通知、密码重置全部没有；顾客只能靠截图记单号 |
| **D-103** | **明文 HTTP 传管理员令牌** | 8080 端口无 TLS，`Authorization: Bearer` 明文过境 | 公共 WiFi 下后台口令与令牌可被截获 |
| **D-104** | **有备份脚本，无备份计划** | 服务器 `crontab -l` 为空；`deploy/backup.sh` 从未被调度 | `db.json` 一个文件装着全部生意，卷损坏 = 全部订单与商品永久丢失 |

### P1 · 功能断裂（链路走不通）

| 编号 | 缺陷 | 证据 | 影响 |
|---|---|---|---|
| **D-105** | **全站搜索不可用** | 顶栏搜索回车后跳 `#/collections/best-sellers?q=ring`；接口 `/products/search?q=ring` 正常返 3 件，集合内过滤返 0 件 | 用户搜 "ring" 看到「0 pieces」，站内明明有 3 件戒指。搜索是电商第二入口，等于没有 |
| **D-106** | **导航下拉 50 条死链** | 下拉子项 `ocean/woodland/celestial/floral/for-her/for-him/gifts-for-mom/birthday-gifts/gift-sets/all-necklaces` 全部 404，且在 5 个类目下重复 | 导航是主路径，点进去就是「Page not found」。这些分类是硬编码的，数据库里从未存在 |
| **D-107** | **评价无法写入** | `POST /api/v1/reviews` → 404；后台只有 `GET`+`PATCH` 审核，无新建；从 0 开始时评价永远为空 | 商品页评价区永远空；「59 条评价」是导入出来的假象，UGC 链路不存在 |
| **D-108** | **没有任何导出** | 无订单导出、无商品导出、无客户导出；后台页面无导出按钮 | 对账、发货单打印、ERP 导入全得手工抄 |
| **D-109** | **`?cat=` 参数被静默忽略** | `GET /products?cat=necklaces` 返回全部 13 件 | 后台改「Category」不影响前台归类，归类只能靠集合，两个概念互相打架 |
| **D-110** | **超大请求体断连而非 413** | 传 8 MB 请求体，客户端只看到连接重置，无错误文案 | 用户不知道发生了什么，只看到「网络错误」 |

### P2 · 性能 / SEO / 可访问性

| 编号 | 缺陷 | 实测 | 影响 |
|---|---|---|---|
| **D-111** | 首屏太慢 | hero 出现 **6461 ms**（空库 8144 ms） | 3 秒内看不到任何内容，跳出率极高 |
| **D-112** | 图片全载完太慢 | 首屏图片全部完成 **16659 ms** | 商品图逐张蹦出来 |
| **D-113** | 未开压缩 | `Accept-Encoding: gzip, br` 请求，响应无 `Content-Encoding` | JS+CSS 约 230 KB 原样传输。开 gzip 可降到 ~65 KB |
| **D-114** | 缓存策略反了 | JS/CSS 是 `Cache-Control: no-cache`；`uploads/` 图片反而是 `max-age=604800` | 回访用户每次重新下载 230 KB 代码，图片却缓存得很好 |
| **D-115** | 首屏 4 层串行请求 | `bootstrap` → `products?collection` → `products?limit=1` → `products?limit=8` | 4 个 RTT 串起来。前三个可合并成一次 bootstrap |

| **D-117** | robots.txt / sitemap.xml 不存在 | 两者都返回 HTML（SPA 兜底）200 | 爬虫拿到 HTML 当 robots，收录不可控 |
| **D-118** | 软 404 | `/no-such-page` 返回 200 + 首页 HTML | 无限 URL 都可被索引 |
| **D-119** | 键盘/读屏不可用 | 首焦点落在 `BODY`，`outline: none`；`aria-live` 数量 0；4 个图标按钮无可读标签 | 键盘用户看不到焦点；加购成功/表单错误读屏不播报 |

## 六、性能实测

12 次采样，p50 / p95：

| 资源 | 大小 | p50 | p95 |
|---|---:|---:|---:|
| `/api/v1/health` | 70 B | 283 ms | 913 ms |
| `/api/v1/bootstrap` | ~6 KB | 333 ms | 1328 ms |
| `/api/v1/products?limit=12` | ~8 KB | 805 ms | 1612 ms |
| `/api/v1/products/:handle` | ~3 KB | 310 ms | 1051 ms |
| `/assets/js/app.js` | 49 KB | **2107 ms** | **5102 ms** |
| `/uploads/xxx.png` | 121 KB | **2809 ms** | **6913 ms** |

**诊断**：小响应（API）300 ms 左右，大文件（49 KB JS、121 KB 图）要 2–3 秒——瓶颈是**带宽**，折算约 350 kbps，不是服务端 CPU。三条低成本改善：

1. 开 gzip/br：49 KB JS → ~14 KB（3.5 倍）
2. 商品图转 WebP 900px：121 KB → ~40 KB（3 倍）
3. 静态资源加 hash 文件名 + `max-age=31536000`，改回访为 0 请求

首屏请求瀑布（冷启动）：

```
    0 ms  HTML 请求
 3074 ms  CSS/JS 才开始下载      ← 首个请求就要 3 秒
 6151 ms  bootstrap 返回
 6835 ms  products?collection 返回
 7214 ms  products?limit=1 返回
 7550 ms  products?limit=8 返回
 8144 ms  hero 渲染完成
16659 ms  首屏图片全部载完
```
