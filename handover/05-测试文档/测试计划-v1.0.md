## 1 测试目标

不是"证明能跑"，而是回答三个问题：

| # | 问题 | 怎么回答 |
| --- | --- | --- |
| 1 | **账算得对不对** | 金额、库存、券、客户累计消费，每一项都能被独立复算 |
| 2 | **违规操作挡不挡得住** | 改价、超卖、重复下单、越权、非法状态流转，逐个试 |
| 3 | **前后台是不是同一份数据** | 后台改一个值，前台下一次请求就得变 |

第 1 条是本轮重点。历史上这类缺陷（赠品没进订单、退款不回补库存）不会让页面报错，只会在第一个月对账时暴露——那时已经几百单了。所以本轮把「功能走通」定为及格线，「账目自洽」才定为通过。

## 3 测试策略

### 3.1 分层策略与理由

```
        ┌──────────────┐
        │  E2E  75 条  │  慢（每轮 3~5 分钟）、脆（依赖渲染时序）
        ├──────────────┤
        │  接口 99 条  │  中（每轮 30 秒）、稳（只依赖 HTTP 契约）
        ├──────────────┤
        │ 单元 38 条   │  快（每轮 <1 秒）、最稳（纯函数）
        └──────────────┘
              ↑ 越往下越便宜，所以逻辑尽量往下压
```

**为什么单元测试只有 38 条也能撑住**：因为把定价、库存、退款这些"算账"逻辑抽成了纯函数（`pricing.js` / `core.js`），可以脱离浏览器和 HTTP 直接调用。一笔订单的金额构成有 6 个变量（商品、金属、尺寸、数量、券、配送方式），用接口测要发 3 个请求才能验证一种组合；用单元测试一次能跑 20 种。

**为什么 E2E 只做 75 条**：E2E 每条都要真实渲染，跑一轮 3–5 分钟，不稳定且定位困难。只保留"只有真实浏览器才能验证"的：抽屉自动打开、支付步骤切换、页面间跳转、前后台数据同步。

### 3.2 用例设计方法

| 方法 | 用在哪 | 例子 |
| --- | --- | --- |
| 等价类 + 边界值 | 数量、金额、库存 | 每行限购 10：测 1 / 10 / 11 |
| 状态迁移 | 订单状态机 | 穷举 6 状态 × 6 目标 = 36 种，其中 9 种合法 |
| 判定表 | 优惠券 | 4 个条件（存在 / 有效期 / 门槛 / 余量）组合出 5 类失败原因 |
| 错误推测 | 幂等、并发点击 | 同一 `Idempotency-Key` 连发 3 次 |
| 逆向验证 | 前端伪造价格、越权 | 手工构造带 `unitPrice: 1` 的请求 |

### 3.3 自动化率

**100%**。289 条断言全部由脚本执行，无手工用例。原因：这是个需要反复回归的项目（改一次价格逻辑就要全量重跑），手工回归撑不住。

代价是"看起来像手工才能测的"（比如"这个按钮好不好看"）没有覆盖——这类判断不在测试范围内，属于 UI 评审，已在前几轮由用户直接反馈完成。

## 4 测试环境

| 项 | 配置 |
| --- | --- |
| 操作系统 | Windows 11（Git Bash） |
| Node | v24.14.0（无第三方依赖，只需 Node 自带模块） |
| 浏览器 | Microsoft Edge（`--headless=new`，通过 CDP 驱动） |
| 原型服务 | `http://localhost:4500` |
| 分离版服务 | `http://localhost:4600`（前端 + API 同源） |
| 数据 | `app/server/data/db.json`，基线快照 `db.seed.json` |
| 测试账号 | owner：`owner@tideglassjewelry.com / tideglass2026`<br>ops：`ops@tideglassjewelry.com / tideglass-ops` |
| 启动命令 | `ALLOW_TEST_RESET=1 node app/server/index.js` |

### 4.1 关于 `ALLOW_TEST_RESET`

接口测试会**真的下单、退款、改价**。跑第二遍时数据已被改过，断言必然失败——那样的测试只能跑一次，没有回归价值。

因此服务在 `ALLOW_TEST_RESET=1` 时会注册 `POST /api/v1/__test/reset`，把数据恢复到 `db.seed.json` 基线并清空限流计数。**生产环境不设这个变量，该路由根本不会注册**（不是靠权限挡，而是压根不存在）。

这一条本身也是本轮发现并修复的缺陷（D-013）。

## 6 进度安排

| 阶段 | 内容 | 与开发的关系 |
| --- | --- | --- |
| 阶段 1 | 依据 FRD 与 SDD 拆解用例，编写测试计划与用例 | 开发编码**并行**（不等编码完成） |
| 阶段 2 | 核心逻辑单元测试（38 条） | 逻辑层一落地就跑 |
| 阶段 3 | 接口自动化（99 条） | 接口一可用就跑 |
| 阶段 4 | 端到端与适配（75 + 77 条） | 页面可用后跑 |
| 阶段 5 | 全量回归 + 测试报告 | 开发提测后 |

实际执行时，阶段 1 在编码前完成，阶段 2、3 与编码同步推进——这样缺陷在写下一块代码前就被发现，而不是堆到最后集中爆。

## 8 风险与对策

| # | 风险 | 影响 | 对策 |
| --- | --- | --- | --- |
| 1 | 支付、邮件、物流未真实接入 | 上线后才发现集成问题 | 凭证到位后按《外部资料需求清单》第 11 节逐项验收，每项都要一张真实截图 |
| 2 | 数据层为单文件 JSON | 并发写入风险，压测无意义 | 上生产前迁 PostgreSQL，届时重做并发与性能测试 |
| 3 | 只测了 Chromium 内核 | Safari 用户可能遇到布局或 API 差异 | 上线前用真实 iPhone / Mac 补一轮手工冒烟 |
| 4 | E2E 依赖渲染时序 | 偶发失败被误判为缺陷 | 已加"强制布局 + 丢弃首帧"；连续失败 3 次才判定为缺陷 |
| 5 | 测试数据是演示数据 | 真实数据分布不同（如超长商品名、超大订单） | 上线前用真实 SKU 数据跑一轮 |
| 6 | 自动化覆盖不到"好不好看" | 视觉问题漏到线上 | 视觉由 UI 评审把关，不纳入自动化 |
