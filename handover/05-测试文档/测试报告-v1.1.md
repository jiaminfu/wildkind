## 4 关键验证：账目自洽

这是本轮最重要的一组验证，单列一节。

### 4.1 库存流水对账

| 项 | 结果 |
| --- | --- |
| SKU 总数 | 67 |
| 流水条目 | 200 条（开账 67 / 卖出 123 / 退款回补 10） |
| **末条余额 = 当前库存** | **67 / 67 全部一致** |
| 负余额条目 | 0 |
| 时间升序（供倒序查询） | 是 |

**对账方法**：逐个 SKU 取流水中最后一条的 `balanceAfter`，与该 SKU 的 `stock` 比对。这条不成立，就说明有库存变动绕过了流水入口——是缺陷，不是"数据不准"。

### 4.2 一单完整金额链路

实测一笔订单，逐项核对：

| 环节 | 数值 | 校验 |
| --- | --- | --- |
| 商品小计（2 件 × $82） | $164.00 | = 82 × 2 |
| `TIDEGLASS10` 10% 折扣 | −$16.40 | = 164 × 10% |
| 折后金额 | $147.60 | = 164 − 16.40 |
| 运费（折后 ≥ $95） | $0.00 | 免邮门槛生效 |
| 赠品（折后 ≥ $120） | 1 件，$0.00 | 计入明细、不参与计价 |
| **应付总额** | **$147.60** | = 147.60 − 0 + 0 |

前后台一致性：后台订单详情的 `total` 与前台报价 `total` 完全一致，**分毫不差**。

### 5.4 缺陷分布说明

```
加购 → 下单 → 退款 链路  ████████████ 7 个 S1（全在此）
数据一致性              ███ 3 个
UI 适配与显示            ███████ 7 个
文档与实现不符           ██ 2 个
功能缺失                ██ 2 个（内容页 404、看板错链）
```

**7 个 S1 全部集中在同一条链路上**，不是巧合：这条链路状态最多、跨页面最多、也最容易"看起来跑通了"。这正是把「能跑通」和「算得对」分成两个验收层级的原因。

**v1.1 补的 5 个缺陷有一个共同点**：都不是核心链路，而是"边上没人走的地方" —— 页脚链接、登录页、看板跳转、窄屏下的 KPI。这类缺陷单看每一处都很小，但它们全部落在用户真实会点到的地方，上线后被投诉的概率不比 S1 低。所以回归不能只跑主流程。
