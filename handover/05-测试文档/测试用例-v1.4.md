## 2 核心场景详细用例（12 条）

这 12 条覆盖了本轮修正的 7 处业务缺陷，以及 4 个"最容易被绕过"的安全点。

---

### TC-CORE-D01 超量下单必须整单拒绝（对应 FRD 12.11 缺陷 3）

| 项 | 内容 |
| --- | --- |
| 优先级 | 🔴 P0 |
| 覆盖需求 | FR-S-054 库存提示、FR-A-017 库存可视化 |
| 前置条件 | 某 SKU 可售库存为 N（如 Solstice Sun Necklace / Gold = 11）；购物车为空 |
| 自动化 | `TC-CORE-05`~`08`、`TC-API-19` |

**步骤**

1. 向购物车加入该 SKU 数量 N（等于库存）。
2. 再加购 1 件，使购物车数量达到 N+1。
3. 调用 `POST /checkout/quote`。
4. 检查返回码与订单表。

**预期结果**

| # | 断言点 | 期望 |
| --- | --- | --- |
| 1 | HTTP 状态 | `409` |
| 2 | `error.code` | `OUT_OF_STOCK` |
| 3 | `error.details[0]` | 含 `sku` / `requested` / `available` 三个字段 |
| 4 | 订单表条数 | **不变**（不产生部分成交的订单） |
| 5 | 该 SKU 库存 | **不变**（不能扣成负数） |

**为什么必须整单拒绝而不是"有多少卖多少"**：部分成交会让用户收到的件数与付款金额对不上，退款流程立刻变成噩梦。而且「买 3 件只发 2 件」在客诉里几乎无法解释。

---

### TC-CORE-D02 赠品必须作为 0 元行进订单并扣真实库存（缺陷 1）

| 项 | 内容 |
| --- | --- |
| 优先级 | 🔴 P0 |
| 覆盖需求 | FR-S-115 赠品库存不足不阻断主单、FR-A-005 订单详情含赠品 |
| 前置条件 | 赠品门槛 $120；赠品 SKU 库存 ≥ 1；主商品加购至折后 ≥ $120 |
| 自动化 | `TC-CORE-11`~`17`、`TC-API-31`~`33` |

**步骤**

1. 加购主商品至小计 $164（≥ $120）。
2. 报价，确认返回体里 `gift` 非空且带 `image`。
3. 下单。
4. 查订单明细与该 SKU 库存流水。

**预期结果**

| # | 断言点 | 期望 |
| --- | --- | --- |
| 1 | 订单 `items` 长度 | 主商品 + 1 条赠品行 |
| 2 | 赠品行 `unitPrice` | `0` |
| 3 | 赠品行 `qty` | `1` |
| 4 | 赠品行 `isGift` | `true` |
| 5 | 订单 `total` | 等于主商品折后金额，**赠品不参与计价** |
| 6 | 赠品 SKU 库存 | 减 1（不是写死的 99） |
| 7 | 库存流水 | 出现一条 `reason = sale`、`refId = 本单号` 的记录 |

**扩展场景（负向）**：赠品库存为 0 时，主单**仍可下单成功**，赠品行不出现或显示"赠品已赠完"，结算不被阻断（FR-S-115）。

---

### TC-CORE-D03 优惠券下单时必须按最终金额复核（缺陷 4）

| 项 | 内容 |
| --- | --- |
| 优先级 | 🔴 P0 |
| 覆盖需求 | FR-S-073 结算页、BR-17 叠加规则与最低金额保护 |
| 前置条件 | 存在门槛 $95 的券 `WELCOME15`；购物车小计已 ≥ $95 |
| 自动化 | `TC-CORE-18`~`21`、`TC-API-22`~`26` |

**步骤**

1. 加购至小计 $120，应用 `WELCOME15`，确认券生效。
2. 把数量减到小计 $82（低于 $95 门槛）。
3. 提交下单。

**预期结果**

| # | 断言点 | 期望 |
| --- | --- | --- |
| 1 | 返回码 | `422` |
| 2 | `error.code` | `COUPON_INVALID` |
| 3 | `error.message` | 说明"再买 $X 可用"，含差多少 |
| 4 | 会话中的券 | **已被清空**（不能让用户带着失效券反复重试） |
| 5 | 订单表 | 无新订单 |
| 6 | 金额 | 不出现"减量后仍享满减" |

**为什么要在下单时再查一次**：报价与下单之间可能隔了 15 分钟，这期间用户改了数量、别人买走了库存、券被用完了。只在加购时校验一次，等于把风险留给了最后一步。

### TC-CORE-D04 订单号必须全局唯一且单调递增（缺陷 2）

| 项 | 内容 |
| --- | --- |
| 优先级 | 🔴 P0 |
| 覆盖需求 | FR-S-077 生成订单号、BR-13 单号规则 |
| 前置条件 | 库内最大单号为 `#TG1130` |
| 自动化 | `TC-CORE-01`~`04` |

**步骤**

1. 下单，得单号 A。
2. **删除中间一张历史订单**（模拟数据清理或误删）。
3. 再下单，得单号 B。
4. 遍历库内全部单号。

**预期结果**

| # | 断言点 | 期望 |
| --- | --- | --- |
| 1 | 单号格式 | 匹配 `/^#TG\d+$/` |
| 2 | A 的数字部分 | 大于此前库内最大值 |
| 3 | B 的数字部分 | 大于 A |
| 4 | 全部单号去重后条数 | 等于订单总数（无重复） |

**原实现为什么错**：用「基数 1041 + 当前订单条数」发号。删掉一张单，条数变少，下一个号就会和已有的撞上。改成「解析库内最大数字 +1」后，删除、清库、重载都不会撞。

### TC-CORE-D05 退款必须回补库存、释放券、冲减客户消费（缺陷 7）

| 项 | 内容 |
| --- | --- |
| 优先级 | 🔴 P0 |
| 覆盖需求 | FR-A-006 订单操作、FR-A-067 退款后评价复核、BR-12 退款方式 |
| 前置条件 | 存在一笔 `paid` 订单，含 2 件商品并使用过券 |
| 自动化 | `TC-CORE-22`~`28`、`TC-API-61`~`68` |

**步骤**

1. 记录该 SKU 退款前库存 S、客户累计消费额 M、券使用次数 U。
2. 调用 `POST /admin/orders/:number/refund`（`restock: true`）。
3. 重新读取上述三个值。
4. 再次调用同一退款接口（重复退款）。
5. 查库存流水。

**预期结果**

| # | 断言点 | 期望 |
| --- | --- | --- |
| 1 | 订单状态 | `refunded` |
| 2 | 库存 | S + 该单件数 |
| 3 | 客户累计消费 | M − 该单金额 |
| 4 | 券使用次数 | U − 1（券被释放） |
| 5 | `refundedAt` / `restockDecision` | 均已记录 |
| 6 | 重复退款 | `409 CONFLICT`，且**库存不再变化** |
| 7 | 库存流水 | 出现 `reason = refund` 的记录，`balanceAfter` 与当前库存一致 |

**同时验证禁止绕过**：调用 `PATCH /admin/orders/:number/status` 且 `status = refunded`，必须返回 `409`（`TC-API-72`）。否则运营点错一次，库存就永远对不上。

### TC-CORE-D06 邮箱大小写不能造出两个客户（缺陷 6）

| 项 | 内容 |
| --- | --- |
| 优先级 | 🔴 P0 |
| 覆盖需求 | FR-S-074 访客结算、FR-S-150 订单归属、BR-20 邮箱匹配 |
| 前置条件 | 客户表中无 `case.test@example.com` |
| 自动化 | `TC-CORE-34`~`38` |

**步骤**

1. 用 `Case.Test@Example.COM` 下一单。
2. 用 `case.test@example.com` 再下一单。
3. 查客户表与两笔订单的 `email` 字段。

**预期结果**

| # | 断言点 | 期望 |
| --- | --- | --- |
| 1 | 订单 1 的 `email` | `case.test@example.com`（已小写） |
| 2 | 客户表条数 | **1**（不是 2） |
| 3 | 该客户 `orders` | `2` |
| 4 | 该客户 `spent` | 两单金额之和 |

**为什么这条重要**：客户档案决定复购分层（New / Repeat / VIP）与后续邮件营销的受众。一个人被记成两个人，等于营销预算按人头算时通胀了一倍。

### TC-CORE-D07 配送方式与运费必须同源（缺陷 5）

| 项 | 内容 |
| --- | --- |
| 优先级 | 🔴 P0 |
| 覆盖需求 | FR-S-073 结算页配送方式 |
| 前置条件 | 标准运费 $6.9，加急 $19.9 |
| 自动化 | `TC-CORE-39`~`41` |

**步骤**

1. 在结算页选择 `Express`。
2. 下单。
3. 检查订单的 `shippingMethod` 与 `shipping` 两个字段。

**预期结果**

| # | 断言点 | 期望 |
| --- | --- | --- |
| 1 | `shippingMethod` | `Express` |
| 2 | `shipping` | `19.9`（不是标准运费 6.9） |
| 3 | 会话缓存的配送方式 | 与订单一致 |

**原实现为什么错**：运费按会话缓存算，订单字段读表单值，两者可能不是同一个。用户选了加急却按标准收费（或少收），单笔金额不大但会持续发生。

### TC-UI-D12 双端必须无横向溢出且内容真的渲染出来

| 项 | 内容 |
| --- | --- |
| 优先级 | 🟡 P1 |
| 覆盖需求 | FRD 验收清单第 15 项、用户既定的 PC/移动适配要求 |
| 前置条件 | 门店端与后台均可访问，已登录后台 |
| 自动化 | `TC-UI-01`~`TC-UI-77` |

**步骤**

1. 在 390 / 768 / 1440 三个视口宽度下，逐个打开 15 个路由。
2. 每路由测量 `documentElement.scrollWidth − clientWidth`。
3. 同时检查该路由的关键元素是否存在（如 `.cartlines`、`.atable`、`.revcard`）。

**预期结果**

| # | 断言点 | 期望 |
| --- | --- | --- |
| 1 | 横向溢出量 | ≤ 1px |
| 2 | 关键元素 | 全部存在（防"页面在但内容空"） |
| 3 | console error / 未捕获异常 | 0 条 |

**为什么要查"关键元素存在"**：异步 SPA 最容易出的问题不是报错，而是接口失败后页面渲染成空壳——不报错、不白屏，只是什么都没有。只测溢出量会漏掉这类。

**已修的相关缺陷**：后台看板在 390px 下溢出 186px（`D-010`）、后台汉堡图标渲染成空白方块（`D-011`）。二者都是本轮 TC-UI 抓出来的。
