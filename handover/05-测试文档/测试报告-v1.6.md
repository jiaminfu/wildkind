## 2 销售税：验的是什么，为什么这么验

### 2.1 断言重点不是"算得对"，而是"不会错收"

算错税是账面问题，**错收税是合规问题**：多收一笔要退款、要修正申报，退比收难十倍。所以 8 条接口用例里，5 条是在防"不该收的时候收了"。

| # | 用例 | 断言 | 结果 |
| --- | --- | --- | --- |
| 1 | 后台填 `California: 7.25` | 落库为 `CA: 0.0725`（百分数自动换算） | ✅ |
| 2 | 加州报价 | `taxRate === 0.0725`、`taxState === 'CA'` | ✅ |
| 3 | 加州税额 | `tax === round2((小计 − 折扣 + 运费) × 0.0725)`，基数由测试独立推一遍 | ✅ |
| 4 | `state: 'California'` | 归一到 `CA`，税额与传 `CA` 完全一致 | ✅ |
| 5 | `state: 'Oregon'`（未注册） | 税额 `0`，但 `taxState` 仍回 `OR`（便于事后追溯） | ✅ |
| 6 | `state: 'Atlantis'`（看不懂） | 税额 `0`、`taxState` 空、**不报错**（不因为一个脏字段让整单下不了） | ✅ |
| 7 | 报价按 CA、地址填 NY | `422 PRICE_CHANGED`，**不许"按报价收钱、按新地址记账"** | ✅ |
| 8 | 跑完关掉税并清空州 | `enabled=false`、`rates={}`，不给后续用例留税 | ✅ |

第 3 条的写法值得说明：测试**没有**用服务端返回的应税基数去算，而是自己按「小计 − 折扣 + 运费」再推一遍。两边对上才算对——如果只拿服务端的数反算服务端的数，那永远对，也永远测不出东西。

### 2.2 浏览器层 15 例：抓的是"接口绿但页面不对"

这一层专门盯一类接口测不出来的问题：

| 观察到的现象 | 真因 | 现状 |
| --- | --- | --- |
| 结算按钮写 `$82.90`、摘要 Total 写 `$88.91`（截图对照发现） | 改州后只重算了摘要，没更新按钮文案 | 已修，并加了「按钮金额必须等于 Total」这条断言 |
| 改州后地址被清空 | 早期实现是整块重渲染 | 已改为只重画 Tax / Total / 按钮三行 DOM |
| 后台税率框用比例字体，一列数字对不齐 | 少了等宽字体 | 已改 `ui-monospace` |
| 确认信 Subtotal 152 → Total 164.16，中间 12.16 没解释 | 邮件模板漏了税行 | HTML + 纯文本两版都补 |

### 2.3 没验到的部分（写清楚，不糊）

- **真实收税**：本地和线上都没有真实买家，税是算出来的，不是收进来的。
- **申报表能否被州里接受**：`tax.csv` 的列名是照着常见申报表的口径做的，**没有对过任何一个州的实际表格**。首次申报请人工核对一遍，别直接上传。
- **跨州组合**：只验了 CA / NY / OR / TX 四州与「未注册州」「未知州名」两类边界，没有穷举 50 州（穷举的意义也不大，逻辑是按州查表，不是按州硬编码）。

## 2b 部分退款：这次修的是"直接亏钱"

### 2b.1 原来的问题

后台只有一个 `Refund` 按钮，退整单。多件订单退一件，系统把**整单的钱退回去**。
这不是体验问题，是每发生一次就亏一次，而且第一笔真实部分退货必然踩到。

### 2b.2 金额口径（写死在服务端，前端不重算）

| 组成 | 规则 |
| --- | --- |
| 商品 | 该行单价 × 退的件数，再扣掉这一行按金额占比分摊的优惠 |
| 税 | 该行按净额占比分摊的税额。**退了货不退税收，等于替州里多吃一笔** |
| 运费 | 只有最后一件付费商品退完时才退；部分退不退运费 |

分摊用「累计目标法」：按累计退掉的数量算这一行"一共该退多少"，减去已退的部分。
所以同一行分三次退，也不会攒出四舍五入的偏差。全程整数分运算，最后一行吃余数。

### 2b.3 断言清单（接口 12 例）

| # | 用例 | 结果 |
| --- | --- | --- |
| 1 | 建一张两行订单（2 件 + 1 件，带 10% 券） | ✅ |
| 2 | 退 1 件 = 单价 − 该件分摊的折扣（$79.20） | ✅ |
| 3 | 订单**没有**被标成整单退款，状态仍为 `paid` | ✅ |
| 4 | `refunds[]` 留痕 1 条、`partiallyRefunded=true` | ✅ |
| 5 | 库存按件回补（53 → 54），不是整行 | ✅ |
| 6 | 退 5 件被拒 400（超过剩余可退） | ✅ |
| 7 | 一次退两行 200 | ✅ |
| 8 | 累计退款 = 整单金额（$226.80） | ✅ |
| 9 | 退完自动转 `refunded` | ✅ |
| 10 | 退款流水累计 2 条 | ✅ |
| 11 | 小额订单确实收了运费（$6.90） | ✅ |
| 12 | 退最后一件把运费一并退掉（$82.90） | ✅ |

**第 9 条第一版是红的**，原因值得记：判断"是否退完"时把**赠品行**也算了进去。
赠品是 0 元行、客户不会"退赠品"，`refundedQty` 永远是 0，于是货全退光了订单还挂在 `paid` 上。
修法是把赠品排除在完成判定外，但在整单完成时把赠品库存一并补齐——下单时赠品是扣了库存的，不补就会出现"库存少一件、账上找不到原因"。

### 2b.4 浏览器层 17 例

| 检查 | 说明 |
| --- | --- |
| 商品表有 `Refund` 列，每行一个输入框 | 赠品行没有输入框（显示 `gift`） |
| 输入框 `max` = 该行剩余可退件数 | 2 件与 1 件两行分别显示 `2` / `1` |
| 点 `Refund selected` 只退填了的那几件 | 退款后接口回读 `refundedQty = 1/2`，不是 `2/2` |
| **可退上限随退款递减**（2 → 1） | 上限不刷新的话页面还能再点一次退 2 件，服务端虽会拦，但人会以为"按钮能点就是能退" |
| 显示「Refunded so far」与退款历史表 | 下次退款不用靠人脑记 |
| 状态区出现 `Partially refunded` | 与 `refunded` 区分，避免误判订单已关闭 |
| `Refund whole order` 仍然保留 | 一刀清的场景还在 |

### 2b.5 没验到的

- **真实退款到卡**：PayPal 仍是沙盒，退款走的是沙盒 API。算法与状态机验过了，钱没真退过。
- **跨月退款对申报的影响**：`tax/report` 的口径是"部分退款按原额计入，报税时手工冲减"，因为各州对"退款后是否调减、何时调减"要求不同，自动冲减反而容易报错。这一条**必须人工核对**，不是系统能替你决定的。

## 2c 物流额度：把「一次订阅、终身免费查」用对

### 2c.1 背景

17TRACK 免费账户每月 100 个订阅额度，1 号重置、**不累积**。官方计费规则里有两句话直接决定成本：

1. **只有 register 扣额度**。订阅成功后的查询、刷新、webhook 推送、自动追踪，全部不扣。
2. **注册时指定翻译语言会额外扣 1 个**（`registration + translation = 2`）。

第二句是钱。我们只发美 / 加 / 英，承运商轨迹本来就是英文，传 `lang` 等于花钱把英文翻成英文 —— **100 个额度会变成 50 单**。已删掉。

### 2c.2 额度耗尽不能被误判成「单号无效」

额度用完返回 `-18019908`（`Your quotas have ran out.`），撞当日上限返回 `-18019907`。原来这两个都走通用失败分支，在订单上记成「订阅失败」——运营看到会去**催客户重报单号**，而真正该做的是等下月 1 号重置。

现在单独识别，文案改成「本月自动追踪额度已用完，1 号恢复；期间可直接在承运商官网查」，并在 audit 里记 `tracking.quota_exhausted` 便于统计。

**关键：额度用完不阻断发货。** 保存运单号、发发货信、订单转 `fulfilled` 全部照常，只是没有自动轨迹。

### 2c.3 断言清单（桩测试 11 例）

用桩替换 `https.request`，直接喂 17TRACK 的响应原文 —— 因为「额度用完」在免费账户下只能等下月初才可能复现，「单号已注册」要真有一个注册过的单号，这两类不打桩就测不了。

| # | 用例 | 结果 |
| --- | --- | --- |
| 1 | 注册成功返回 `ok` | ✅ |
| 2 | 带回承运商 | ✅ |
| 3 | **注册请求体不带 `lang`** | ✅ |
| 4 | 请求体带 `tag`（webhook 靠它找订单） | ✅ |
| 5 | 额度用完 → `quotaExhausted: true` | ✅ |
| 6 | 额度用完 ≠ `ok` | ✅ |
| 7 | 额度用完保留原错误码 | ✅ |
| 8 | 撞当日上限也归到额度类 | ✅ |
| 9 | 已注册过（`-18019901`）当成功处理 | ✅ |
| 10 | 单号本身无效（`-18019903`）不误判成额度问题 | ✅ |
| 11 | 配额读数透传 | ✅ |

第 9 条为什么要当成功：同一单号被两单复用（补发、退换重寄），或上次请求其实成功但响应丢了。当失败处理会把订单盖上「自动追踪不可用」，之后怎么点刷新都修不回来。

### 2c.4 没验到的

- **真实额度耗尽**：没有真实账号跑到 0，靠桩模拟。
- **`lang` 省略后额度是否真的只扣 1**：要等真实账号跑一个月对账单才知。官方规则这么写，代码照规则改。
- **后台额度面板在「已配置」状态下的读数**：当前环境未配 17TRACK Key，面板显示的是「未配置」文案；有 Key 后的读数渲染没在真机上看过。

## 3 清库工具：口径比功能更重要

### 3.1 为什么要有它

每跑一次回归，后台就多几张假订单、几个假客户，看板 GMV 跟着失真。跑到后来**没人敢信后台数字**——这比没有报表更糟。而"上线前清库"这件事如果靠人一条条勾，一定会漏，而且漏的是最不该漏的那种（比如假评价，FTC 明文禁止）。

### 3.2 三条保守原则

1. **默认不删**。不带 `--apply` 只预演，把要删的每一条逐行打出来。
2. **删前备份**。备份文件名带时间戳，放在同目录，随时可以整份拷回去。
3. **认不出的不删**。按「域名 + 局部前缀」识别测试邮箱；商品、单号序列、审计日志、员工账号**一律不动**——尤其商品：**新品也是商品，不能因为"基线里没有"就当残留删掉**。

### 3.3 实跑结果（2026-11-16）

| 对象 | 删 | 留 | 说明 |
| --- | --- | --- | --- |
| 订单 | 11 | 90 | 约占 GMV $991 |
| 客户 | 8 | 56 | 测试单对应的幽灵客户 |
| 定制需求单 | 4 | 0 | 全部为测试提交 |
| 过期报价 | 35 | 0 | 15 分钟有效期，早该失效 |
| 幂等键 | 6 | 0 | 指向已删订单 |
| 库存流水 | 22 | 212 | 指向已删订单 |
| 过期会话 | 8 | 10 | 保留未过期的，避免把正在用的人踢下线 |
| 商品 | **0** | **38** | 一款不少（含基线里没有的 2 款新品） |

清完立即复检：**所有计数归零**，说明工具是幂等的。

### 3.4 顺带修好的基线

`db.seed.json` 从 36 款商品刷新到 38 款，并把这轮清理后的状态作为新基线。此后 `POST /__test/reset` 回到的是**干净且完整**的状态，而不是"干净但少了两个商品"。

## 4 六处「假红」：测试自己坏了，不是代码坏了

第一次跑回归红了 6 项。逐条查下来，**没有一项是代码回归**：

| 症状 | 真因 | 处置 |
| --- | --- | --- |
| 商品总数、后台列表数不对 | 写死 36，实际 38 | 从 `/health` 派生 |
| 小计 / 合计断言失败 | 写死 82 + 76 = 158，调价后是 88 + 76 | 从商品接口现取单价，断言算式而非数字 |
| 伪造价格被忽略（应为 82） | 同上 | 改用现取单价 |
| 10% 折扣 = 15.8 | 同上 | 由小计派生 |
| 幂等重放 / 状态流转 / 退款 一连串失败 | 幂等键写死 `test-key-1`，第二遍命中了上一轮**已退款**的订单 | 改为 `apitest-<时间戳>` |
| UI 验收登录失败 | 脚本默认密码还是上一轮临时改的 `Temp1234!` | 改回基线密码，保留环境变量覆盖 |

**这条教训值得单独记**：断言绑数据，红了也分不清是数据变了还是代码坏了。分不清的告警，看三次之后就会被无视——那时候这份测试就等于不存在了。

## 6 结论与建议

1. **销售税可以交付了**，但要记住它的前提：**没配税率的州就是没注册，系统一分不收**。这个"少收"是刻意的，不是漏的。
2. **上线前再跑一次 `node tools/clean-test-data.js --apply`**，然后核对后台 GMV 是否回到真实水平。
3. **真实收税要等你在州里注册**。在那之前，后台税率保持空白是**正确状态**，不要为了"看起来完整"随手填几个州——收了不交比不收严重得多。
