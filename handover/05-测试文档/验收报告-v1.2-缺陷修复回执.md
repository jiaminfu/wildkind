### 3.4 修复过程中自己引入又修掉的回归

诚实记录两条，因为它们都说明了「改完必须重跑」：

1. **CSP 把图片预览拦死**：新加的 `img-src` 漏了 `blob:`，后台上传图片的本地预览全部失败，提示「That file is not a readable image」。加上 `blob:` 后恢复。
2. **`<picture>` 里只改 `img.src` 不换图**：详情页缩略图点击后画面纹丝不动——浏览器优先取 `<source>` 的 WebP，改 `img.src` 无效。修法是同步替换 `source[srcset]`，并为此新增 U11 的换图断言。

另外三处是**测试链路自身**的缺陷，不修就无法证明「可重复回归」，一并记下：

3. **评价配额按 IP 计会误伤真人**：原来 `review:` 是 8 次/小时/IP。同一个出口 IP 后面可能是咖啡馆、写字楼，也可能是一台跑回归的机器——所有人和所有轮次共用一个桶。实测一小时跑三轮验收就把额度打满，之后真实顾客提交也拿 429。改成按**邮箱** 6 次/24 小时（防哄抬），IP 那层只留 `review-raw` 40 次/小时负责防轰。
4. **限流把回归自己挡住了**：登录 10 次/5 分钟、下单 20 单/分钟、报价 60 次/分钟，这些阈值对人合理，但一套 207 条的用例连跑两遍必然撞上，测出来的就是自己的噪音。补了一个 `POST /api/v1/__test/rate-limits`，**只清计数桶、不动数据**（区别于会打回基线的 `__test/reset`），且同样只在 `ALLOW_TEST_RESET=1` 时注册，生产环境这条路由根本不存在。
5. **断言依赖了分页顺序**：「上架后出现在前台列表」原本查 `?limit=100` 的第一页。库里商品涨到 48 个、服务端对 limit 有上限之后，新建商品不一定落在第一页——那测的是分页，不是「上架是否生效」。改成 `?handles=<handle>` 精确过滤。

### 3.5 可重复性的证明

这三条修完之后，**同一台机器上背靠背连跑两轮**，结果一致：

```
第一轮  合计 207 条：通过 207，失败 0，功能缺口 0
第二轮  合计 207 条：通过 207，失败 0，功能缺口 0
```

在此之前，第二轮必然崩在登录或下单的 429 上——一个「只能跑一次」的验收是没法当回归基线用的。
