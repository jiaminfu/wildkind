## 1 一句话结论

这一版的能力边界是清楚的：**主交易链路、后台 13 个模块、商品录入全链路在真实生产环境上跑通了，接口层 94 条、界面层 42 条无人为干预全部通过。** 剩下的问题不在"能不能卖货"，而在「对外凭证没到位」（真实支付/邮件/物流）、「基础设施没加固」（HTTPS、监控、备份验证）和「接口返回结构有一处历史不一致」这三件事上。

---

## 2 测试策略：为什么在生产环境测、又怎么保证不弄脏数据

上一版（v1.3）的 394 条用例里，只有 `e2e-product` 24 条真正打过线上，其余全靠 `POST /__test/reset` 把本地数据打回基线。这套办法在线上用不了——**线上没有这个端点（实测 404），也不该有**。

所以本轮换了策略：**只读为主 + 可回滚写 + 破坏性用例一律不执行**。

| 操作类型 | 是否执行 | 约束 |
| --- | --- | --- |
| 读接口、读页面 | 全部执行 | 无限制 |
| 建商品 / 传图 / 改价 / 上下架 / 复制 / CSV 导入 | 执行 | **全部落在标题带 `QA-<随机>`、句柄带 `qa-<随机>-` 前缀的测试商品上**，`finally` 里按 id 精确删除，并按前缀兜底扫一遍 |
| 报价（`/checkout/quote`） | 执行 | 服务端会写一条报价记录（限最近 200 条），属可接受的临时数据 |
| 真实下单、退款、删真实商品、改站点设置、清数据 | **不执行** | 会污染订单/库存/流水或破坏商品；这类用例只在本地库跑 |
| 限流压测 | **不执行** | 登录阈值为 10 次/5 分钟，压测会把自己锁在门外，且对生产无意义 |

**数据影响复核**：测试前后 `health` 返回的商品数与订单数均为 **36 / 90**，无漂移；测试商品 3 个已全部删除。

> 这套策略的代价是覆盖不全——"删除有订单的商品"这类用例在生产上不能验。已在第 8 节逐条记为未覆盖项，不用"通过"来含糊它。

前台主链路（18 条）覆盖：首页渲染 → Cookie 同意 → 进详情 → 加购 → 抽屉打开 → 结账入口 → 结算页表单齐全（邮箱 + 7 项地址字段）→ 服务端报价显示 → 刷新后购物袋保持 → 390px 无横向溢出。

**下单按钮刻意没点**——点了会真的建单、扣库存、写流水。

### 4.4 本轮新增缺陷

| 编号 | 级别 | 标题 | 根因 | 处置 |
| --- | --- | --- | --- | --- |
| D-033 | S4 | 接口文档把 `GET /admin/products/:id` 的返回写成 `{data:{product}}`，实际是 `{data:{商品对象}}` | 该端点是后补的，写 OpenAPI 时按 PATCH 的 envelope 照抄，未对照实现 | **已修**：文档改为如实的 `AdminProductDirect`，并在该端点描述里显式提示与 POST/PATCH 的差异 |
| D-034 | S4 | 同一资源不同方法返回结构不一致：`GET` 把对象直接放 `data` 下，`POST`/`PATCH` 包一层 `data.product` | 早期只有 PATCH，后来加 GET 时图省事直接 `ok(res, {...})`；前端也就按 `res.data` 写了，两边自洽，问题被掩盖 | **未修**（改实现要动前端一处 + 重新发布）。文档已标注差异，列入第 9 节前置条件 |

> D-034 是本轮最有价值的发现：**它不是"跑不通"，而是"跑得通但姿势不对"**。这类缺陷自动化测试很难抓——前端按什么写、后端就返什么，永远自洽。只有把文档、实现、前端三方对起来看才会露出来。

## 6 本轮执行中出现的两类"噪声"，以及为什么判定它们不是缺陷

测试报告的可信度取决于**是否把测试自身的问题误报成产品问题**。本轮出现过两条，逐条说明：

| 现象 | 初判 | 复核方法 | 结论 |
| --- | --- | --- | --- |
| 首轮 77 条里 9 条失败 | 疑似 9 个缺陷 | 逐条查实现源码 + 手工 curl 对照 | **9 条全是用例断言写错**：把 `category` 当 `cat`、把分页 `meta` 期望在 `/products` 上（实际在 `/products/search`）、`qty` 边界返回 422 而我期望 400、拿前台接口取 `version`（前台不返回该字段）。修正断言后重跑 0 失败 |
| 一次 5 轮探测里 2 轮全站返回 000 | 疑似服务不可用 | 与同机 80 端口服务做对照，并分别做低频（20 次，间隔 1.5s）与高频（30 次连发）采样 | 低频 20/20、高频 30/30。判定为**跨境链路的瞬时握手失败**，非应用缺陷；但"没有监控告警、出问题只能靠人肉发现"是真的运营风险，记入 8.4 |

> 这两条如果不在报告里写出来，读者会误以为"一次就全绿"。实际是**改了两轮脚本才全绿**——这本身说明测试资产也需要被测试。

## 7 上线判定

| 判断项 | 结论 | 依据 |
| --- | --- | --- |
| 能不能对外访问 | **能** | `http://194.36.85.20:8080/` 前台、`/#/admin` 后台，实测 200 |
| 能不能真实收钱 | **暂时不能** | 支付为模拟态，缺 Stripe `sk_live` 与 webhook 域名 |
| 能不能真实发货 | **能**（人工填运单号） | 订单状态机与运单号写入已验证；物流轨迹不能自动回传 |
| 能不能录入 100 款 SKU | **能** | 商品编辑器 + CSV 批量导入，线上真浏览器走通 |
| 能不能承受日均 100 单 | **能**（有前提） | 单进程 JSON + 内存镜像，读接口 p95 594 ms；批量导入 100 行时会有短暂阻塞，见 8.2 |
| 能不能多实例扩容 | **不能** | 数据层是单文件 JSON，必须单进程；限流也是单机内存计数 |
| 数据是否干净 | **是** | 测试前后 36 商品 / 90 订单一致，测试商品已清理 |
| 是否可判定"这一版通过" | **通过** | 136 条用例 0 失败；无新增 S1/S2 |

## 8 遗留风险与未覆盖

### 8.1 外部凭证阻塞（4 项，优先级最高）

| 项 | 卡在哪 | 影响 |
| --- | --- | --- |
| 真实收款 | Stripe `sk_live` + webhook 域名 | 上线即无法成交；且 webhook 签名校验、退款回调、争议处理三段代码从未被真实事件验证过 |
| 真实发信 | Resend Key + SPF/DKIM | 订单确认、发货通知、退款通知全部发不出；进件率无从谈起 |
| 物流轨迹 | 承运商 API 或 3PL 对接方式 | 用户看不到轨迹，客服压力全落在人身上 |
| 商品实拍图 | 素材 | 现用演示图，转化率数据全部无效 |

### 8.2 架构与性能（3 项）

| 项 | 影响 | 触发条件 |
| --- | --- | --- |
| 单文件 JSON + 内存镜像 | 无法水平扩容；进程重启期间写入丢失 | 日均订单明显超过 100 单，或需要零停机发布 |
| 限流为单机内存计数 | 多实例部署时形同虚设 | 上多实例前必须换 Redis 或网关限流 |
| 商品图未走对象存储 | 图片与数据同卷，扩容受限；无 CDN，跨境首屏慢 | 商品数上 200 或开始投广告 |

### 8.3 已验证范围之外（4 项）

| 项 | 为什么没测 | 建议 |
| --- | --- | --- |
| 目标市场真实网络下的首屏 | 只能从本机跨境访问，测得的是"最坏情况" | 上线前用美国节点（朋友/代理/云主机）跑一遍首页与结算页 |
| Safari / Firefox | 只有 Chromium 环境 | 上线前真机冒烟（iPhone Safari 必测） |
| 并发下单 | 生产环境不能压测 | 迁 PostgreSQL 或至少加写队列后再做 |
| 超大订单（>30 行）与超长商品名 | 演示数据没有极端值 | 真实 SKU 数据到位后补 |

### 8.4 基础设施与运营（5 项，本轮新增观察）

| 编号 | 项 | 现状 | 风险 |
| --- | --- | --- | --- |
| R-01 | 无 HTTPS | 8080 明文 HTTP，后台口令与令牌在明网传输 | **最高**。同一网络下的任何人可截获管理员令牌 |
| R-02 | 无监控告警 | 本轮曾出现一次约 10 秒的全站不可达，没有告警，只能靠人肉发现 | 高。出故障时无人知晓，靠客户投诉 |
| R-03 | 备份未验证恢复 | `backup-docker.sh` 会打包 `db.json` + `uploads/`，但从未做过"从备份恢复"演练 | 高。备份不能用等于没有备份 |
| R-04 | `CORS_ORIGIN` 为 `*` | 任意站点可调用公开接口（报价、查单） | 低。认证走 Bearer 令牌，跨站拿不到；但建议收敛到自有域名 |
| R-05 | 静态资产无 ETag / Last-Modified | `Cache-Control: no-cache` 下每次请求都全量下载 50 KB JS | 低。跨境访问放大首屏耗时 |

### 8.5 本轮未执行、也不要假装覆盖了的用例（3 项）

| 用例 | 不执行的原因 | 现由谁保证 |
| --- | --- | --- |
| 删除有订单引用的商品应返回 409 | 生产上"先试删再看结果"不可接受：若该商品恰好没订单，服务端会如实删掉它 | 本地 `api-test-product.js` TC-PROD-30 |
| 退款要回补库存、释放券、冲减客户消费 | 会改动真实订单与库存 | 本地 `unit-core` + `api-test` 退款用例 |
| 幂等下单（同 `Idempotency-Key` 连点只出 1 单） | 会真的建单 | 本地 `api-test` TC-API-D09 |

## 9 上线建议与前置条件

### 9.1 结论

**可以上线，但上线 ≠ 可以开卖。** 当前状态适合：挂到公网、用真实流量验证选品与页面转化、跑通"浏览到结算页"的漏斗。不适合：接真实收款前的公开投放。

### 9.2 开卖前必须做完（按顺序）

| # | 事项 | 为什么卡在这 |
| --- | --- | --- |
| 1 | **配域名 + HTTPS** | 明文传管理员令牌是不可接受的风险（R-01），且 Stripe 要求 HTTPS 回调 |
| 2 | 接真实 Stripe 并跑通 webhook | 支付是唯一"没验证就等于没做"的环节 |
| 3 | 接 Resend 并验证域 | 没有订单确认邮件的独立站，退款纠纷率会很高 |
| 4 | 做一次"从备份恢复"演练 | 验证 R-03，否则备份是心理安慰 |
| 5 | 加最小监控（存活探测 + 5xx 告警） | 验证 R-02，本轮已出现过一次静默不可达 |
| 6 | 清空演示数据、上传实拍图 | 否则转化数据全是噪声 |
| 7 | 统一 `GET /admin/products/:id` 的返回结构（D-034） | 不影响使用，但会给后续对接埋坑；趁还没第三方接入时改成本最低 |

### 9.3 可以不阻塞上线的

- D-034 的接口结构统一（有文档标注，前端自洽）
- R-04 的 CORS 收敛、R-05 的静态资产加 ETag（都是配置级优化）
- Safari 冒烟、美国节点实测（可在灰度期补）
