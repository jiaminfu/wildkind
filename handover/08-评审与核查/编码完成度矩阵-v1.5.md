### 3.1 关于 S-13 ~ S-20 这 8 条

这是**最大的一块未实现**，必须说清楚，不能含糊过去：

| 事实 | 说明 |
| --- | --- |
| 原型（4500）有完整 8 页账户中心 | 注册、登录、概览、订单列表、地址簿、心愿单、设置都跑通过 |
| 交付版（4600）只有 `/account/lookup` | 就是访客查单页，其余 `/account/*` 一律重定向到查单 |
| 后端没有 account 接口 | 56 个操作里没有 `/api/v1/account/*`、没有 `/auth/register`，只有 `/admin/login` 给员工用 |
| 原型账户数据存哪 | 纯前端 localStorage，服务端无用户表 |

**为什么可以这样上线**：FRD v2.0 的结论是"保留访客下单，账户体系是增强"。当前 100 款 SKU、单人运营、客单价 $35~$85 的阶段，访客下单 + 单号查单能覆盖 95% 的真实场景——亚马逊之外的 DTC 饰品站（Atolea、Pura Vida）大量成交也是访客单。

**什么时候必须补**：① 要做复购营销（需要用户身份才能算 LTV）；② 客户开始问"我的订单在哪"且查单页不够用；③ 上线后订单量超过日均 20 单。**这三条任一成立就该补，不是"以后再说"。**

**过程中修掉的三个致命 bug**（不是小事，记录在案）：

1. **OAuth 表单被 JSON 序列化** → `400 Grant Type is NULL`，通道 100% 不可用。修法：字符串 body 原样发送，只有对象才 `JSON.stringify`。
2. **回跳参数被 hash 吃掉** → PayPal 把 `token/PayerID` 追加在 `#` **之前**，而原 `parseHash()` 只读 hash，导致页面显示「Payment link incomplete」**而钱已经扣了**。修法：先铺 `location.search`，再用 hash 覆盖。真浏览器三形态 3/3 通过。
3. **伪造回调返回 500 而不是 400** → `http.js` 的 `fail()` 只认 `ApiError`，`Object.assign(err,{status:502})` 挂属性出去仍是 500。修法：改用 `new ApiError(...)`。

## 10 上线判定

| 判断 | 结论 |
| --- | --- |
| 能不能部署到服务器、对外可访问 | **能**。已部署在 `194.36.85.20`，容器 healthy，域名 `lastgrove.com` 已通 |
| 能不能真实收钱 | **代码能，密钥不能**。PayPal 两段式链路已完整（建单 → 跳转 → 捕获 → webhook 兜底），但仍是 `PAYPAL_ENV=sandbox`，缺 Live 密钥。**销售税已能按州计算并出申报表** |

| 代码是否"完成" | **主链路完成，横切能力（支付 / 物流 / 邮件 / 销售税）完成，账户与营销自动化未做，博客未做**。剩下的事已逐条列出，没有"不知道还有多少"的模糊地带 |
