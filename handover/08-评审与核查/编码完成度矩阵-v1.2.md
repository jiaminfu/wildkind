## 1 三句话结论

1. **主交易链路 100% 完成**：浏览 → 集合筛选 → 详情 → 加购 → 报价 → 下单 → 后台发货 → 退款回补库存，全部可操作，账目自洽（67/67 SKU 流水对账一致）。

### 3.1 关于 S-13 ~ S-20 这 8 条

这是**最大的一块未实现**，必须说清楚，不能含糊过去：

| 事实 | 说明 |
| --- | --- |
| 原型（4500）有完整 8 页账户中心 | 注册、登录、概览、订单列表、地址簿、心愿单、设置都跑通过 |
| 交付版（4600）只有 `/account/lookup` | 就是访客查单页，其余 `/account/*` 一律重定向到查单 |
| 后端没有 account 接口 | 56 个操作里没有 `/api/v1/account/*`、没有 `/auth/register`，只有 `/admin/login` 给员工用 |
| 原型账户数据存哪 | 纯前端 localStorage，服务端无用户表 |

**为什么可以这样上线**：FRD v2.0 的结论是"保留访客下单，账户体系是增强"。当前 100 款 SKU、单人运营、客单价 $35~$85 的阶段，访客下单 + 单号查单能覆盖 95% 的真实场景——亚马逊之外的 DTC 饰品站（Atolea、Pura Vida）大量成交也是访客单。

**什么时候必须补**：① 要做复购营销（需要用户身份才能算 LTV）；② 客户开始问"我的订单在哪"且查单页不够用；③ 上线后订单量超过日均 20 单。**这三条任一成立就该补，不是"以后再说"。**

**这意味着**：

- ✅ 交付版（4600）的**接口、后台操作、渲染与适配**都有自动化守着；
- ✅ 交付版（4600）的**后台商品录入链路**已有真浏览器端到端自动化（`e2e-product`，本地与线上各跑一轮全绿）；

**已经补了**：`tools/e2e-storefront.js` 18 条直接打交付版，不迁原型那 17 条——原型的用例绑的是账户中心与原型 DOM，迁过来要重写大半，不如按交付版的实际路径重写一套。下单按钮刻意不点（会真的建单扣库存），下单语义由接口层守着。

## 9 上线判定

| 判断 | 结论 |
| --- | --- |
| 能不能部署到服务器、对外可访问 | **能**。有部署手册 + 一键脚本，无域名也能上（IP + 端口） |
| 能不能真实收钱 | **暂时不能**。支付是模拟态，缺 Stripe 密钥 |
| 能不能真实发货 | **能**（人工填运单号），物流轨迹不能自动回传 |
| 能不能承受日均 100 单 | **能**（单进程 JSON 足够，内存常驻约 80MB） |
| 能不能多实例 / 水平扩容 | **不能**。数据层是单文件 JSON + 内存镜像，必须单进程（见 SDD 8.1） |
| 代码是否"完成" | **主链路完成，功能面 88%**。剩下 13 项已逐条列出，没有"不知道还有多少"的模糊地带 |
