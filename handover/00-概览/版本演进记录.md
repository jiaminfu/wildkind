## 一、为什么要留这份记录

文档不是一次写对的。这套材料从 v1.0 走到今天，中间有 **5 次判断被自己推翻**（见第五节），如果不留痕，接手的人会看到一份"天生就这样"的文档，然后重复踩同样的坑。

更重要的是：**每一版编号对应一个当时的确信程度**。FRD v2.5 是目前唯一一版经过「逐条对账 + 298 条测试验证」的，之前任何版本都不能直接拿去开发。

## 二之八、券状态区分 · 测试空洞回填 · 品牌数据统一（2026-11-16 午）

用户三句话，看起来是三件事：

> 「券状态过期就是过期，发完就是发完，状态一定要区分好，这个不是技术问题就是产品问题也是属于一个bug，需要记录」
> 「新品牌已经更新，所以数据包括文档都要用最新的」
> 「直接做第 1、2 条，其它条也可以做」

做完发现是**同一个病**：同一个事实在三处各存一份，谁也不知道哪份是真的。

### 1 券状态：产品口径先于代码

`SUMMER20` 这张券 `used=640 / limit=640`，`endsAt=2026-08-31`，存库的 `status` 写的是 `expired`。
后台列表照着 `status` 渲染，于是：**一张早就发满的券，徽章只说过期，KPI 却把它算成「Live now」**。

根因不是判断顺序写错，是**根本没有判断**——把人工写的快照当成了事实。运营不会因为一张券卖完了就回去把 `status` 改成 `exhausted`，也没人会在到期那天手动改 `expired`。

改法是让事实只有一个来源：

```
couponState(c, now) → { state, reasons[] }
优先级 expired > disabled > exhausted > scheduled > active
```

`reasons` 是关键，它不是给客户看的，是给运营对账用的：一张券可以**既过期又发满**，主状态只能显示一个，另一个必须以 `also exhausted` 的形式留在列表上。否则运营看到 `Expired` 会以为「早点发就好了」，其实名额也早就没了。

`expired` 排第一是有意的：客户看到 `expired` 知道自己来晚了，看到 `not active` 会以为自己拿错了码——而实际上两种原因可能同时成立。

### 2 假绿灯：测试照抄了实现

`pricing.js` 里库存不足时，顶层错误码一律是 `OUT_OF_STOCK`，真正的 `INSUFFICIENT_STOCK` 塞在 `details[0]`。
`unit-core.js` 的断言写的是 `r.code === 'OUT_OF_STOCK'`——**和错误实现完全一致，所以永远是绿的**。

这类绿灯最危险，因为它不只没抓到问题，还替问题背书。修的时候不能只改代码，必须把测试改成分开构造：

- 库存 3 件要 5 件 → `INSUFFICIENT_STOCK`（改数量还能买）
- 库存 0 件要 1 件 → `OUT_OF_STOCK`（只能等补货）

两件事对客户是两件事，对系统也必须是两个码。

### 3 品牌：代码改了，数据没跟上

SKU 前缀早在改名时批量换成 `LG-`，**订单号漏了**：代码还在生成 `#TG`，库里 90 单全是 `#TG10xx`。

这不是改个字符串的事，牵涉三层：

| 层 | 改了什么 | 漏了会怎样 |
|---|---|---|
| 生成逻辑 | `checkout.js` / `core.js` / `seed.js` | 新单还是旧前缀，越积越多 |
| 存量数据 | 90 个 `orders[].number` + 141 处零散引用 | 客服按单号查、客户报单号，都对不上品牌 |
| 测试基线 | `db.seed.json` | 复位一次又全变回 `#TG`，白改 |

第三层最容易漏。改完代码和数据，跑一次复位又回到起点——**基线也是数据，它不是配置**。

顺带清掉一个更隐蔽的：基线里躺着一个 `AU Test Necklace`（UI 验收脚本建的），已经存在至少一天。基线是所有回归的起点，混进一个测试商品意味着此后每一次「复位再跑」都在假数据上跑。这条和测试报告 v1.6 记的那次（基线落后 2 款新品）是同一个坑的两个方向——**刷基线前必须先核对商品数**。

### 4 功能缺口：能用，但每一步都在多干活

四条都是「接口支持、界面不做」：

| 缺口 | 原来 | 现在 |
|---|---|---|
| 侧栏门控 | 16 项里只有 2 项挂权限位，其余点了吃 403 | 全部挂上最小可读权限位，没权限就不渲染 |
| 库存补货 | 只有写死的 `+20` | 每行一个数量框，允许负数核减 |
| 评价拒绝 | 点一下直接拒，理由无处写 | 弹框填理由，存库并回显在卡片上 |
| `pages.journal` | 博客没迁走时的遗留键，能改但改了没用 | 删除，老库加载时自动清理 |

「能改但改了没用」比「没有这个入口」更糟——运营会以为自己改好了。

### 5 这一轮的教训

1. **状态字段如果不是派生出来的，它迟早会撒谎**。人的记忆跟不上时间与用量。
2. **测试断言要和实现分开写**。照抄实现写出来的断言，等价于没有断言。
3. **改名是三层动作**：生成逻辑、存量数据、测试基线。少一层就等于没改。
4. **界面把能力关掉了，也是缺陷**。接口支持任意数量，按钮只给 `+20`，用户只会觉得系统笨。

## 二之九、历史数据删除 · 券 `status` 字段溯源（2026-11-16 午后）

上一轮留下两条待拍板，用户的回复只有两句：

> 「1，历史数据删除　2，券为什么没有status这个字段？这个字段之前表示什么含义？」

### 1 决策 D1：不给 `#TG` 写兼容，历史数据直接删

我上一轮的建议是「加一层 `#TG` → `#LG` 自动映射，约 20 分钟」。用户选了更彻底的那条。**这次我接受被推翻，理由是这套库从没上线过**——90 单全是 `data.js` 生成的演示数据，为 0 张真实订单写一层永久兼容代码，等于把一次性成本换成永久维护成本。

执行结果：

| 项 | 数量 |
|---|---|
| 删除历史快照 | 6 个（`bak-before-clean` ×2、`bak-before-lg` ×1、`pre-test`、`bak-tideglass` ×2） |
| 原型层旧品牌 | **42 处** `TIDEGLASS` / `tideglass` |
| 种子源券码 | `TIDEGLASS10` → `LASTGROVE10`（**源不改，重新 seed 一次就变回去**） |
| 重新 seed 后 | 商品 36 / 变体 67 / 订单 90 / 客户 56 / 券 4 / 评价 59 / 库存流水 200 |
| 全库复核 | `tideglass` 0、`#TG` 0、`TG-` 0 |

**这次值得记的一个教训**：上一轮我以为「文档和 app 代码改完就算改完」，实际上 `prototype/` 目录才是客户会看到的界面——后台登录页的字标、前台品牌故事段、`localStorage` 键名、演示口令，全都还是 `TIDEGLASS`。**改名要扫的不是「文档 + 代码」，是「用户能看见的一切」**。

还有一处更隐蔽的：`prototype/assets/js/data.js` 里券码是 `TIDEGLASS10`，而运行库早就是 `LASTGROVE10`——说明上一次改名只改了库、没改源。这种「库对、源错」最危险，因为**表现完全正常，直到下一次 seed**。

### 2 券的 `status` 字段：不是「没有」，是「它原本就不表示状态」

用户的反问点破了一件事：我上一轮把字段说成「不再生效」，容易被读成「删掉了」。实际上它一直在写、一直在读，只是**语义被降级了**。

溯源结论：

| 维度 | 事实 |
|---|---|
| 取值 | `active` / `scheduled` / `expired` / `disabled` |
| 写入点 | 全项目**只有一处**：`POST /admin/coupons` 的 `status: b.status \|\| 'active'` |
| 修改方式 | **没有**。券只有 GET / POST / DELETE，没有 PATCH。建完即冻结 |
| 真实含义 | 「建券那一刻运营希望它怎么样」，不是「它现在怎么样」 |
| 设计意图 | 让运营能手动作废、临时停用、预排档期 |

**问题出在四个值里有两个不是状态、是时间的函数**：`expired` 等价于 `endsAt < now`，`scheduled` 等价于 `startsAt > now`。人工再标一遍，就多了一个会跟时间打架的字段——改 `endsAt` 时忘了改 `status`，两个字段互相打脸。四个值里只有 `disabled` 是真正的人工意图（「与时间无关，我现在就想关掉」）。

所以这一轮的修法（`couponState()` 派生 + 优先级合并）是对的，但只解决了「展示」，没解决「字段语义」。留给下一轮的建议已写进缺陷台账 §4 Q2：**缩窄为 `active` / `disabled` 两值，或直接改名 `enabled: true/false`**。

### 3 这一轮的教训

1. **「历史数据」要分清是资产还是负债**。没上线的演示数据是负债，删了比重构便宜。
2. **改名要扫「用户能看见的一切」**，不只是文档与后端代码。原型目录同样会被人看到。
3. **「字段还在」和「字段有用」是两件事**。前者看 `grep`，后者看「谁在什么条件下读它」。

## 二之七、文档三件套：员工教程 / 第三方同步 / 技术详解（2026-11-16 深夜）

用户的原话分三条：「出个使用教程，方便员工培训及时使用，要把各模块讲清楚，要有功能流程图」「将用到的第三方技术比如支付，物流跟踪，邮件等同步到对应的技术文档中」「专门出个技术文档，将前后端用到的技术讲解下，各个模块都用到什么类，其中用到什么技术，作用是什么，数据存储等等全方位的，越详细越好」。

三条要求看起来是三件事，其实指向同一个问题：**知识都在代码里，没落在能被找到的地方。** 于是分工是——

| 谁需要 | 给什么 | 为什么不能合成一份 |
| --- | --- | --- |
| 员工（不懂技术） | 《员工使用教程》 | 他们需要的是"这一步点哪里、点错会怎样、哪十条是红线"，不是分层架构 |
| 运维（要开通三方） | SDD §21 + 部署手册 §6.4.1 | 需要的是"缺哪个变量就瘸了哪块、回调地址差一个字符会怎样" |
| 接手工程师 | 《前后端技术详解》 | 需要的是"这个功能在哪个文件、这张表有几个字段、这个算法为什么这么算" |

**合成一份的后果**：给员工看架构图，他们翻两页就放弃；给工程师看"点击 +20 补货"，等于没写。

### 1 员工教程：先讲清"屏幕上看到的英文"和"实际发生的事"

界面是英文的，员工是中文的，这是第一道坎。所以全文规则是：**英文照抄屏幕原文，中文跟在后边解释**。

做了几个判断：

- **流程图 9 张，全部用标准 Mermaid**，不用图片——图片改一次要重画，Mermaid 改一行就行。
- **每个模块都写"你能做什么 / 你不能做什么"**。比如商品卖过之后不能删，系统会拒绝并提示 `Unlist it instead` ——这个限制不写出来，员工会以为是自己操作错了。
- **故意把界面上的不一致讲出来**：订单状态徽章显示 `Preparing`，但旁边按钮写着 `Fulfilling`，是同一件事。不提前说，新人第一次点会犹豫。
- **把已知缺口如实写进教程**：库存补货按钮是写死的 `+20`，没有数量输入框；评价审核没有"拒绝理由"栏。员工不知道这是系统局限，就会一次次以为是自己的问题。

### 2 第三方：从"设计为什么这样"到"出事先看哪里"

SDD v2.6 已经把支付/物流/邮件的设计写得很细，但那是**当初为什么这么设计**。运维半夜报警时要的是另一类信息——**这个报错是哪家的问题、先看哪个变量、降级之后客户会看到什么**。两者混在一起写，真出事的时候两样都翻不到。

于是新增 §21，五块：

| 节 | 回答什么 |
| --- | --- |
| §21.1 全景 | 五家外部依赖各自干嘛、出问题客户看到什么 |
| §21.2 逐家要点 | 超时多少、重试几次、错误码怎么映射、自查顺序 |
| §21.4 凭证矩阵 | **哪个功能缺哪个变量就瘸了哪块** |
| §21.5 30 秒自检 | 启动日志四行 + 四个只读端点 |
| §21.8 准入清单 | 以后接新三方前必须回答的七个问题 |

顺手修了 SDD 两处与实现矛盾的地方（这也是"同步"的一部分）：

- **§17.1 原文写"当前生产配置为 paypal"**，而 API 文档 §8 写着"支付为模拟模式"。真实情况是：四通道代码都在，**交付版默认 `mock`**。这种矛盾比没写更糟——两个人各看一份，会得出相反结论。
- **§15.3 写着四个定时任务**，实际只交付一个（图片孤儿清理）。不标出来，运维会花半天找一段不存在的代码。

### 3 技术详解：把 17,178 行代码摊成一张地图

这份文档的目标很具体：**让一个陌生工程师三天内能独立改功能**。所以它不按知识体系排，按"你会遇到的问题"排。

几个刻意的写法：

- **目录地图给行数和"你什么时候会打开它"**，不是简单罗列文件名。`admin.js` 1,902 行挤了 49 个操作，所以给的是**分区起始行号 + 两条 grep 命令**，因为行号一定会漂移。
- **"请求的一生"用一张时序图把十步摊开**，每步标出在哪一层、哪个文件。定位问题时这是最有用的那张图。
- **关键算法给的是"输入 / 输出 / 边界"**，不是伪代码。比如退款分摊，重点是**为什么用累计目标法**（同一行分三次退，每次算增量会攒出四舍五入偏差），而不是那个 `splitByWeight` 怎么写。
- **12 个陷阱按踩到的概率排**。前三个是"忘记服务端算钱""直接改库存数字""新增字段没加进 `normalize()`"——这三个每个都能造成线上事故，而且本地都测不出来。

顺带把部署手册升到 v1.3：全文 150 处旧品牌 `tideglass` 统一（照抄会建错目录、装错服务名），并补了第三方变量与自检两节。

### 4 这一轮的教训

**文档的第一读者不是"未来的自己"，是"现在的别人"。** 之前写 SDD 时按设计脉络组织，写得很完整；但对一个刚接手的人来说，"完整"不等于"能找到"。这一轮的判断标准换成了一句话：**出问题时，他能不能只翻一节就定位**。

## 二之五、销售税闭环与测试残留清理（2026-11-16）

用户的原话是：「历史遗留问题哪些需要我确认解决的？给我方案我去解决，剩下的全部都去解决。」这句话把 §13 的 16 项劈成了两半，这一轮只做「剩下的」里最扎人的两件。

### 1. 销售税：唯一一项「不解决就不能开门收钱」的代码缺口

**为什么它排第一**：P-02 PayPal、P-03 邮件是等凭证，代码早就写好了；只有 P-01 是代码真的没做。而且它错起来最贵——多收一笔税要退款、要修正申报，退比收难十倍。所以整套实现的第一原则是**宁可少收，不可错收**：没在后台配税率的州，一分不收。

**做了什么**

| 层 | 改动 |
| --- | --- |
| 州名归一化 | 新增 `lib/us-states.js`，`California` / `CA` / `calif` / `Brooklyn, New York` 都归到 `CA`。**不能取前两位**——`New York` 取两位是 `NE`（Nebraska），这种错会安静地收错州 |
| 定价 | `pricing.quote()` 加 `state` 入参，多算一步税；运费是否计入税基由 `shipTaxable` 决定 |
| 下单 | **不信报价里的税额**，按订单收货地址的州重算。不一致抛 `PRICE_CHANGED` 并回传新旧金额 |
| 后台 | `Settings → Sales tax` 一行一州填写（填 `7.25` 自动存 `0.0725`）；新增申报汇总页与 CSV 导出 |
| 前台 | 结算摘要多一行 Tax；改州时只重画三行 DOM，不重渲染（重渲染会清空刚填的地址） |
| 邮件 | 确认信补 Tax 行（HTML + 纯文本两版）。此前 Subtotal 152 → Total 164.16 中间有 12.16 没解释 |

**验证**：`api-test.js` 新增 9e 节 8 例，专盯三件事——只对注册州收、州名归一、报价州与地址州不一致必拒。另有 `tax-ui-check.js` 15 例真浏览器断言（含「按钮上的金额必须等于摘要 Total」，这条是截图比对时发现过的真实缺陷）。

### 2. 清库：把「测试跑一次脏一次」从根上治了

原来的处境是：每跑一次回归，后台就多几张假订单、几个假客户，看板上的 GMV 跟着失真。跑到后来**没人敢信后台数字**——这比没有报表更糟。

`tools/clean-test-data.js` 的口径是「宁可漏删，不可错删」：

- **默认只预演**，`--apply` 才动手，动手前自动备份，`--seed` 顺带把清理后的状态存成基线快照
- 按「域名 + 局部前缀」识别测试邮箱（`az.*@example.com` 这种随机后缀追不住）
- 明确不动：**商品**（新品也是商品，不能因为基线里没有就删）、**单号序列**（回退会让新单撞历史单号）、**审计日志**（删审计等于销毁证据）
- 实测清掉 11 张假订单（约占 GMV $991）、8 个假客户、4 条假定制单、35 张过期报价，38 款商品一款不少

顺手修掉一处咬了很久的问题：`db.seed.json` 基线是 11-13 的快照，比线上少了 2 款新品，一复位就把新品抹了。现在清库和刷基线是同一条命令。

### 2.5 部分退款：多件订单退一件，钱退了一整单

后台原来只有一个 `Refund` 按钮，退整单。多件订单退一件，系统把整单的钱退回去——**每发生一次就亏一次**。

金额口径写死在服务端：商品 = 行价 − 该行分摊的折扣；税 = 该行分摊的税额（退了货不退税收，等于替州里多吃一笔）；运费只在退最后一件付费商品时退回。分摊用「累计目标法」（按累计数量算"一共该退多少"再减去已退），同一行分三次退也不会攒出四舍五入的偏差。

界面是每行一个小输入框 + `Refund selected`，`Refund whole order` 保留。浏览器断言里有一条专门盯「可退上限要随退款递减」——上限不刷新，页面还能再点一次退 2 件，服务端虽会拦，但人会以为"按钮能点就是能退"。

第一版红了一条：判断"是否退完"把 **0 元赠品行**也算了进去，`refundedQty` 永远为 0，于是货全退光了订单还挂在 `paid`。修法是赠品排除出完成判定，但整单完成时把赠品库存一并补齐（下单时赠品是扣了库存的）。

### 2.6 五条决策之后：需要你做的事从 7 项降到 2 项

用户回了五条，每一条都改变了阻塞结构：

| 决策 | 原本的判断 | 落地改动 |
| --- | --- | --- |
| PayPal 先沙盒，上线才换真实 | 记为「卡上线」 | 沙盒链路确认可完整验证（建单→跳转→捕获→webhook→退款）。「换 Live」重新定义为**上线动作的一部分**，不是上线前的独立门槛 |
| 面单由海外仓代打 | 记为「待确认，可能要接 EasyPost」 | **P-04 关闭**。不接物流 API，省 1.5 天 + 一份月费 + 一个故障点。现有「填单号 → 订阅 → 发信」就是最终形态 |
| 17TRACK 先用免费额度 | 记为「要买 ¥299 套餐」 | 查官方计费规则后改了两处代码，见下 |
| 工商暂不变更 | 记为「卡支付通道合规」 | 记下风险窗口（开票 / 对公结算 / 被风控关注时再办），不定时点 |
| Resend 是什么、怎么建 Key | 操作单只写了步骤，没解释「为什么需要它」 | 重写操作单第 1 节：邮局类比 + 六步 + 三个易错点（橙云、先验域名、Sending access） |

**17TRACK 那两处改动是真金白银：**

1. **删掉注册时的 `lang`**。官方计费规则原文：注册时指定翻译语言会为「成功的翻译」额外扣 1 个额度（`registration + translation = 2`）。免费账户每月 100 个额度，带 `lang` 就等于只剩 50 单。我们只发美/加/英，承运商轨迹本来就是英文 —— 这是花钱把英文翻成英文。
2. **额度耗尽单独归因**。`-18019908`（额度用完）/`-18019907`（撞当日上限）原来走通用失败分支，在订单上记成「订阅失败」，运营看到会去催客户重报单号，而真正该做的是等下月 1 号。现在文案说清是额度问题，**且不阻断发货**（保存单号、发信、转 `fulfilled` 全部照常）。

顺手补了后台的额度可见性：设置页新增 `Tracking quota` 面板（剩余/已用/总量 + 进度条，剩余 ≤ 20 变红）。接口本来就存在，前端一直没接 —— 额度会在月中悄悄用完，等发货时发现「怎么没轨迹」就晚了一批单。

验证：新增 `tools/unit-tracking.js` 11 例桩测试（打桩 `https.request`，喂 17TRACK 响应原文）。为什么必须打桩 —— 「额度用完」在免费账户下只能等下月初才可能复现，「单号已注册」要真有一个注册过的单号，这两类不打桩就测不了。设置页 UI 断言从 15 增至 17。

### 2.7 员工账号：先建护栏，再建页面

这个后台**没有「忘记密码」入口**。删掉自己、停用自己、把最后一个 owner 降级——任何一种都是永久失去后台，且没有任何界面能救回来。所以顺序是先定护栏，再写页面。

护栏四条：不能动自己、不能动最后一个 active owner、非 owner 不能造 owner、改自己密码必须验旧密码。前三条在接口层（409/403），界面只是把按钮禁掉并写明原因——**只禁用不解释，人会以为是 bug**。

测出两个真问题，都不是"功能没做"，而是"做了但会悄悄错"：

1. **改角色不改权限**。`role` 改了，库里那份旧 `permissions` 数组仍然生效，于是页面写着 support、一按退款还是能退。根因是读取顺序 `staff.permissions || 预设` —— 有数组就永远优先。修法：角色变了且没显式传权限时，按新角色重置。
2. **新增权限位会把老 owner 静默锁死**。v1.4 加了 `staff:read/write`，而 owner 的 permissions 是当初存的 10 位数组，只读数组就会凭空少两位、打不开员工页且不报错。修法是一处刻意的不对称：**owner 恒为全权限，不读库里那份数组**；其他角色仍以数组为准。

另外两处工程细节：权限每次请求现读库（所以降权即时生效，不用重新登录）；改密码/停用即刻吊销该账号其他会话（改密码的场合通常是怀疑泄漏，留着旧令牌等于没改）。

测试先把自己写崩过一次，值得记：`api-test-staff.js` 第一版把"降级最后一个 owner 应被拒绝"这条断言，跑在了当时恰好有两个 owner 的库上 —— 断言失败，同时把 owner 真的降成了 ops，后续所有接口 403，排查半天才发现是测试改的数据。修法：开跑前复位、跑完再复位，且这条"万一护栏失效就自毁"的断言放在最后、失败即刻复位并中止。

### 3. 测试脚本自身的三处「假红」

跑回归时红了 6 项，逐条查下来**没有一项是代码回归**，全是测试自己绑定了过期数据：

| 症状 | 真因 | 处置 |
| --- | --- | --- |
| 商品总数、后台列表数不对 | 写死 36，实际 38 | 改为从接口派生 |

## 二之三、交付前复核轮（2026-11-16）

**触发点是一句很普通的提问**：「服务器代码和本地是否已经同步？」

答案是没有——而且是三层三个版本：

| 层 | 版本 | 时间 |
|---|---|---|
| 本地 `main` | `82fc81a` | 11-16 |
| GitHub `origin/main` | `b060b2d` | 11-15 |
| 生产 `/opt/tideglass/current` | `100630c` | 11-15 23:21 |

顺着这条线查下去，暴露了三件比"不同步"更要紧的事：

| # | 问题 | 为什么会这样 |
|---|---|---|
| 1 | 生产在跑的 13 个提交（PayPal 两段式扣款、验签修复、17TRACK）**GitHub 上根本没有** | 11-15 当天走了服务器本地的 `incoming` 分支反复 fast-forward 部署，从没 push 过。换机即丢、想回滚都没有副本 |
| 2 | **每日备份连挂两天** | 11-15 品牌改名时容器从 `tideglass` 改成 `lastgrove`，但 cron 仍指向 11-13 写的旧脚本，按旧容器名查找，直接 `not running`。11-15 只留一个 20 字节空 `.tmp`——文件在、内容是空的 |
| 3 | **照部署说明书操作会全线失败** | 说明书 v1.0 全文容器名/卷名/镜像名/账号都是旧品牌，每条 `docker` 命令都会 `No such container` |

**这一轮的教训不是"要记得同步"，而是：改名这类全局重构，必须连带检查所有"按名字找东西"的地方**
——cron 里的容器名、文档里的命令、脚本里的路径、备份目录。功能测试一条都抓不到：
站点是好的、接口是好的、374 条断言全绿，但备份已经沉默地死了两天。

修复：备份 cron 改指 `deploy/backup-docker.sh` 并实跑验证（商品 37 / 订单 98 / 客户 60）；
