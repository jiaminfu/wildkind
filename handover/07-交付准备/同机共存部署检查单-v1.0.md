# 同机共存部署检查单 v1.0

> 场景：一台服务器上**已经跑着** QRIS 收银台（Next.js + Docker + Caddy），
> 现在要把 TIDEGLASS 装上去，且**不能干扰已有项目**。
> 编写日期：2026-11-13　·　对象服务器：`194.36.85.20`
> 配套：`deploy/install.sh`（已支持 `NO_NGINX=1`）、`deploy/docker-compose.yml`（端口已可配置）

---

## 0. 一句话结论

**不要在这台机器上装系统 Nginx。** 它的 80/443 已经被 Docker 容器占着，装 Nginx 只会撞车；
TIDEGLASS 用**独立端口 8080** 对外，其余资源（目录 / 容器 / 卷 / systemd 单元）全部独立，
端口不撞就互不影响。**唯一需要你手动做的**是在云厂商安全组放行 8080。

---

## 1. 这台服务器实测长什么样

以下是对 `http://194.36.85.20` 的实测结果，不是推测：

| 项目 | 实测 | 含义 |
|---|---|---|
| 80 端口 | `200`，响应头含 `Via: 1.1 Caddy`、`X-Powered-By: Next.js` | 有 **Caddy 在反代**一个 Next.js 应用 |
| 站点标题 | `QRIS 收银台 · Bali` | 就是你那套收银台项目 |
| 443 端口 | 有时完全连不上（`000`），有时拿到 `502` | 结合已有项目用的是「只有 IP」的 Caddy 配置（只监听 `:80`），最可能是 **443 上没有站点在监听**。见下方说明 |
| 8080 / 8081 / 8090 | 从我这台机器探测超时 | 可能是云安全组没放行，也可能是中间网络。**以服务器上 `ss -lntp` 为准** |
| 部署方式 | 本地 `qris-cashier/deploy/docker-compose.yml` | **docker compose 三容器**：`app`（内部 3000）+ `sweeper` + `caddy`（发布 80/443） |
| compose 项目名 | `qris-cashier` | 我们的项目名是 `tideglass`，两者互不覆盖 |
| 数据 | 命名卷 `qris-data`、`caddy-data` 等 | 我们的卷叫 `tideglass-data`，不同名 |

> **关于那个 502，别误判。** 我在本机对 `127.0.0.1` 的一个正常服务做同样的探测，也拿到了
> 完全一样的 `502`（`Retry-After: 1` + `text/plain`）——说明探测链路上有代理会自己生成 502。
> 所以「443 返回 502」**不能**作为「服务器 443 有问题」的证据。
> 唯一确定的是：**本次部署一个字节都不碰 443**，它现在是什么状态都不影响我们。

**关键推论**：QRIS 的 80/443 是 **Docker 容器**发布的端口，不是宿主机服务。
宿主机上再装一个系统 Nginx，它会去 bind 80 → 必然 `Address already in use`，
然后 apt 认为启动失败，还可能有人去 `systemctl stop docker` 排障——那才是真正的事故。

## 2. 四条硬红线（碰了就会影响已有项目）

| # | 绝对不能做 | 做了会怎样 |
|---|---|---|
| 1 | `apt install nginx` 并让它监听 80/443 | 与 Docker 的 caddy 容器抢端口，Nginx 起不来；排障时容易误伤 Docker |
| 2 | `rm -f /etc/nginx/sites-enabled/default` | 如果宿主机另有 Nginx 站点，别人的站当场失联 |
| 3 | `ufw enable`（原本是关的） | 只放行 22/80/443，别人跑在 3000/8080 的服务立刻对外失联 |
| 4 | `docker compose down -v`、`docker system prune -a --volumes` | **会删掉别人容器的数据卷**（`qris-data`），不可恢复 |

另外两条容易忽略的：

- **Docker 发布的端口会绕过 ufw**（走 nat 表，不走 INPUT 链）。所以"ufw 没放行 80 却能从外面访问"是正常的，别以为防火墙失效了。
- **不要 `docker network prune`**。已停的容器再启动会找不到网络。

## 3. 推荐路径 A：Docker 独立项目（与已有项目同一种方式，隔离最彻底）

好处：**一个宿主机级软件都不装**（不装 Nginx、不装 Node、不加 systemd 单元）。
出问题 `docker compose down` 就干净退出，宿主机状态回到部署前。

### 3.1 先体检（把输出留着，出问题我要看）

```bash
# 端口：看 8080 有没有人占，看 80/443 是谁在听（docker-proxy 就是容器）
sudo ss -lntp | grep -E ':(80|443|8080|4600)\b'

# 已有容器：确认 qris-cashier 三个都在，记住它们的容器名
docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Ports}}'

# 资源：构建镜像约 130MB，磁盘别剩太少；内存别已经快满
df -h / ; free -h

# compose 版本（应该有 v2）
docker compose version
```

判定：

| 体检结果 | 处理 |
|---|---|
| 8080 被占 | 换 `8081` 或 `18080`（改下面 `.env` 的 `HOST_PORT`） |
| 磁盘可用 < 2 GB | 先 `docker image prune` 清无用镜像，别硬上 |
| 内存可用 < 300 MB | 本项目常驻约 80~120 MB，勉强；建议先加 swap |

### 3.2 放代码（独立目录，不碰任何已有路径）

```bash
sudo mkdir -p /opt/tideglass
sudo git clone https://github.com/jiaminfu/wildkind.git /opt/tideglass/current
```

`/opt/tideglass` 与 QRIS 的目录毫无关系。哪怕它也在 `/opt` 下，也只是同一个父目录。

### 3.3 配置（三行决定它只占 8080）

```bash
cd /opt/tideglass/current/deploy
sudo cp .env.example .env

# 换掉两个 CHANGE_ME（下面这行自己造口令，别用我给的示例）
openssl rand -base64 18

sudo nano .env
```

`.env` 里必须改这三处：

```ini
ADMIN_PASSWORD=刚生成的口令
OPS_PASSWORD=再生成一个

# 这两行是关键：决定它绑在 0.0.0.0:8080，而不是和宿主机反代抢 127.0.0.1:4600
BIND_ADDR=0.0.0.0
HOST_PORT=8080
```

> 默认值是 `127.0.0.1:4600`（只给宿主机反代用）。你这台机器不装反代，所以必须改成 `0.0.0.0`，否则浏览器访问不到。
> 注：`.env.example` 里这两行是注释掉的，需要去掉 `#`。

### 3.4 起服务

```bash
cd /opt/tideglass/current/deploy
sudo docker compose up -d --build

# 看状态：tideglass 应该是 Up (healthy)
sudo docker compose ps
sudo docker compose logs -f --tail=50
```

首次启动会自动生成演示数据（100 款 SKU、若干订单、券、评价），落在卷 `tideglass-data` 里。

### 3.5 本地自检（还没进公网）

```bash
curl -s http://127.0.0.1:8080/api/v1/health
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/
```

期望：`health` 返回 JSON 且 `"ok":true`，首页 `200`。

### 3.6 放行 8080（**这一步只能你做**）

两处都要，缺一个外面就打不开：

1. **云厂商控制台 → 安全组** → 入站规则加 `TCP:8080`
   （建议来源填**你自己的公网 IP**，不要 `0.0.0.0/0`——这条是 HTTP 明文，后台口令会裸奔）
2. 宿主机防火墙（**只有本来就是 active 才需要**）：

```bash
sudo ufw status | head -2
# 显示 inactive 就到此为止，别开！开了会波及已有项目
# 显示 active 才执行：
sudo ufw allow 8080/tcp
```

### 3.7 验收：新项目可用，且旧项目没变

| # | 检查 | 命令 / 动作 | 期望 |
|---|---|---|---|
| 1 | 旧站点还在 | `curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1/` | `200` |
| 2 | 旧后台还在 | 浏览器开 `http://194.36.85.20/admin/login` | 正常登录页 |
| 3 | 旧容器没被重启 | `docker ps` 看 `qris-cashier-*` 三个的 `STATUS` | 仍是原来的 Up 时长，没变成秒级 |
| 4 | 新站点通 | 浏览器开 `http://194.36.85.20:8080/` | TIDEGLASS 首页 |
| 5 | 新后台能登录 | `http://194.36.85.20:8080/#/admin` | 用 `.env` 里的口令登录成功 |
| 6 | 数据可写 | 后台改一个商品价格 → 刷新前台详情 | 价格变了（证明卷挂载正确） |
| 7 | 没抢 80 | `http://194.36.85.20/` 仍是 QRIS | 若变成 TIDEGLASS，说明有东西抢了反代，立刻停 |
| 8 | 端口归属正确 | `docker ps --format '{{.Names}} {{.Ports}}'` | `tideglass` 只有 `0.0.0.0:8080->4600/tcp` |

### 3.8 回滚（30 秒，互不影响）

```bash
cd /opt/tideglass/current/deploy
sudo docker compose down          # 只停/删 tideglass 的容器和网络

# 数据还留着（在 tideglass-data 卷里）。确认不要了再执行：
# sudo docker compose down -v && sudo docker volume rm tideglass-data
# sudo rm -rf /opt/tideglass
```

`docker compose down` 的作用域**只限本项目**（`name: tideglass`），不会碰 `qris-cashier` 的容器。
**注意别加 `-v`**，那会删数据卷。

## 4. 备选路径 B：宿主机 Node 直连 8080（不装 Nginx）

不想用 Docker 就走这条。它只装 Node（已有 ≥18 就跳过）、建一个系统用户、加一个 systemd 单元，
**连 nginx 这个包都不装**。

```bash
sudo NO_NGINX=1 LISTEN_PORT=8080 \
     bash /opt/tideglass/current/deploy/install.sh - \
     https://github.com/jiaminfu/wildkind.git
```

脚本在这个模式下的行为（已逐条核对源码）：

| 步骤 | 做什么 | 不做什么 |
|---|---|---|
| 基础包 | 装 `curl ca-certificates git openssl` | **不装 nginx** |
| Node | 已有 ≥18 就跳过；没有才装 22 | 不覆盖已有版本 |
| 端口体检 | 只检查 8080 | 不检查/不动 80/443 |
| 数据初始化 | 只在 `db.json` 缺失时生成 | 绝不动已有数据 |
| 反向代理 | 打印"跳过" | 不写任何 Nginx 配置、不 reload |
| 防火墙 | ufw 本来 active 才放行 8080 | 绝不 `ufw enable`；不封 8080 |
| HTTPS | 跳过 | 不装 certbot |

代价：Node 直接面对公网，没有反代的静态缓存与 gzip。功能上没差别（限流是应用内实现的），
卖货前建议拿到域名后换成「Nginx/域名 + HTTPS」。

## 5. 端口分配建议

| 端口 | 现在归谁 | TIDEGLASS 能否用 |
|---|---|---|
| 22 | SSH | — |
| 80 | QRIS 的 caddy 容器 | ❌ 绝对不用 |
| 443 | 同上（当前无站点） | ❌ 绝对不用 |
| 3000 | QRIS 的 app 容器（**未发布**，仅容器内） | ⚠️ 宿主机上没占用，但数字重叠易混淆，不用 |
| 8080 | 空闲（待你 `ss` 确认） | ✅ **首选** |
| 8081 / 18080 | 空闲 | ✅ 备选 |
| 4600 | 本项目容器内端口 | 只在容器内部，不发布 |

## 6. 三个"看着像故障、其实不是"的现象

1. **443 打不开** —— QRIS 用的是「只有 IP」的 `Caddyfile.ip`，那份配置只写 `:80`，容器里没有 `:443` 站点，所以连上就被重置。这是它当前无域名模式的正常结果，**不是本次部署造成的**，也不用你修。
   （顺带一句：从外网探测时偶尔会拿到 `502`，那多半是探测链路上的代理生成的——我在本机对正常服务做过对照，拿到了同样的 502。别拿它当故障证据。）
2. **`ss -lntp` 里 80 端口显示 `docker-proxy` 而不是 `caddy`** —— 正常。Docker 发布端口时由 `docker-proxy` 在宿主机侧监听，真实进程在容器 network namespace 里。
3. **`ufw status` 没放行 80，外面却能访问** —— 正常。Docker 的 DNAT 规则在 nat 表，绕过了 ufw 的 INPUT 链。

## 7. 将来的路（现在不用做）

拿到域名后不必重装，两种姿势：

| 现状 | 换法 | 改动量 |
|---|---|---|
| 路径 A（Docker） | 把 `BIND_ADDR` 改回 `127.0.0.1`，在 QRIS 的 Caddy 里加一个 `shop.域名 { reverse_proxy tideglass:4600 }` 站点 | 改 1 行 `.env` + 加 1 段 Caddy 配置 + `docker compose up -d` |
| 路径 B（直连） | 装 Nginx 并加域名站点，Node 收回 127.0.0.1 | 需要确认 80/443 归谁，先看第 2 节红线 |

Caddy 那种做法最省事：**同一个 caddy 容器带多个站点**，80/443 只被一个进程占用，
加了域名各自按 `server_name` 分流，不会互相截流量。等你要上域名时我再给完整配置。
