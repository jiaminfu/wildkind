**红线：`send` / `rsend` 两个子域必须是灰云（DNS only）。** 改成橙云后 CNAME 不再以 CNAME 形式解析，Resend 域名验证会立刻失败。这是 Cloudflare + Resend 组合最常见的坑。

### 3.2 Resend（事务邮件）

| 项 | 内容 |
| --- | --- |
| 控制台 | https://resend.com |
| 状态 | ✅ 已开通并实测发信成功（HTTP 200 + message id） |
| 权限 | Sending access（最小权限，不能读域名列表、不能建新 key） |
| 发件人 | `LASTGROVE <hello@lastgrove.com>` |
| 免费额度 | 3,000 封/月，100 封/天。一天 100 封 ≈ 一天 100 单，当前量级够用 |
| 超额 | 升级 Pro $20/月（5 万封），换 key 后改 `.env` 即可 |

**域名侧实际用的是 Resend 一键 Cloudflare 配置（CNAME 方案），不是手写 MX+SPF：**

| 记录 | 类型 | 值（实测） | 作用 |
| --- | --- | --- | --- |
| `send.lastgrove.com` | CNAME | `send.forge.rmta.net` | 退信处理（Return-Path），其 MX 为 `10 feedback.forge.rmta.net` |
| `rsend.lastgrove.com` | CNAME | `rsend.forge.rmta.net` | 发信认证 |
| `resend._domainkey.lastgrove.com` | TXT | `p=MIGfMA0GCSq...` | DKIM 签名公钥 |

> 与手工方案（`send` 上放 MX `feedback-smtp.us-east-1.amazonses.com` + TXT `v=spf1 include:amazonses.com ~all`）等价，两种都合法。**以 Resend 面板显示的为准**，别按旧文档手敲 MX —— 会与现有 CNAME 冲突。

**验证命令**（在服务器上跑，不用打开面板）：

```bash
docker exec lastgrove node -e 'const m=require("/app/app/server/lib/mailer");m.send({to:"delivered@resend.dev",subject:"自检",text:"ok",html:"<p>ok</p>"},"lg-selftest-"+Date.now()).then(r=>console.log("OK",JSON.stringify(r))).catch(e=>console.error("FAIL",e.status,e.message))'
```

`delivered@resend.dev` 是 Resend 官方测试地址，模拟成功投递，不骚扰真人。返回 `OK {"id":...}` 即通；403 是域名未验证；401 是 key 错。

**域名收信能力（2026-11-16 已开通）**：根域 MX 已指向 `route1/2/3.mx.cloudflare.net`，`hello@lastgrove.com` 经 **Cloudflare Email Routing** 转发到 `jiajiaornaments@gmail.com`。实测：以真实订单模板发往 `hello@lastgrove.com`，Gmail **收件箱**直接收到（主题 `Order #LG1042 confirmed`，message id `01a1e4bd-2a7e-74df-b190-04ae9a2405ec`），排版正常、无坏链接。

**一条实测教训——目标邮箱不要用 Outlook**：同一个地址先后转发到 `jamie2797@outlook.com`，Cloudflare Activity log 显示 `Forwarded`、Resend 显示 `Delivered`，但 Outlook **收件箱、垃圾邮件、「其他」三处均无此信**，属静默丢弃。换到 Gmail 后一次通过。若日后更换收件邮箱，**优先 Gmail / 企业邮箱，并在更换后立刻发一封 `Order #LG1041 confirmed` 验证实际到达**，不要只看 Cloudflare 的 `Forwarded`（它只表示「已投出」，不代表「已送达」）。

**Cloudflare 的一条硬限制**：Email Routing 只转发**认证通过**的来信，未通过 SPF/DKIM 的会被 `550 5.7.26 Cannot forward emails that are not authenticated` 拒绝。因此自建脚本裸 SMTP 发往 `hello@` 必失败，这是预期行为，不代表收信坏了——测试必须走 Resend 真实通道。

**收件地址定稿（2026-11-16 22:33）**：**只用 `jiajiaornaments@gmail.com`，Outlook 不再使用**。这是在实测之后做的决定，不是临时妥协——Outlook 对代发转发的过滤不可控且静默，出了问题连退信都没有，客户售后信丢了也不会有人知道。

因此 Cloudflare 侧还有两个收尾动作（都是可选，不做也不影响 `hello@` 收信）：

| 动作 | 位置 | 为什么值得做 |
|---|---|---|
| 删掉 `jamie2797@outlook.com` 这个 Destination | Email Routing → Destination addresses | 避免哪天误把规则指回 Outlook，重演静默丢信 |
| 把 Catch-all 从 `Drop` 改为转发到 Gmail 并启用 | Email Routing → Routing rules → Catch-all `...` → Edit | 现在是**关闭 + 丢弃**：客户写给 `support@`、`service@` 或把 `hello` 拼错的信会被静默丢弃，且发件人收不到退信。开启后全部落到 Gmail，代价只是随机地址的垃圾邮件 |

> 判断依据写在上面那条实测里：**`Forwarded` 不等于「已送达」**。所以「删除 Outlook 目标」比「留着当备份」更安全——它给不出任何保障，只会制造「应该能收到」的错觉。

## 4 改配置的标准流程

顺序固定，每一步都有原因：

```bash
# 1 备份（改错了能立刻退回去）
cd /opt/tideglass/current/deploy
cp .env .env.bak.$(date +%F-%H%M)

# 2 改（用编辑器改，别用 sed 拼字符串 —— 密钥含 / + = 时容易拼坏）
vi .env

# 3 重建（env_file 变了需要重建容器，restart 不会重新读文件）
docker compose up -d

# 4 三条验证
docker logs lastgrove 2>&1 | head -9          # 看「支付通道」「事务邮件」「物流追踪」三行
curl -s http://127.0.0.1:8080/api/v1/health   # 看 products/orders 数字有没有掉
docker exec lastgrove printenv <改的变量名>    # 确认值没被引号/空格吃掉
```

**为什么必须 `up -d` 而不是 `restart`**：`env_file` 是容器创建时读取的，`restart` 只是重启进程，环境变量还是旧的。改完 `.env` 用 `restart`，你会得到一个「改了但没生效」的假象，然后开始怀疑代码。

**含空格或尖括号的值**（如 `LASTGROVE <hello@lastgrove.com>`）直接写，不要加引号——加引号后引号本身可能被当成值的一部分。

## 6 交接时必须一起交的四样东西

1. **本文** —— 知道有哪些服务、各自什么状态
2. **服务器 SSH 私钥 + root 口令** —— 唯一的入口
3. **各服务控制台账号** —— Cloudflare / Resend / PayPal / 17TRACK，建议共用一个专用邮箱且开启两步验证
4. **`.env` 的位置说明** —— 只告诉在哪，不要把文件内容抄进聊天记录或邮件

> 交接时的常见事故：把 `.env` 内容截图发微信。截图会留在对方相册、可能被自动备份到云端，而里面的 PayPal Secret 可以直接用来发起收款。
