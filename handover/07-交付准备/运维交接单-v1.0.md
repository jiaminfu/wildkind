## 1. 一分钟了解现状

| 项 | 值 | 怎么自己确认 |
|---|---|---|
| 前台 | https://lastgrove.com/ | 浏览器打开 |
| 后台 | https://lastgrove.com/#/admin | 用老板账号登 |
| 健康检查 | `https://lastgrove.com/api/v1/health`（本机 `http://172.18.0.1:8080/api/v1/health`） | `curl` 一下，看 `"status":"ok"` |
| 代码目录 | `/opt/tideglass/current` | 目录名沿用旧品牌，**不要改**，改了要停机 |
| 容器 | `lastgrove`（healthy，`172.18.0.1:8080→4600`，**公网连不上，只在网桥上**） | `sudo docker ps` |
| 数据 | Docker 卷 `lastgrove-data` | `sudo docker volume inspect lastgrove-data` |
| 备份 | `/var/backups/lastgrove`，每天 19:30 UTC（北京 03:30），留 30 份 | `sudo bash /opt/tideglass/current/deploy/backup-docker.sh --list` |
| 环境变量 | `/opt/tideglass/current/deploy/.env`（权限 600，含口令与密钥） | `sudo ls -l` |
| 同机其他项目 | `qris-cashier-*` 三个容器（**别人的**，碰不得） | `sudo docker ps` |

**这个站点没有"服务器运维平台"**，就是一台 Ubuntu + Docker + 一个 compose 项目。
所有操作都在 `/opt/tideglass/current/deploy` 下执行。

## 2. 日常：每天 / 每周 / 每月

### 每天（2 分钟，早上看一眼就够）

| 看什么 | 命令 | 正常长什么样 |
|---|---|---|
| 服务活着吗 | `curl -s http://172.18.0.1:8080/api/v1/health` | `{"status":"ok",...}`，`products` / `orders` 数字不为 0 |
| 昨晚备份成功吗 | `tail -5 /var/log/lastgrove-backup.log` | 有**今天日期**的两行 `[ok]` |
| 有没有报错 | `sudo docker compose logs --since 24h 2>&1 \| grep -ic error` | 个位数；几十条才需要看具体内容 |

> 备份日志里出现 `container ... is not running` = 备份在默默失败。
> 这时**不要以为"配过就有了"**——去查 `/etc/cron.d/lastgrove-backup` 指向哪个脚本。

### 每周（10 分钟）

```bash
cd /opt/tideglass/current/deploy

# 磁盘：低于 15% 可用就要清理旧备份或镜像
df -h /

# 容器有没有反复重启（RESTARTS 列大于 3 要查）
sudo docker ps --format 'table {{.Names}}\t{{.Status}}\t{{.RunningFor}}'

# 数据在长多大（备份文件大小 ≈ 数据库大小）
sudo bash backup-docker.sh --list | head -3

# 顺手确认别的项目没被我们影响
sudo docker ps --format '{{.Names}} {{.Status}}' | grep qris
```

### 每月（30 分钟，**这条最重要**）

**真做一次恢复演练。** 不演练的备份等于没有备份——你以为有，出事时才发现是空的。

```bash
# 1. 记下当前某个商品的现价
# 2. 备份
sudo bash /opt/tideglass/current/deploy/backup-docker.sh
# 3. 后台把那个商品改价（改成明显不同的数字）
# 4. 用第 2 步的文件恢复
sudo bash /opt/tideglass/current/deploy/backup-docker.sh --restore \
     /var/backups/lastgrove/db-<刚才那个时间戳>.json.gz
# 5. 刷新前台，价格应该退回第 1 步的值
```

演练完**把价格改回真实值**，别把演练数据留在线上。

## 3. 出事时的判断顺序

**先判断范围，再动手。** 顺序错了会把小问题放大。

| 症状 | 先查什么 | 大概率原因 | 怎么办 |
|---|---|---|---|
| 整站打不开 | `curl -sS -m 5 http://172.18.0.1:8080/api/v1/health` | 容器挂了 / 端口没绑 | `sudo docker compose up -d`，看 `logs` |
| 本机通、外网不通 | 上面那条先在服务器上跑一遍 | 安全组/防火墙，或 `BIND_ADDR` 是 `127.0.0.1` | 查 `.env` 的 `BIND_ADDR` 与云厂商安全组 |
| 能打开但一片空白 | 浏览器 F12 → Console | 前端 JS 报错 / 静态资源 404 | 看 Network 里哪个请求红 |
| 后台登录后立刻掉线 | `logs` 里找 `401` | 令牌没存住 / `CORS_ORIGIN` 配错 | 查 `.env` 的 `CORS_ORIGIN` |
| 下单成功但没收到钱 | 后台订单详情里的支付状态 | `PAYMENT_PROVIDER=mock`，或 PayPal 回调没打通 | 见第 5 条红线；查 PayPal webhook 记录 |
| 后台改了东西、刷新就变回去 | `logs` 里找 `EACCES` | 数据卷属主被 root 改过 | `chown 10001:10001 /data/db.json` |
| 客户收不到邮件 | 启动日志里的邮件行 | 未配 `RESEND_API_KEY`（dry-run）或域名没验 DKIM | 见 `.env.example` 邮件段 |
| 物流不更新 | 订单里的单号是否已订阅 | 未配 `TRACK17_KEY` | 可以后补，不影响订单本身 |

**通用排查顺序**：健康接口 → 容器状态 → 日志最后 50 行 → 最近一次发版时间。
四条走完，九成问题能定位。

## 4. 五条红线

1. **不要 `docker compose down -v`。** 那个 `-v` 会删掉 `lastgrove-data` 卷，**所有订单、商品、客户一次性清零**，且不可恢复（只能从备份退回到昨天）。
2. **不要碰 `qris-cashier-*` 三个容器、不要改 80/443、不要动系统 Nginx。** 那是同机另一个项目，占着 80/443；我们只用 8080。历史上部署全程这三个容器的 Up 时长一次都没被打断，要保持。
3. **不要在生产上直接改代码。** 服务器目录只接受 `git reset --hard origin/main`。手工改的文件下次发版就被覆盖，而且没人知道线上跑的和仓库差在哪。
4. **不要在 `db.json` 上手工编辑。** 它是全部生意（含口令 hash）。要改数据走后台界面；后台改不了的需求先提，别上服务器 sed。
5. **不要把 `PAYMENT_PROVIDER` 留成 `mock` 就上线。** 那等于全站免费下单——订单会标成已支付，账户里一分钱不会有，而且不会报错。

## 5. 交接时必须交出去的四件东西

| 东西 | 在哪 | 怎么交 |
|---|---|---|
| 后台账号与口令 | `deploy/.env` 的 `ADMIN_PASSWORD` / `OPS_PASSWORD` | 当面或密码管理器，**不要发微信/邮件** |
| 第三方密钥 | `deploy/.env` 的 `PAYPAL_*` / `RESEND_API_KEY` / `TRACK17_KEY` | 同上；换人后要去各平台重新签发 |
| 服务器 SSH 权限 | 云厂商控制台 | 加**自己的**公钥，不要共用同一个私钥 |
| 备份在哪、怎么恢复 | `/var/backups/lastgrove` + 第 2 章月度演练 | 当面跑一遍恢复演练给对方看 |

> `.env` 里所有值都是生产凭据。这份文件不进 Git（`.gitignore` 已排除），也不要截图发群。

## 6. 发版怎么做

只有一条命令：

```bash
sudo bash /opt/tideglass/current/deploy/update-docker.sh
```

它会按 **备份 → 拉代码 → 重建 → 探活** 的顺序走，任何一步失败都会打印回滚命令并停下。
发了之后发现问题，回退到上一个版本：

```bash
sudo bash /opt/tideglass/current/deploy/update-docker.sh --rev <上一个提交号>
```

没验证过就上线的版本，不要在工作时间发版——留出能回退的窗口。
