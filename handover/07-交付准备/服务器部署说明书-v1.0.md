## 0. 读完这一页就够

三句话：

1. 这台机器的 **80/443 被已有项目的 Docker 容器占着**，所以 TIDEGLASS 只用 **8080**，一个字节都不碰 80/443。
2. 用 **Docker 独立项目**部署（`name: tideglass`），跟已有项目除了宿主机端口之外没有任何共享。
3. **`ADMIN_PASSWORD` 必须在第一次启动前改掉**——不改的话后台口令是公开的 `tideglass2026`。

跑完你会得到：

## 1. 这台机器的现状（部署前必须知道）

### 1.1 已有什么

| 项 | 现状 | 来源 |
|---|---|---|
| 已有项目 | QRIS 收银台 · Bali（Next.js） | `http://194.36.85.20/` |
| 部署方式 | **docker compose 三容器** | `qris-cashier/deploy/docker-compose.yml` |
| 80 / 443 归谁 | 那个项目的 **`caddy` 容器**（宿主机侧显示 `docker-proxy`） | `docker ps` |
| compose 项目名 | `qris-cashier` | — |
| 数据卷 | `qris-data`、`qris-backup`、`caddy-data`、`caddy-config` | — |

### 1.2 四条红线

| # | 绝对不能做 | 后果 |
|---|---|---|
| 1 | 装系统 Nginx（`apt install nginx`） | 它自动启动去 bind 80，与 `docker-proxy` 冲突；排障时容易误伤 Docker |
| 2 | `ufw enable`（原本是关的） | 只放行 22/80/443，别人跑在其他端口的服务当场对外失联 |
| 3 | `docker compose down -v`、`docker system prune -a --volumes` | **删掉别人的数据卷**，不可恢复 |
| 4 | 在 80/443 上起任何东西 | 抢已有项目的流量 |

只要你的命令里没有这四样，就不会伤到已有项目。

## 2. 部署前 5 分钟：五条体检

```bash
# ① 端口：谁在听 80/443，8080 有没有被占
sudo ss -lntp | grep -E ':(80|443|8080|4600)\b'

# ② 已有容器：记住它们的状态（部署后要对比有没有被重启）
docker ps --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'

# ③ 编排工具是否可用（必须能打印出版本号）
docker compose version

# ④ 资源：磁盘至少留 2 GB，内存至少留 300 MB
df -h / ; free -h

# ⑤ git 是否可用
git --version
```

判定表：

| 体检结果 | 怎么办 |
|---|---|
| `8080` 出现在 `ss` 输出里 | 换端口：全文把 `8080` 换成 `8081` 或 `18080` |
| 磁盘可用 < 2 GB | 先 `docker image prune -f`，再 `df -h /` 复查 |
| 内存可用 < 300 MB | 本项目常驻约 80~120 MB，勉强能跑；建议先加 1 GB swap |
| `docker compose version` 报 "not a plugin" | `sudo apt install -y docker-compose-plugin` |
| `git` 不存在 | `sudo apt install -y git` |

> **把第 ① ② 条的输出留一份。** 部署完要拿它对比，这是证明「没影响已有项目」的唯一证据。

## 3. 正式部署：七个步骤

### Step 1 · 放代码（独立目录）

```bash
sudo mkdir -p /opt/tideglass
sudo git clone https://github.com/jiaminfu/wildkind.git /opt/tideglass/current
```

期望：`Cloning into '/opt/tideglass/current'...`，最后一行是 `Resolving deltas: 100%`。

失败处置：

| 报错 | 原因 | 处理 |
|---|---|---|
| `Repository not found` | 仓库是 Private | 换成带令牌的地址，或用部署密钥（见手册第 6 章） |
| `Could not resolve host` | DNS 不通 | `ping github.com` 排查 |

### Step 2 · 配 `.env`（这一步决定成败）

```bash
cd /opt/tideglass/current/deploy
sudo cp .env.example .env

# 生成两个强口令，先记下来
openssl rand -base64 18
openssl rand -base64 18

sudo nano .env
```

`.env` 里必须改 **4 处**：

```ini
ADMIN_PASSWORD=第一个口令
OPS_PASSWORD=第二个口令

BIND_ADDR=0.0.0.0        # 去掉行首 #
HOST_PORT=8080           # 去掉行首 #
```

改完核对一遍（应能看到 4 行都已生效）：

```bash
sudo grep -E '^(ADMIN_PASSWORD|OPS_PASSWORD|BIND_ADDR|HOST_PORT)=' .env
```

> **为什么这 4 行是命门**
> - `ADMIN_PASSWORD` 不设 → 种子脚本用默认值 `tideglass2026`（代码里写死的）。后台挂在公网、口令是公开的，等于没有后门也等于敞开。
> - `BIND_ADDR` 不改 → 端口只绑 `127.0.0.1`，容器起来了、健康检查也是绿的，但**外网打不开**，很容易白白排查半小时。
> - 口令是 `scrypt` 哈希存进 `db.json` 的，**启动之后再改 `.env` 不起作用**（改法见第 5.6 节）。

### Step 3 · 校验编排配置

先不启动，让 compose 把变量替换算一遍：

```bash
sudo docker compose config | grep -A4 'ports:'
```

期望看到：

```yaml
ports:
  - mode: ingress
    target: 4600
    published: "8080"
    host_ip: 0.0.0.0
```

若 `published` 还是 `4600` 或 `host_ip` 还是 `127.0.0.1` → 回 Step 2，`.env` 没改对。

### Step 4 · 构建并启动

```bash
cd /opt/tideglass/current/deploy
sudo docker compose up -d --build

# 看构建与启动日志（首次会打印 seed 结果与后台口令）
sudo docker compose logs --tail=40
```

期望日志里出现两段：

```
[init] /app/app/server/data/db.json 不存在，用种子数据初始化…
[init] 完成。请立即登录后台修改默认口令。
TIDEGLASS API 已启动 → http://localhost:4600
  数据：…（商品 36 / 订单 90）
```

（商品 36 款、SKU 67 个、订单 90 单、客户 56 位、券 4 张、评价 59 条 —— 这是演示数据，可直接用来验收。）

确认状态：

```bash
sudo docker compose ps
```

期望 `STATUS` 列显示 **`Up (healthy)`**。若显示 `Up (health: starting)`，等 30 秒再看一次。

### Step 5 · 本机自检（还没进公网）

```bash
curl -s http://127.0.0.1:8080/api/v1/health
curl -s -o /dev/null -w '首页 %{http_code}\n' http://127.0.0.1:8080/
curl -s -o /dev/null -w '后台资源 %{http_code}\n' http://127.0.0.1:8080/assets/js/admin.js
```

期望：

```
{"data":{"status":"ok","version":"1.0.0","products":36,"orders":90,"time":"..."}}
首页 200
后台资源 200
```

三条都过 = 应用本身没问题，后面打不开就只可能是网络/防火墙。

### Step 6 · 放行 8080（**只能你做**）

两处都要，缺一个外面就打不开：

1. **云厂商控制台 → 安全组 → 入站规则** → 加 `TCP:8080`
   - 来源填**你自己的公网 IP**（查法：本机浏览器访问 `ifconfig.me`）
   - 不要填 `0.0.0.0/0`：这条是 HTTP 明文，后台口令在网络上是裸的
2. **宿主机防火墙**（**只有本来就是 active 才需要**）：

```bash
sudo ufw status | head -2
```

| 输出 | 动作 |
|---|---|
| `Status: inactive` | **到此为止，不要开**。开了会波及已有项目 |
| `Status: active` | `sudo ufw allow 8080/tcp` |

> Docker 发布的端口会绕过 ufw（走 nat 表）。所以最终裁判是**云安全组**。
> 但也正因为绕过，`ufw allow` 不会帮你放行——安全组必须自己加。

### Step 7 · 验收 8 条

| # | 检查 | 怎么做 | 通过标准 |
|---|---|---|---|
| 1 | 旧站点还在 | `curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1/` | `200` |
| 2 | 旧后台还在 | 浏览器开 `http://194.36.85.20/admin/login` | 正常登录页 |
| 3 | **旧容器没被重启** | `docker ps` 看 `qris-cashier-*` 三个 | STATUS 是原来的 Up 时长，没有变成秒级 |
| 4 | 新前台通 | `http://194.36.85.20:8080/` | TIDEGLASS 首页，图片正常 |
| 5 | 新后台能登录 | `http://194.36.85.20:8080/#/admin` | 用 `owner@tideglassjewelry.com` + Step 2 的口令登进去 |
| 6 | 数据可写 | 后台 → 商品 → 改一个价格 → 保存 → 前台详情刷新 | 价格变了（证明卷挂载正确） |
| 7 | 没抢 80 | 再开 `http://194.36.85.20/` | 仍是 QRIS。**若变成 TIDEGLASS，立刻 `docker compose down`** |
| 8 | 端口归属正确 | `docker ps --format '{{.Names}} {{.Ports}}'` | `tideglass` 只有 `0.0.0.0:8080->4600/tcp` |

8 条全过，部署结束。

> **第 3 条为什么重要**：如果旧容器被重启了，说明有东西动了 Docker（比如 `systemctl restart docker`、
> 或某个 compose 项目 name 撞了导致 `up` 把别人的容器重建）。这时不要继续，先把 `docker ps` 和
> `docker compose config` 的输出发我。

## 4. 上线后必做（两件事，别跳）

### 4.1 立刻收紧来源 IP

现在 8080 是 HTTP 明文。验证完就把安全组的来源改回只允许你的 IP；等切换域名 + HTTPS 后再放开。

### 4.2 配一条每天备份

```bash
sudo mkdir -p /opt/tideglass/backups

# 手动先跑一次，确认能出文件
sudo docker cp tideglass:/app/app/server/data/db.json \
     /opt/tideglass/backups/db-$(date +%F-%H%M).json
ls -lh /opt/tideglass/backups/
```

期望：一个约 200 KB 的 `.json`，**不是 0 字节**（0 字节说明 `docker cp` 路径写错了）。

加定时任务：

```bash
sudo crontab -e
# 加这一行：每天 3:10 备份，保留 14 天
10 3 * * * docker cp tideglass:/app/app/server/data/db.json /opt/tideglass/backups/db-$(date +\%F-\%H\%M).json && find /opt/tideglass/backups -name 'db-*.json' -mtime +14 -delete
```

> cron 里的 `%` 必须写成 `\%`，否则 `date` 参数会被 cron 切断——这是最容易踩的一个坑。

## 5. 日常运维：六件事

全部在 `/opt/tideglass/current/deploy` 目录下执行。

### 5.1 看状态

```bash
cd /opt/tideglass/current/deploy
sudo docker compose ps
curl -s http://127.0.0.1:8080/api/v1/health
```

### 5.2 看日志

```bash
sudo docker compose logs -f --tail=100      # 跟实时日志
sudo docker compose logs --since 30m        # 看最近 30 分钟
```

日志已按 10 MB × 3 个文件滚动，不会把磁盘写满。

### 5.3 重启

```bash
sudo docker compose restart
```

### 5.4 更新代码（发版）

**顺序不能换：先备份 → 再拉代码 → 再重建 → 再探活。**

```bash
# 1 备份
sudo docker cp tideglass:/app/app/server/data/db.json \
     /opt/tideglass/backups/db-$(date +%F-%H%M)-before-update.json

# 2 拉代码
cd /opt/tideglass/current
sudo git pull

# 3 重建（数据在卷里，不受影响）
cd deploy
sudo docker compose up -d --build

# 4 探活
sleep 5
curl -s http://127.0.0.1:8080/api/v1/health
```

数据卷 `tideglass-data` 不会被 `up --build` 动到，订单不会丢。

### 5.5 备份与恢复

**备份**：见 4.2。

**恢复**（会把数据退回到备份那一刻）：

```bash
cd /opt/tideglass/current/deploy
sudo docker compose stop

# 先验证备份文件是合法 JSON，坏文件不要往进灌
sudo docker run --rm --entrypoint node \
  -v /opt/tideglass/backups:/b tideglass:1.0.0 \
  -e "JSON.parse(require('fs').readFileSync('/b/db-2026-11-13-1530.json','utf8'));console.log('JSON 合法')"

# 灌回去（用 --entrypoint 绕开启动脚本，避免它去跑 seed）
sudo docker run --rm --entrypoint sh \
  -v tideglass-data:/data -v /opt/tideglass/backups:/b tideglass:1.0.0 \
  -c 'cp /b/db-2026-11-13-1530.json /data/db.json'

sudo docker compose start
curl -s http://127.0.0.1:8080/api/v1/health
```

**每个月真演练一次**：改个商品价 → 备份 → 再改价 → 恢复 → 看价格有没有退回去。
不演练的备份等于没有备份。

### 5.6 改后台口令

口令是 `scrypt` 哈希存在 `db.json` 里，**改 `.env` 无效**（那只在第一次 seed 时生效）。
必须停服务改数据：

```bash
cd /opt/tideglass/current/deploy
sudo docker compose stop

sudo docker compose run --rm --entrypoint node tideglass -e "
const fs=require('fs'), a=require('/app/app/server/lib/auth');
const f='/app/app/server/data/db.json';
const db=JSON.parse(fs.readFileSync(f,'utf8'));
const p=a.hashPassword(process.argv[1]);
const s=db.staff.find(x=>x.email==='owner@tideglassjewelry.com');
s.salt=p.salt; s.hash=p.hash;
db.sessions=[];                                  // 顺手踢掉所有旧登录
fs.writeFileSync(f, JSON.stringify(db,null,1));
console.log('已更新，旧会话全部失效');
" '你的新口令'

sudo docker compose start
```

> 必须先停：进程内存里还有一份数据镜像，运行中改文件会被下一次写操作覆盖。

### 5.7 换端口

```bash
cd /opt/tideglass/current/deploy
sudo nano .env            # 改 HOST_PORT=8081
sudo docker compose up -d
# 安全组同步放行新端口，旧的收回
```

## 6. 故障排查：症状 → 查什么 → 怎么办

| 症状 | 先查 | 处置 |
|---|---|---|
| `docker compose up` 报 `bind: address already in use` | `sudo ss -lntp \| grep 8080` | 端口被占，改 `.env` 的 `HOST_PORT` |
| 容器 `Up` 但 `unhealthy` | `sudo docker compose logs --tail=50` | 看日志报错；常见是数据目录权限或端口不对 |
| 容器反复重启 | `sudo docker inspect tideglass --format '{{.State.ExitCode}}'` | 退出码 1 且日志有 EACCES → 卷属主问题，见下条 |
| 日志 `EACCES ... db.json` | `sudo docker volume inspect tideglass-data` | 卷被 root 动过。`sudo docker run --rm --entrypoint sh -v tideglass-data:/data tideglass:1.0.0 -c 'chown -R 10001:10001 /data'` |
| 本机 `curl 127.0.0.1:8080` 通，外网打不开 | 云安全组 | 放行 `TCP:8080`；来源别只填错的网段 |
| 外网报连接超时（不是拒绝） | 同上 | 九成是安全组；`拒绝` 才是宿主机没监听 |
| 页面能开但接口全 404 | `curl -s 127.0.0.1:8080/api/v1/health` | 若 health 通、页面 404 → 前端静态资源没打进镜像，重新 `--build`（别用 `--no-cache` 之前的旧层） |
| 后台登录后立刻跳回登录页 | 浏览器 F12 → Network 看 `/admin/login` 响应 | 401 且提示 `Session expired` → 会话过期（12 小时）；没提示 → 把 `docker compose logs` 发我 |
| 后台改了价格，前台没变 | 前台强制刷新 `Ctrl+Shift+R` | 还不变就查 `.env` 的 `CORS_ORIGIN`；同域部署留 `*` 即可 |
| 重启后数据回到初始状态 | `sudo docker volume ls \| grep tideglass` | 卷丢了 → 说明用了 `down -v` 或 `--rm` 临时容器。从备份恢复（5.5） |
| `git pull` 报冲突 | `git status` | 部署机上**不该改代码**。`git checkout -- .` 丢弃本地改动后重拉 |
| 磁盘满 | `df -h /`、`docker system df` | `docker image prune -f`（**别用 `-a`，可能删到别人正在用的镜像**） |
| 忘记后台口令 | — | 按 5.6 直接改 `db.json`，不需要知道旧口令 |

出问题请给我这三段（只读，不改任何东西）：

```bash
cd /opt/tideglass/current/deploy && sudo docker compose ps
sudo docker compose logs --tail=60
sudo ss -lntp | grep -E ':(80|443|8080)\b'
```

## 8. 拿到域名之后

不用重装，数据一个字节都不变。两种做法：

| 现状 | 换法 | 改动 |
|---|---|---|
| **推荐**：把新站点挂到已有 Caddy 里 | 在 `qris-cashier` 的 Caddyfile 加一段 `shop.你的域名 { reverse_proxy tideglass:4600 }`，两个容器接同一个 Docker 网络；`.env` 的 `BIND_ADDR` 改回 `127.0.0.1` | 1 段 Caddy 配置 + 1 行 `.env` |
| 或者自己装 Nginx | ⚠️ 先确认 80/443 归属，见 1.2 红线 | 较多 |

Caddy 那种最省事：80/443 永远只被一个进程占着，多个站点按域名分流，互不截流量。
要切换时把两台机器的现状发我，我给完整配置。

## 9. 备选路径：不用 Docker

只想装一个 Node 进程、不想要容器，用直连模式（**连 nginx 这个包都不装**）：

```bash
sudo mkdir -p /opt/tideglass
sudo git clone https://github.com/jiaminfu/wildkind.git /opt/tideglass/current
sudo NO_NGINX=1 LISTEN_PORT=8080 \
     bash /opt/tideglass/current/deploy/install.sh - \
     https://github.com/jiaminfu/wildkind.git
```

它会做：装 Node（已有 ≥18 就跳过）→ 建系统用户 `tideglass` → 拉代码 → 生成随机口令并打印 →
初始化数据 → 装 systemd 单元 `tideglass-api` → 跳过 Nginx 整段 → 放行 8080（防火墙本来开着才做）。

| 对比 | Docker（推荐） | 直连 |
|---|---|---|
| 宿主机装了什么 | 什么都没装 | Node + 系统用户 + systemd 单元 |
| 回滚 | `docker compose down` 一句话 | 停服务、删单元、删目录 |
| 口令怎么来 | 自己写进 `.env` | 脚本生成并打印在屏幕上 |
| 更新 | `git pull` + `up -d --build` | `bash deploy/update.sh` |

两种方式**不要同时用**——会抢 8080，而且两套数据文件互相不认识。

## 附录 B · 为什么不能装 Nginx（三句话讲完）

1. `apt install nginx` 装完**自动启动**，它去 bind `0.0.0.0:80`。
2. 而 80 已经被 Docker 的 `docker-proxy` 占住（那是已有项目的 caddy 容器发布的），于是 `bind() failed (98: Address already in use)`。
3. 接下来最常见的错误动作是 `systemctl stop docker` 去腾端口——**那会让已有项目全站挂掉**。

所以本项目在这台机器上的合法姿势只有两个：**Docker 独立项目**（本文第 3 节）或 **直连端口不装 Nginx**（第 9 节）。
