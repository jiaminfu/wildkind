## 2 三个通道的准入门槛

### 2.1 Stripe（体验最好，但需要境外主体）

Stripe 的支持地区列表里**没有中国大陆**。可选路径：

| 路径 | 一次性成本 | 年维护 | 代码改动 |
|---|---|---|---|
| Stripe Atlas 注册美国 LLC | $500 | 报税 + 注册代理，约 $500–1500/年 | 零 |
| 香港公司 + Stripe HK | ¥3–6k 注册 | ¥2–4k 年审 | 零 |

⚠ **美国 LLC 的隐性成本**：非居民持有的美国 LLC 每年要报 5472 + 1120 表，逾期罚款起步 $25,000。这笔钱要么自己学，要么找代账。很多人只算了注册费。

### 2.2 Airwallex（大陆营业执照可直接开）

申请材料（缺一不可）：

- 营业执照扫描件
- 法人身份证正反面
- **对公账户流水**（PDF）
- 办公地址证明：近 3 个月水电费或物业账单
- 《企业信息确认函》（官网下载模板，加盖公章）

流程：线上申请 → 视频认证法人（约 5 分钟）→ KYC 审核 **2–7 个工作日**。

**审核会被拒的三种情况**：
1. 网站没上线 / 只有 IP 访问
2. 商品数量太少、页面完成度低，看不出在正经经营
3. **营业执照经营范围与售卖品类不符**（本项目现状：主体是「摄影有限公司」，卖饰品）

费率：卡收单 **2.8%–3.4% + $0.30/笔**，月流水上去可谈。首站免费，第二站 $500。

### 2.3 PayPal（兜底，不是替代）

大陆营业执照可开企业账户。费率约 **3.49% + $0.49**，跨境再加 1.5%。

价值在于转化：美国消费者 PayPal 渗透率两到三成，没有这个按钮会直接弃单。
风险在于风控：新账户突然起量、发货慢、拒付率高都可能触发 180 天冻结。

## 3 配置步骤

### 3.1 环境变量

复制 `deploy/.env.example`，改这几项：

```bash
PAYMENT_PROVIDER=stripe        # 或 airwallex / paypal
PUBLIC_URL=https://你的域名    # 不带结尾斜杠

# 按所选通道填对应的一组，其余留注释
STRIPE_SECRET_KEY=sk_live_xxx
STRIPE_WEBHOOK_SECRET=whsec_xxx
```

⚠ **`PAYMENT_PROVIDER` 忘了改是最危险的失误**：留 `mock` 上线，每单都会被标记为已支付，但账户里一分钱没有。启动日志会打警告，但不会阻止进程启动。

### 3.2 回调地址

统一格式：`https://你的域名/api/v1/payments/webhook/<provider>`

| 通道 | 必须订阅的事件 |
|---|---|
| Stripe | `checkout.session.completed`、`checkout.session.async_payment_failed`、`payment_intent.payment_failed`、`charge.refunded` |
| Airwallex | `payment_intent.succeeded`、`payment_intent.failed`、`refund.succeeded` |
| PayPal | `PAYMENT.CAPTURE.COMPLETED`、`PAYMENT.CAPTURE.DENIED`、`PAYMENT.CAPTURE.REFUNDED` |

### 3.3 切换与验证

```bash
# 1. 确认通道信息接口认到了新通道
curl -s https://你的域名/api/v1/payments/methods | jq .data

# 期望：provider 是所选通道，flow=async，configured=true
```

```bash
# 2. 沙盒走一单（Stripe 测试卡 4242 4242 4242 4242，任意未来日期，任意 CVC）
#    预期链路：
#    下单 → 202 + clientSecret → 付款 → webhook → 订单 status 从 pending_payment 变 paid
```

```bash
# 3. 查回调是否被正确处理
grep '\[payments\] webhook' /var/log/tideglass/app.log | tail -20
```

**验证清单**（每条都要真跑，不能看代码推断）：

- [ ] 下单返回 202 且带 `clientSecret`
- [ ] 订单状态初始为 `pending_payment`，后台能按此筛选
- [ ] 付款完成后 webhook 到达，订单变 `paid`
- [ ] **同一事件重投两次，第二次返回 `duplicate:true`，订单状态不被重复变更**
- [ ] 伪造签名（改一个字符）返回 400
- [ ] 支付失败 → 订单变 `cancelled`，**库存被释放回原值**
- [ ] 退款 → 订单变 `refunded`

## 6 代码里已经守住的几条线

这些是本次抽象时一并处理的，改动时不要破坏：

1. **金额只由服务端算**。前端传来的任何价格字段在 `checkout.js` 里直接被丢弃，支付通道拿到的是 `fresh.total`。
2. **先建会话再落单**。反过来的话，会话创建失败会留下「库存已扣、订单挂着却收不到钱」的僵尸单。
3. **库存是预留，不是终态**。支付失败的回调会触发 `releaseStock()` 把库存加回去，并写一条 `payment_failed_release` 流水。
4. **验签用原始字节**。`req.rawBody` 从 body 的不可枚举属性 `__raw` 取出，因为 JSON 二次序列化会改变空格与键序，签名必然对不上。
5. **回调路径必须与当前通道一致**。往 `/webhook/stripe` 打事件，在 Airwallex 启用期间会被直接拒绝，防止伪造路径绕过验签。
6. **事件去重**。同一 `eventId` 第二次到达返回 `duplicate:true`，避免「已退款」被重投翻回「已支付」。
7. **webhook 找不到订单时返回 200**。通道对 4xx 会持续重投，而那单可能本来就不属于本站。
