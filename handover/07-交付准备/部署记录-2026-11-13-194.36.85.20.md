## 五、每日备份

```bash
cat /etc/cron.d/tideglass-backup
# 30 19 * * * root bash /opt/tideglass/backup.sh >> /var/log/tideglass-backup.log 2>&1
```

服务器时区是 UTC，`19:30 UTC` = 北京次日 `03:30`。

| 操作 | 命令 |
|---|---|
| 立即备份 | `bash /opt/tideglass/backup.sh` |
| 看备份列表 | `bash /opt/tideglass/backup.sh --list` |
| 恢复 | `bash /opt/tideglass/backup.sh --restore /var/backups/tideglass/db-xxx.json.gz` |
| 看备份日志 | `tail -20 /var/log/tideglass-backup.log` |

策略：保留最近 30 份（`BACKUP_KEEP`），单份约 24 KB，一年也就 9 MB。
备份脚本与仓库里的 `deploy/backup.sh` 不同——那一份假设数据在宿主机目录且宿主机装了 node，这台机器是纯容器部署、宿主机没有 node，所以数据从容器里取、用容器里的 node 校验。

**每次备份都会做 JSON 解析 + 四个关键字段校验，校验失败当场删掉，不留假备份。**

## 七、当前风险（按严重度）

| # | 风险 | 现状 | 处置 |
|---|---|---|---|
| 1 | **全程 HTTP 明文** | 8080 直接对公网开放，后台口令与令牌明文传输 | 拿到域名当天签证书（说明书第 8 章）；过渡期在云安全组把 8080 来源改成你的固定 IP |
| 2 | 8080 对全网开放 | 实测从外网可达，说明安全组已放行（可能是全开） | 同上，建议收紧来源 |
| 3 | 仍是演示数据 | 36 个商品是渲染图，订单 90 条是虚构的 | 换真实商品与实拍图，清空演示订单 |
| 4 | 无域名 | 只能用 IP + 端口访问，Stripe 上线必须有 HTTPS 域名 | 买域名（¥10~60/年）后按说明书第 8 章挂到已有 Caddy |
| 5 | 单实例约束 | JSON 单文件 + 内存限流 + 内存会话 | 只能 1 个副本；扩容前必须先换数据库（见 SDD 8.1） |
| 6 | 服务器内存 1.8 G | 现有 755 MB 已用，本项目占 10 MB | 目前充裕；不要在这台机上再加大内存型服务 |

> **关于第 1、2 条**：现在后台口令是随机 18 位，被猜中的概率可以忽略；但明文传输意味着同一网络路径上的嗅探者能看到。演示阶段可接受，接入真实收款前必须换成 HTTPS。

## 八、回滚

```bash
# 只停本站，数据保留（推荐）
cd /opt/tideglass/current/deploy && docker compose down

# 连数据一起删（不可恢复，除非有备份）
#   docker compose down -v
#   注意：-v 会删 tideglass-data 卷，但不会碰 qris-cashier 的任何卷

# 重新起来
cd /opt/tideglass/current/deploy && docker compose up -d
```

彻底卸载（不留痕）：

```bash
cd /opt/tideglass/current/deploy && docker compose down -v
docker rmi tideglass:1.0.0
rm -rf /opt/tideglass /var/backups/tideglass /var/log/tideglass-backup.log
rm -f /etc/cron.d/tideglass-backup
```
