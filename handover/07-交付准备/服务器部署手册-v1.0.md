## 0. 这份手册怎么用

三条路，按你的情况选一条，不要混着走：

| 路径 | 适合谁 | 耗时 | 从哪开始 |
|---|---|---|---|
| **A. 全自动** | 想最快看到线上跑起来 | 约 15 分钟 | 第 5 章 |
| **B. 手动逐步** | 想知道每一步在干什么、以后自己改 | 约 40 分钟 | 第 6 章 |
| **C. Docker** | 服务器上还跑着别的东西，怕污染环境 | 约 20 分钟 | 第 11 章 |

三条路的**结果完全一样**：Nginx 收 443 → 反代给本机 Node 4600 → 数据落在 `app/server/data/db.json`。

不管走哪条，**第 7 章「上线后必做」不能跳**，跳过等于把后台口令写在公网上。

## 1. 部署前准备清单

先确认这些东西齐了，缺一样后面就会卡住：

| # | 需要 | 必须 | 说明 | 去哪拿 |
|---|---|---|---|---|
| 1 | 服务器 | ✅ | Ubuntu 22.04 / 24.04 或 Debian 12，2 核 2G 起 | 见第 4 章选型 |
| 2 | 公网 IP + root 密码或 SSH 密钥 | ✅ | 能 SSH 登录 | 云厂商控制台 |
| 3 | 域名 | ✅ | 例如 `shop.tideglass.com` | 已有域名加一条子域即可 |
| 4 | DNS 解析权限 | ✅ | 加一条 A 记录指向服务器 IP | 域名商后台 |
| 5 | GitHub 仓库 | ✅ | 代码已经推上去（见第 5.1 节） | 本手册配套 |
| 6 | 一个邮箱 | 🟡 | 签 Let's Encrypt 证书、接收到期提醒 | 任意可用邮箱 |
| 7 | Stripe 密钥 | 🟢 | 现在没有也能上线，支付走测试模式 | 见 `07-交付准备/外部资料需求清单` |
| 8 | Resend API Key | 🟢 | 同上，邮件先写日志不真发 | 同上 |

> **不要提前准备的东西**：数据库、Redis、PM2。本项目零第三方依赖，不需要这些；装了反而是负担（原因见第 3 章）。

### 1.1 一个决策：服务器放哪儿

| 方案 | 优点 | 代价 | 建议 |
|---|---|---|---|
| 美西（洛杉矶 / 圣何塞 / 硅谷） | 主力客群在美国，延迟最低；不需要 ICP 备案 | 你在国内 SSH 会有点慢 | **推荐** |
| 中国香港 | 国内外都快 | 带宽贵，价格通常高一倍 | 备选 |
| 中国大陆 | 便宜 | 必须 ICP 备案（没备案域名不能解析到大陆服务器） | 不建议，备案周期会拖死上线 |

## 2. 目标架构

```
                    用户浏览器（美国 / 加拿大 / 英国）
                              │  HTTPS 443
                              ▼
        ┌──────────────────────────────────────────┐
        │  Nginx（同机，占用 80 / 443）              │
        │                                          │
        │  /            → 直接读磁盘上的静态文件      │
        │                 /opt/tideglass/current/app/web
        │  /api/*       → 反向代理到 127.0.0.1:4600  │
        └──────────────────┬───────────────────────┘
                           │ HTTP（只在本机回环，不出网卡）
                           ▼
        ┌──────────────────────────────────────────┐
        │  Node.js 进程（systemd 管，占 4600）       │
        │  · REST API（47 个操作）                   │
        │  · 前台 SPA 兜底（未命中静态文件时给 index） │
        │  · 服务端定价 / 报价锁 / 幂等 / 库存流水     │
        └──────────────────┬───────────────────────┘
                           │ 读 + 原子写
                           ▼
        ┌──────────────────────────────────────────┐
        │  app/server/data/db.json（唯一数据源）      │
        │  商品 / 订单 / 客户 / 券 / 流水 / 会话 / 账号 │
        └──────────────────────────────────────────┘
```

端口与暴露面：

| 端口 | 谁在听 | 对外 | 说明 |
|---|---|---|---|
| 80 | Nginx | ✅ | 只用于证书校验 + 跳 HTTPS |
| 443 | Nginx | ✅ | 全部业务流量 |
| 4600 | Node | ❌ | 只允许本机；防火墙必须封掉 |
| 22 | SSH | 🟡 | 建议只允许你的 IP |

**为什么静态文件交给 Nginx 而不是 Node 出**：Node 那套静态服务是给本地联调方便的（`app/server/index.js` 里 `serveStatic`）。生产环境让 Nginx 出图片，单进程的 Node 就不会被 23MB 图片拖慢。

## 3. 一条铁律：业务进程只能有一个

这一章请务必看完。违反了不会立刻报错，而是**过几天才发现数据不对**，那是最难查的一类故障。

### 3.1 为什么

代码里有三处状态只活在**进程内存**里：

| 状态 | 在哪 | 起两个进程会怎样 |
|---|---|---|
| 数据内存镜像 | `lib/store.js` 的 `db` 变量 | A 进程改了库存，B 进程的内存还是旧的；B 一保存，把 A 的订单覆盖掉 |
| 限流令牌桶 | `lib/http.js` 的 `buckets` | 限流上限凭空翻倍，等于没限流 |
| 会话表 | `db.sessions`（有落盘，但读的是内存镜像） | 刚登录的令牌在另一个进程里不存在，表现为「时好时坏地掉登录」 |

数据文件本身是安全的：写操作走「临时文件 + rename」原子替换，不会写出半个 JSON。但**两个进程各自持有一份完整快照**这件事，原子写救不了——后写的那个赢，先写的那些订单就没了。

### 3.2 所以不要做这些事

| ❌ 别做 | 为什么 | ✅ 该做 |
|---|---|---|
| `pm2 start app/server/index.js -i max` | 集群模式 = 多进程 | `pm2 start app/server/index.js -i 1`（或直接用 systemd） |
| `docker compose up --scale tideglass=3` | 多副本 | `deploy.replicas: 1`（compose 文件里已固定） |
| 前面挂个负载均衡到两台机器 | 两个独立数据文件 | 单机 + 定时备份；要扩容先换 PostgreSQL |
| 一边跑 systemd 一边手动 `node index.js` | 两进程抢同一个 db.json | 只留 systemd 那一个 |

### 3.3 什么时候可以多实例

等订单量真的上来（日均几百单以上），按这个顺序改，改完才有多实例的资格：

1. 存储换 PostgreSQL（`lib/store.js` 是唯一入口，接口签名不用动，见 SDD 4.4）
2. 限流与会话换 Redis
3. 静态文件上对象存储 + CDN
4. 这时才谈得上 Nginx 后面挂多个 Node

在那之前，2 核 2G 单进程撑日均几百单完全够——接口全是内存读，单请求通常 1~3ms。

## 4. 服务器选型

### 4.1 规格

| 项目 | 最低 | 建议 | 说明 |
|---|---|---|---|
| CPU | 1 核 | 2 核 | Node 单进程，但 Nginx + 系统也要吃 |
| 内存 | 1 GB | 2 GB | Node 常驻约 60~90 MB，剩下给系统与构建缓存 |
| 磁盘 | 20 GB SSD | 40 GB SSD | 代码 + 图片约 120 MB，余量给日志与备份 |
| 带宽 | 3 Mbps | 5 Mbps 或按流量 | 首屏含图片约 1.2 MB，商品图建议后续上 CDN |
| 系统 | Ubuntu 22.04 | **Ubuntu 24.04 LTS** | 本手册命令在两个版本都验过 |
| 地域 | — | 美西 | 贴近主力客群 |

### 4.2 常见供应商对照（价格随活动变动，仅作量级参考）

| 供应商 | 入门配置 | 月费量级 | 适合 |
|---|---|---|---|
| Vultr / DigitalOcean / Linode | 1C1G ~ 2C2G | $6~$12 | 最省心，按小时计费，随时换 |
| 阿里云 / 腾讯云 轻量应用服务器 | 2C2G | ¥60~¥100 | 国内控制台熟悉，但大陆节点要备案 |
| Hetzner | 2C2G | €4~€5 | 便宜，机房在欧美 |

### 4.3 系统初始化（可选但建议）

```bash
# 时区设成 UTC —— 全站时间戳都是 ISO/UTC，服务器本地时区不一致会让日志对不上
sudo timedatectl set-timezone UTC
timedatectl                # 确认 Time zone: UTC

# 顺手把系统补到最新
sudo apt update && sudo apt -y upgrade
```

## 5. 路径 A：全自动部署（推荐）

### 5.1 先确认代码在 GitHub 上

本地（你的电脑）执行：

```bash
cd D:/桔子/wildkind
git log --oneline -1                 # 有提交记录
git remote -v                        # origin 指向 github.com/jiaminfu/wildkind
```

如果还没推到 GitHub，先做这一步（仓库名可自定，本手册以 `wildkind` 为例）：

```bash
# 在 github.com 上新建空仓库（不要勾 README / .gitignore），然后：
git remote add origin https://github.com/jiaminfu/wildkind.git
git branch -M main
git push -u origin main
```

> 私有仓库也没问题，但服务器上 `git clone` 需要凭据。两种做法：
> **①** 仓库设为 Public（代码本身不含任何密钥，`.gitignore` 已排除 `.env` 与 `db.json`）；
> **②** 保持 Private，在服务器上生成 SSH key 并加到 GitHub 的 Deploy keys（只读权限）：
> ```bash
> ssh-keygen -t ed25519 -C "tideglass-server" -f ~/.ssh/id_ed25519 -N ""
> cat ~/.ssh/id_ed25519.pub          # 贴到 仓库 → Settings → Deploy keys（不勾写权限）
> ssh -T git@github.com              # 看到 "successfully authenticated" 即可
> ```
> 之后仓库地址用 `git@github.com:jiaminfu/wildkind.git`。

### 5.2 域名解析

在域名商后台加一条 A 记录：

| 类型 | 主机记录 | 值 | TTL |
|---|---|---|---|
| A | `shop`（或 `@` 表示主域） | 你的服务器公网 IP | 600 |

生效检查（在你电脑上跑，不是在服务器上）：

```bash
nslookup shop.tideglass.com 8.8.8.8
# 或
dig +short shop.tideglass.com
```

必须返回你的服务器 IP 才能签 HTTPS 证书。一般 1~10 分钟，慢的等半小时。

### 5.3 跑部署脚本

SSH 登进服务器，用 root：

```bash
# 1. 放代码
mkdir -p /opt/tideglass
git clone https://github.com/jiaminfu/wildkind.git /opt/tideglass/current

# 2. 一条命令部署
bash /opt/tideglass/current/deploy/install.sh \
     shop.tideglass.com \
     https://github.com/jiaminfu/wildkind.git \
     you@mail.com
```

三个参数：**域名**、**仓库地址**、**邮箱**（邮箱只用于签证书，可以不填，之后手动签）。

脚本会依次做 12 件事，每步都有 `==>` 输出：

| 步骤 | 做什么 | 万一失败看哪儿 |
|---|---|---|
| 1 | 装 curl/git/nginx/ufw | `apt` 报错 → 换软件源或检查网络 |
| 2 | 装 Node.js 22（已有 ≥18 就跳过） | `nodesource` 拉不到 → 见 12.1 |
| 3 | 建系统用户 `tideglass`（无登录 shell） | — |
| 4 | 拉代码到 `/opt/tideglass/current` | 私有仓库 → 见 5.1 的 SSH key |
| 5 | 生成 `/etc/tideglass/tideglass.env` 与**随机口令** | — |
| 6 | 修权限（数据目录 750，只给业务用户） | — |
| 7 | 首次初始化数据（**已有 db.json 就跳过**） | 见 12.2 |
| 8 | 装 systemd 服务并启动 | `journalctl -u tideglass-api -n 50` |
| 9 | 配 Nginx 并 reload | `nginx -t` 的输出 |
| 10 | 防火墙：放行 22/80/443，封 4600 | — |
| 11 | certbot 签证书 + 自动续期 | 见 12.6 |
| 12 | 自检：`/api/v1/health` + 首页状态码 | — |

### 5.4 跑完你会看到什么

```
============================================
 部署完成
============================================
  前台   https://shop.tideglass.com/
  后台   https://shop.tideglass.com/#/admin
  健康   https://shop.tideglass.com/api/v1/health
...
```

以及一段被框起来的**随机口令**（只在首次生成时打印一次，务必存到密码管理器）：

```
    ┌──────────────────────────────────────────────
    │ 后台地址： https://shop.tideglass.com/#/admin
    │ 老板账号： owner@tideglassjewelry.com
    │ 密码　　： xxxxxxxxxxxxxxxxxxxx
    │ 运营账号： ops@tideglassjewelry.com
    │ 密码　　： yyyyyyyyyyyyyyyyyyyy
    └──────────────────────────────────────────────
```

> 口令同时写在 `/etc/tideglass/tideglass.env`（root 可读），忘了可以 `sudo cat` 取。**登录后请改掉，见 9.5。**

### 5.5 验证

在服务器上：

```bash
curl -s http://127.0.0.1:4600/api/v1/health
# {"data":{"status":"ok","version":"1.0.0","products":36,"orders":90,"time":"..."}}

curl -sI https://shop.tideglass.com/ | head -5
# HTTP/2 200
```

在你电脑浏览器打开 `https://你的域名/`，应该看到前台首页；`/#/admin` 是后台登录页。

## 6. 路径 B：手动部署（逐步）

不跑脚本、每条命令自己敲。和路径 A 结果一致。

### 6.1 基础环境

```bash
sudo apt update
sudo apt install -y curl ca-certificates git nginx ufw openssl
sudo timedatectl set-timezone UTC
```

### 6.2 安装 Node.js

```bash
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo bash -
sudo apt install -y nodejs
node -v      # 期望 v22.x
```

只有 Node ≥ 18 就行（代码用了 `node:` 前缀模块与全局 `WebSocket`，18 起都有）。

> 不建议用 `nvm`：systemd 里 `ExecStart` 要写绝对路径，nvm 的路径带版本号，升级 Node 时服务会莫名起不来。

### 6.3 建用户、放代码

```bash
sudo adduser --system --group --home /opt/tideglass --shell /usr/sbin/nologin tideglass

sudo mkdir -p /opt/tideglass
sudo git clone https://github.com/jiaminfu/wildkind.git /opt/tideglass/current
sudo chown -R tideglass:tideglass /opt/tideglass/current
sudo chmod -R a+rX /opt/tideglass/current/app/web     # Nginx 要能读静态文件
```

**为什么不用 root 跑**：Node 进程只需要写 `app/server/data/` 一个目录。用 root 跑，一旦有路径穿越或依赖漏洞，整台机器都交出去了。

### 6.4 环境变量

```bash
sudo mkdir -p /etc/tideglass
sudo install -m 640 -o root -g tideglass \
     /opt/tideglass/current/deploy/.env.example \
     /etc/tideglass/tideglass.env
sudo nano /etc/tideglass/tideglass.env
```

要改的只有三行：

| 变量 | 改成 | 说明 |
|---|---|---|
| `ADMIN_PASSWORD` | 你自己的强口令 | **只在首次 seed 时生效** |
| `OPS_PASSWORD` | 另一个强口令 | 运营账号，权限较少 |
| `CORS_ORIGIN` | `https://你的域名` | 同域部署其实可以留 `*`，但写死更稳 |

`ALLOW_TEST_RESET` **保持注释状态**。这一行一旦打开，任何人 `curl -X POST /api/v1/__test/reset` 就能把线上数据清回演示状态——脚本里这条路由只有在这个变量为 `1` 时才注册，不设它等于这条路不存在。

> **重要**：`ADMIN_PASSWORD` 只影响「生成数据」那一刻。数据里存的是 `scrypt` 哈希，事后改环境变量不会改密码。要换密码走 9.5。

### 6.5 初始化数据

```bash
cd /opt/tideglass/current
sudo -u tideglass env \
  ADMIN_PASSWORD='你的强口令' \
  OPS_PASSWORD='另一个强口令' \
  HOME=/opt/tideglass \
  node app/server/seed.js
```

会生成两个文件：

| 文件 | 是什么 | 能不能删 |
|---|---|---|
| `app/server/data/db.json` | 线上真实数据 | **绝对不能删**，删了商品订单全没 |
| `app/server/data/db.seed.json` | 基线快照，只给自动化测试复位用 | 可删，测试前再跑一次 seed 即可 |

首次数据规模：36 个商品 / 67 个 SKU / 45 个集合 / 90 张订单 / 56 个客户 / 4 张券 / 59 条评价 / 200 条库存流水。

> `seed.js` 从 `prototype/assets/js/data.js` 读种子数据，所以 `prototype/` 目录不能从仓库里删。它同时也是早期设计原型，留着当参考。

### 6.6 systemd 服务

```bash
NODE_BIN="$(command -v node)"

sudo sed -e "s#/usr/bin/node#$NODE_BIN#" \
         /opt/tideglass/current/deploy/tideglass-api.service \
    | sudo tee /etc/systemd/system/tideglass-api.service >/dev/null

sudo systemctl daemon-reload
sudo systemctl enable tideglass-api
sudo systemctl start tideglass-api

sudo systemctl status tideglass-api --no-pager
sudo journalctl -u tideglass-api -n 20 --no-pager
```

启动成功的日志长这样：

```
TIDEGLASS API 已启动 → http://localhost:4600
  数据：/opt/tideglass/current/app/server/data/db.json（商品 36 / 订单 90）
  前台：http://localhost:4600/   后台：http://localhost:4600/#/admin
  健康检查：GET /api/v1/health
```

服务单元里值得注意的三处：

| 配置 | 作用 |
|---|---|
| `EnvironmentFile=/etc/tideglass/tideglass.env` | 变量只有 root 能改，代码里读不到文件系统 |
| `ProtectSystem=strict` + `ReadWritePaths=…/data` | 整个磁盘对进程只读，唯一能写的就是数据目录 |
| `Restart=always` / `RestartSec=3` | 进程崩了 3 秒后自动拉起（`uncaughtException` 已兜住，正常不会崩） |

### 6.7 Nginx

```bash
sudo mkdir -p /var/www/certbot
sudo sed 's/__DOMAIN__/shop.tideglass.com/g' \
     /opt/tideglass/current/deploy/nginx-tideglass.conf \
  | sudo tee /etc/nginx/sites-available/tideglass.conf >/dev/null

sudo ln -sf /etc/nginx/sites-available/tideglass.conf /etc/nginx/sites-enabled/tideglass.conf
sudo rm -f /etc/nginx/sites-enabled/default     # 去掉默认站点，否则会抢 80

sudo nginx -t          # 必须 syntax is ok / test is successful
sudo systemctl reload nginx
```

几个容易踩的点：

| 现象 | 原因 |
|---|---|
| 打开域名看到 Nginx 欢迎页 | `sites-enabled/default` 没删，它先匹配上了 |
| 接口 502 | Nginx 起来了但 Node 没起来，`systemctl status tideglass-api` |
| 页面白屏、控制台 404 | `root` 指向错，必须是 `…/app/web`（含 `index.html` 那一层） |
| 登录后一直 429 | 少了 `X-Forwarded-For`，全站挤在同一个 IP 桶里（配置里已带） |

### 6.8 HTTPS

```bash
sudo apt install -y certbot python3-certbot-nginx
sudo certbot --nginx -d shop.tideglass.com -m you@mail.com --agree-tos --redirect
```

`--redirect` 会顺手加一个 80→443 的跳转。certbot 直接在**原地**改你的 server 块（加 `listen 443 ssl` 与证书路径），不会新建一份配置，所以 6.7 写的 location、安全头、gzip 全部保留。

检查续期：

```bash
sudo certbot renew --dry-run
systemctl list-timers | grep certbot     # 应该有 certbot.timer
```

> **为什么必须上 HTTPS**：后台登录是 `Authorization: Bearer`，走 HTTP 等于口令在公网上明文裸奔；将来接 Stripe，支付组件也强制要求 HTTPS。

### 6.9 防火墙

```bash
sudo ufw allow OpenSSH
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw deny 4600/tcp          # 业务端口只给本机 Nginx
sudo ufw enable
sudo ufw status verbose
```

⚠️ **如果你的 SSH 不是 22 端口**，先 `sudo ufw allow <你的端口>/tcp` 再 `enable`，否则会把自己锁在门外。

云厂商控制台里还有一层「安全组」，两边都要放行 80/443、都要封 4600。

### 6.10 自检

```bash
curl -s http://127.0.0.1:4600/api/v1/health
curl -sI -H "Host: shop.tideglass.com" http://127.0.0.1/ | head -3
curl -sI https://shop.tideglass.com/ | head -3
```

三条都通就部署完成，接着进第 7 章。

## 9. 日常运维

### 9.1 更新发布

```bash
sudo bash /opt/tideglass/current/deploy/update.sh
```

脚本顺序是刻意的：**先备份 → 再拉代码 → 再重启 → 再探活**。顺序反过来的话，新代码起不来时你既没有干净备份，也不知道旧版本是哪个 commit。

输出会打印旧/新 commit 和回滚命令。

### 9.2 手动更新（不想用脚本时）

```bash
cd /opt/tideglass/current
sudo bash deploy/backup.sh                 # 1. 备份
sudo git fetch --depth 1 origin main
sudo git reset --hard origin/main          # 2. 拉代码
sudo chown -R tideglass:tideglass .
sudo chmod -R a+rX app/web
sudo systemctl restart tideglass-api       # 3. 重启
curl -s http://127.0.0.1:4600/api/v1/health # 4. 探活
```

> 用 `git reset --hard` 而不是 `git pull`：服务器上不该有本地修改，`reset` 能保证和远端一字不差。

### 9.3 回滚

```bash
cd /opt/tideglass/current
sudo git log --oneline -5                   # 找到要回的那个 commit
sudo git reset --hard <commit>
sudo systemctl restart tideglass-api
```

如果新版本动了数据格式，还要配 `deploy/backup.sh --restore` 回到对应时刻的数据（10.4）。

### 9.4 看日志

```bash
sudo journalctl -u tideglass-api -f              # 实时跟
sudo journalctl -u tideglass-api --since "1 hour ago"
sudo journalctl -u tideglass-api -p err          # 只看错误

sudo tail -f /var/log/nginx/tideglass.access.log
sudo tail -f /var/log/nginx/tideglass.error.log
```

接口日志是每请求一行，长这样：`GET    /api/v1/health → 200 (1ms)`。慢请求（>200ms）说明有异常，正常都在个位数毫秒。

日志不会无限长——systemd 自带 journal 轮转，Nginx 的用 logrotate（已默认配好）。想限制 journal 占用：

```bash
sudo nano /etc/systemd/journald.conf     # SystemMaxUse=500M
sudo systemctl restart systemd-journald
```

### 9.5 改后台密码（正确做法）

密码以 `scrypt` 哈希存在 `db.json` 的 `staff` 数组里，**改环境变量无效**。两种做法：

**做法一（推荐）：直接改数据文件**

```bash
sudo systemctl stop tideglass-api

cd /opt/tideglass/current
sudo -u tideglass node -e "
const fs=require('fs'), auth=require('./app/server/lib/auth');
const f='app/server/data/db.json';
const db=JSON.parse(fs.readFileSync(f,'utf8'));
const p=auth.hashPassword(process.argv[1]);
const s=db.staff.find(x=>x.email==='owner@tideglassjewelry.com');
s.salt=p.salt; s.hash=p.hash;
fs.writeFileSync(f, JSON.stringify(db,null,1));
db.sessions=[];                       // 顺手踢掉所有旧会话
fs.writeFileSync(f, JSON.stringify(db,null,1));
console.log('已更新，旧会话已全部失效');
" '你的新口令'

sudo systemctl start tideglass-api
```

> 先停服务再改文件，是因为进程内存里还有一份镜像，运行中改文件会被下一次写操作覆盖。

**做法二：重建数据（会丢业务数据，只适合刚部署还没真实订单）**

```bash
sudo systemctl stop tideglass-api
cd /opt/tideglass/current
sudo -u tideglass env ADMIN_PASSWORD='新口令' OPS_PASSWORD='运营口令' \
  HOME=/opt/tideglass node app/server/seed.js
sudo systemctl start tideglass-api
```

### 9.6 改端口 / 改域名

- **改端口**：改 `/etc/tideglass/tideglass.env` 的 `PORT`，同步改 Nginx `proxy_pass`，`systemctl restart` + `nginx -s reload`。
- **改域名**：Nginx 配置里 `server_name` 与 `root` 不用动，改 `sed` 替换过的域名；重新签证书；`CORS_ORIGIN` 跟着改；DNS 加新记录。

## 10. 备份与恢复

`db.json` 就是全部生意：商品、订单、客户、券、库存流水、账号口令哈希都在这一个文件里。**没有第二个地方能恢复它。**

### 10.1 手动备份

```bash
sudo bash /opt/tideglass/current/deploy/backup.sh
```

做了什么：

1. 复制 `db.json` 到 `/var/backups/tideglass/db-20261113-101500.json`
2. **用 `JSON.parse` 校验**——解析不了就当场删掉这份备份并报错，避免留下"看起来存在但是坏的"文件
3. gzip 压缩（约 220 KB → 30 KB）
4. 只保留最近 30 份（`BACKUP_KEEP` 可改）
5. 若配了 `RCLONE_REMOTE`，顺手同步到对象存储

### 10.2 定时备份（必做）

```bash
sudo crontab -e
```

加两行：

```cron
# 每 6 小时备份一次；日志留在 /var/log/tideglass-backup.log
0 */6 * * * /bin/bash /opt/tideglass/current/deploy/backup.sh >> /var/log/tideglass-backup.log 2>&1
# 每天 04:10 把备份同步到异地（需要先配 rclone）
10 4 * * * RCLONE_REMOTE=oss:tideglass-backup /bin/bash /opt/tideglass/current/deploy/backup.sh >> /var/log/tideglass-backup.log 2>&1
```

> 备份留在同一台机器上只防「误删/误改」，不防「整机挂掉」。真要防后者，用 `rclone` 推到对象存储（阿里云 OSS / 腾讯云 COS / Backblaze B2 都可），`deploy/backup.sh` 已支持 `RCLONE_REMOTE`。

### 10.3 看有哪些备份

```bash
sudo bash /opt/tideglass/current/deploy/backup.sh --list
```

### 10.4 恢复（每季度演练一次）

```bash
sudo bash /opt/tideglass/current/deploy/backup.sh --restore /var/backups/tideglass/db-20261113-101500.json.gz
```

脚本会：

1. 解压并解析校验，坏文件直接拒绝覆盖
2. 打印这份备份里有几个商品/订单/客户，让你确认是不是想恢复的那一份
3. 要你输入 `y` 二次确认
4. 把**当前**数据先另存一份 `before-restore-*.json`（恢复错了还能退回来）
5. 停服务 → 覆盖 → 起服务 → 检查进程活着

**演练方法**（建议部署完就做一次，5 分钟）：

```bash
# 1. 造一个可见的变化：后台随便改一个商品价格
# 2. 备份
sudo bash deploy/backup.sh
# 3. 再改一次价格（改成明显不同的值）
# 4. 恢复刚才的备份
sudo bash deploy/backup.sh --restore /var/backups/tideglass/db-最新那份.json.gz
# 5. 刷新前台商品页 —— 价格应该回到第 2 步的状态
```

价格回退了，说明备份链路是通的。没回退，说明你备份的是错的文件或者服务没读到新数据，趁现在还有时间查。

### 10.5 迁移到新服务器

```bash
# 旧机
sudo bash deploy/backup.sh
scp /var/backups/tideglass/db-最新.json.gz root@新机:/tmp/

# 新机：按第 5 或第 6 章装完，先不要 seed，直接放数据
sudo mkdir -p /opt/tideglass/current/app/server/data
sudo install -m 640 -o tideglass -g tideglass \
     <(gzip -dc /tmp/db-最新.json.gz) /opt/tideglass/current/app/server/data/db.json
sudo systemctl start tideglass-api
```

DNS 切过来之前，建议先改本机 hosts 验证一遍。

## 11. 路径 C：Docker 部署

适合服务器上已经有别的东西、不想被 Node 版本牵连的情况。

### 11.1 准备

```bash
# 装 Docker（官方脚本，会装 docker + compose 插件）
curl -fsSL https://get.docker.com | sudo sh
sudo systemctl enable --now docker
```

### 11.2 起服务

```bash
cd /opt/tideglass/current/deploy
sudo cp .env.example .env
sudo nano .env                  # 改掉两个 CHANGE_ME，CORS_ORIGIN 写你的域名

sudo docker compose up -d --build
```

### 11.3 容器方案的关键点

| 关注点 | 怎么处理的 |
|---|---|
| 数据持久化 | 具名卷 `tideglass-data` 挂在 `/app/app/server/data`，容器重建不丢数据 |
| 首次初始化 | `docker-entrypoint.sh` 只在 `db.json` 不存在时 seed，**不会覆盖已有数据** |
| 端口暴露 | 只绑 `127.0.0.1:4600`，外网仍走宿主机 Nginx |
| 健康检查 | `HEALTHCHECK` 打 `/api/v1/health`，编排层能看出"活着但接口坏了" |
| 单实例 | `deploy.replicas: 1`（原因见第 3 章） |
| 镜像体积 | 约 130 MB，没有 `npm install`，因为零依赖 |

### 11.4 容器下的常用命令

```bash
sudo docker compose ps
sudo docker compose logs -f --tail=100
sudo docker compose restart
sudo docker compose down            # 停止并删容器，卷保留
sudo docker compose up -d --build   # 更新代码后重建

# 备份（在宿主机跑，卷里的数据可以用 docker cp 取出来）
sudo docker cp tideglass:/app/app/server/data/db.json /tmp/db-$(date +%F).json
```

Nginx 仍按 6.7 / 6.8 配，`root` 指向宿主机上的 `…/app/web`（镜像里也有一份，但静态文件走宿主机更快）。

> 容器方案下 `deploy/install.sh` 不适用（它装 systemd 服务）。二者选一。

## 12. 故障排查

按现象查表。每条都给了判定命令，先确认再动手。

### 12.1 `apt` 装 Node 卡住 / 403

国内服务器访问 `deb.nodesource.com` 可能被限速。

```bash
# 换国内源装 Node 22
curl -fsSL https://mirrors.tuna.tsinghua.edu.cn/nodesource/deb_22.x/dists/nodistro/InRelease | head -1
# 或直接用 NodeSource 官方二进制包
```

实在不行用官方二进制：

```bash
cd /usr/local
sudo curl -fsSLO https://nodejs.org/dist/v22.11.0/node-v22.11.0-linux-x64.tar.xz
sudo tar -xJf node-v22.11.0-linux-x64.tar.xz
sudo ln -sf /usr/local/node-v22.11.0-linux-x64/bin/node /usr/local/bin/node
sudo ln -sf /usr/local/node-v22.11.0-linux-x64/bin/npm  /usr/local/bin/npm
node -v
```

### 12.2 服务起不来，日志报 `ENOENT … db.json`

数据没初始化。

```bash
cd /opt/tideglass/current
sudo -u tideglass env ADMIN_PASSWORD='x' OPS_PASSWORD='y' HOME=/opt/tideglass node app/server/seed.js
sudo systemctl restart tideglass-api
```

> `store.load()` 在启动时直接读文件，文件不存在就抛错退出——这是刻意的，宁可起不来也不要带着空数据跑。

### 12.3 打开域名是 Nginx 欢迎页

```bash
ls /etc/nginx/sites-enabled/
sudo rm -f /etc/nginx/sites-enabled/default
sudo nginx -t && sudo systemctl reload nginx
```

### 12.4 接口 502 Bad Gateway

Nginx 活着，Node 死了。

```bash
sudo systemctl status tideglass-api --no-pager
sudo journalctl -u tideglass-api -n 50 --no-pager
```

常见原因：`db.json` 权限不对（应 `tideglass:tideglass 640`）、`ProtectSystem` 挡住了写、端口被占（`sudo ss -lntp | grep 4600`）。

### 12.5 页面白屏 / 静态资源 404

```bash
ls /opt/tideglass/current/app/web/index.html          # 文件在不在
sudo -u tideglass test -r /opt/tideglass/current/app/web/index.html && echo readable
grep -n "root " /etc/nginx/sites-available/tideglass.conf
```

`root` 必须是 `…/current/app/web`（`index.html` 的父目录）。权限上 Nginx（`www-data`）要能读到，`chmod -R a+rX app/web` 解决。

### 12.6 证书签不下来

| 报错 | 原因 |
|---|---|
| `DNS problem: NXDOMAIN` | A 记录没生效或写错，`dig +short 域名` 确认 |
| `Timeout during connect` | 80 端口没放行（ufw 或云安全组） |
| `too many certificates already issued` | 短时间签太多次，等 1 小时 |
| `Could not bind to IPv4` | Nginx 没起来，先 `systemctl start nginx` |

Let's Encrypt 有效期 90 天，certbot 自动续。别用自签证书——Stripe 会拒。

### 12.7 登录后过一会儿又掉登录 / 点菜单就退出

两种情况：

1. **改了 `ADMIN_PASSWORD` 但没重启**，或数据被 seed 覆盖 → 重新登录即可，属预期。
2. **历史缺陷（已修）**：早期测试复位接口会把 `db.sessions` 一起回滚，导致所有令牌失效；前端又静默删掉令牌，表现就是「点一下就退出」。现在复位只还原业务数据、保留会话，且 401 会在登录页显示提示。若仍遇到，检查是不是同时跑了两个 Node 进程（12.11）。

### 12.8 下单报 429 `RATE_LIMITED`

限流是「按 IP + 路由」的令牌桶：

| 路由 | 上限 |
|---|---|
| 报价 `/checkout/quote` | 60 次 / 分钟 |
| 下单 `/checkout/orders` | 20 次 / 分钟 |
| 查单 `/orders/lookup` | 30 次 / 分钟 |
| 登录 `/admin/login` | 10 次 / 5 分钟 |
| 定制需求单 `/custom-requests` | 6 次 / 10 分钟 |

如果**所有用户同时**被限，几乎一定是 Nginx 没传 `X-Forwarded-For`，所有人挤在 `127.0.0.1` 一个桶里。检查 `location /api/` 里有没有 `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;`。

单用户偶发 429 属正常保护，等一分钟即可（响应里的 `details.retryAfter` 是秒数）。

### 12.9 提交报 413 `PAYLOAD_TOO_LARGE`

接口上限 256 KB（`lib/http.js` 的 `MAX_BODY`），Nginx 也设了 `client_max_body_size 256k`。当前所有请求体都远小于此——**如果触发了，说明有异常请求**，先看 Nginx access log 的请求路径，别急着调大。

### 12.10 图片 403 / 打不开

```bash
sudo -u www-data test -r /opt/tideglass/current/app/web/assets/img/xxx.png && echo ok
sudo namei -l /opt/tideglass/current/app/web/assets/img
```

`/opt/tideglass` 与 `/opt/tideglass/current` 都必须对 other 有 `x` 权限（`chmod 755`），否则 Nginx 进不去。

### 12.11 数据莫名其妙回退 / 订单少了

**十有八九是两个进程在写同一个 `db.json`。**

```bash
ps aux | grep -c "[n]ode app/server"
sudo ss -lntp | grep 4600
```

只能有一个。停掉多余的那个（通常是不小心手动跑的 `node app/server/index.js`），然后从备份恢复最近数据（10.4）。

### 12.12 时间显示差 8 小时

服务器时区不是 UTC，或浏览器按本地时区渲染。全站时间戳都是 ISO/UTC，展示层转本地时区是正常的。若后台列表时间整体偏移：

```bash
timedatectl                       # 应为 UTC
sudo systemctl restart tideglass-api
```

### 12.13 改了代码但页面没变

```bash
sudo systemctl restart tideglass-api     # 后端
# 前端是静态文件，浏览器缓存最顽固
```

`index.html` 已设 `no-cache`，但 JS/CSS 有 `max-age`，强刷 `Ctrl+Shift+R`（Mac 是 `Cmd+Shift+R`）。真要彻底，发版时给静态资源加版本号。

## 附录 B · 部署时最容易犯的五个错

1. **改了 `ADMIN_PASSWORD` 但数据已存在** —— 密码没变，你以为变了。正确做法见 9.5。
2. **用 `pm2 -i max` 或 compose 多副本** —— 两个进程互覆盖数据，几天后才发现订单少了。见第 3 章。
3. **备份从来没恢复过** —— 需要它的那天才发现文件是坏的。见 10.4，季度演练一次。
4. **忘了删 `sites-enabled/default`** —— 域名打开是 Nginx 欢迎页，然后开始怀疑代码。
5. **把 4600 直接开到公网** —— 绕过 HTTPS、绕过限流，后台口令明文传输。
