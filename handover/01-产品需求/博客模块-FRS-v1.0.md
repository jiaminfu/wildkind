**为什么必须先拍板 Q-01**：本站是纯 hash SPA，`/#/pages/journal` **不会被搜索引擎当作独立 URL**。也就是说，按原来的路由形态做博客，文章写 100 篇，Google 收录量是 **0** —— 而做博客的主要目的就是 SEO。这不是实现细节问题，是"做出来有没有用"的问题。

| 方案 | 做法 | 工作量 | SEO 收益 | 结论 |
| --- | --- | --- | --- | --- |
| A | 沿用 hash，只在 SPA 里加列表与详情 | 0.5 天 | ≈ 0 | ❌ 等于白写 |
| **B** | **只给博客开真路径** `/journal` 与 `/journal/<slug>`，服务端预渲染 meta；其余仍走 hash | **约 1 天** | 可被收录 | ✅ **已采用** |
| C | 全站迁 history 路由 | 3–4 天 | 全站收益 | ❌ 改动面大，回归成本高 |

B 方案的三个实现难点（真路径与 hash 如何共存、正文由谁渲染、爬虫看到的 HTML 里有什么）已在 SDS §2 / §5 / §6 给出答案。

## 0 先说结论：现状与差距

「前端有博客内容」这句话只对了一半。核查结果：

| 事项 | 现状 | 结论 |
|---|---|---|
| 前台入口 | 页脚 `Field Notes` → `#/pages/journal` | 有，但藏在页脚第三列，顶栏无入口 |
| 页面形态 | 3 篇文章（标题 + 假日期 + 一段正文）**全部写死在 `app/web/assets/js/pages.js`** | 不是博客，是一篇固定的长页面 |
| 后台编辑 | `/admin/content` 只能改这个页面的 **title + intro 两行字** | ❌ 无文章编辑窗口 |
| 文章数据 | `db.json` 无 `posts` 表 | ❌ 无数据结构 |
| 列表 / 详情分离 | 无，三篇挤在同一页 | ❌ |
| 封面图 / 草稿 / 发布时间 / 标签 | 无 | ❌ |

| 能被搜索引擎索引 | **不能**。SPA 用 hash 路由，`sitemap.xml` 里给的 `/#/pages/journal` 中 `#` 之后不被当作独立 URL | ❌ SEO 收益为零 |

**最关键的一条**：博客对 DTC 独立站的价值 90% 在自然搜索流量。当前 hash 路由的架构下，就算把编辑器做出来，写 50 篇文章也不会被 Google 正常收录。这个架构决策必须在动手前定下来（见第 9 节待确认问题 Q-01）。

## 1 背景与目标

### 1.1 背景

LASTGROVE 是 316L 不锈钢饰品 DTC 独立站，主力市场美国。付费流量成本持续上涨，内容营销是唯一不随投放预算线性涨价获客渠道。此外还有三个现实用途：

1. **承接信任**：$35–$85 的饰品，客户在付款前会搜「不锈钢饰品会不会掉色」「PVD 和电镀什么区别」。站内有一篇讲清楚的文章，比首页文案有效得多。
2. **承接合规叙事**：材质、产地、1% 捐赠这些说法需要落脚点，否则只是 slogan。
3. **承接邮件与社媒**：newsletter 和 Instagram 的流量需要一个能反复利用的落地页。

### 1.2 目标（可度量）

| 编号 | 目标 | 度量方式 |
|---|---|---|
| G-1 | 运营能独立发文章，不需要开发介入 | 从「想发一篇文章」到「线上可见」全程无代码改动、无重新部署 |
| G-2 | 文章能被搜索引擎收录 | 文章 URL 在 site: 查询中可被检索；Search Console 显示已编入索引 |
| G-3 | 发一篇文章的操作时长 | ≤ 10 分钟（含配图），不需要读文档 |
| G-4 | 不为博客引入第三方依赖 | 构建后仍为零运行时依赖，CSP 不需要放宽 |

### 1.3 非目标（本期不做）

- ❌ 评论 / 用户投稿
- ❌ 富文本所见即所得编辑器（做不出好用的，且引入依赖）
- ❌ 定时发布（到点自动上线）
- ❌ 多作者署名体系（单店单人运营，作者字段默认为店铺）
- ❌ 相关文章推荐算法（先手动指定）
- ❌ RSS / AMP

## 2 名词定义

| 术语 | 含义 |
|---|---|
| 文章（Post） | 一条博客内容，有 slug、标题、正文、状态 |
| slug | 文章的 URL 标识，如 `why-pvd-is-not-plating`，一经发布不建议修改 |
| 草稿（draft） | 已保存但前台不可见、不进 sitemap |
| 已发布（published） | 前台可见、进 sitemap、进列表 |
| 栏目（section） | 文章的一级归类，如 Materials / Studio / Giving |
| 正文块（block） | 文章正文由有序块组成，而非一坨 HTML |

## 4 功能需求

编号规则：`FR-B-<三位序号>`。优先级：🔴 必须有 / 🟡 应该有 / 🟢 可以有。

### 4.1 文章数据与状态

**FR-B-001** 🔴 系统应保存文章实体，字段至少包含：`id`、`slug`、`title`、`excerpt`（列表摘要）、`coverImage`、`coverAlt`、`section`、`blocks`（正文）、`status`、`publishedAt`、`updatedAt`、`seoTitle`、`seoDescription`。

**FR-B-002** 🔴 当创建文章时，如果未填写 slug，系统应根据 title 自动生成 slug（小写、连字符、去符号），并保证全站唯一。

**FR-B-003** 🔴 当提交的 slug 与既有文章重复时，系统应拒绝保存并提示「This slug is already used」。

**FR-B-004** 🔴 系统应支持两种状态：`draft`（草稿）、`published`（已发布）。新建文章默认 `draft`。

**FR-B-005** 🔴 当文章状态从 `draft` 变为 `published` 时，如果 `publishedAt` 为空，系统应写入当前时间。

**FR-B-006** 🔴 如果文章状态为 `draft`，则前台列表、详情、sitemap 均不得出现该文章；直接访问其 URL 应返回 404。

**FR-B-007** 🟡 当文章已经是 `published` 时，系统应允许改回 `draft`（下架），下架后前台立即不可见。

**FR-B-008** 🟡 系统应保留文章的 `updatedAt`，并在详情页展示「Last updated」——但仅当它与 `publishedAt` 相差超过 24 小时时展示，避免「刚发布就显示已更新」的观感。

**FR-B-009** 🟢 系统应允许删除文章；删除需二次确认，且不可恢复。

### 4.2 正文结构

**FR-B-010** 🔴 正文应支持以下块类型：段落（`p`）、二级标题（`h2`）、三级标题（`h3`）、无序列表（`ul`）、引用（`quote`）、单图（`image`）、图文说明（`figure` + 说明文字）、分隔线（`hr`）。

**FR-B-011** 🔴 段落块内应支持行内格式：粗体、斜体、链接。

**FR-B-012** 🔴 当正文渲染时，系统应对所有用户输入文本做转义，只生成白名单内的标签。**不得**把用户输入当作 HTML 直接插入 DOM。

> 理由：正文是后台可写内容，一旦支持原始 HTML，就等同于把 XSS 入口开在 CMS 里。当前 CSP 虽限制外链脚本，但站内脚本仍是同一源。

**FR-B-013** 🔴 图片块必须包含 `alt` 文本；未填写时后台保存应提示，且不阻断保存（先存后补），但前台渲染 `alt=""`。

**FR-B-014** 🟡 图片上传应复用现有上传通道（6 张 / 5MB / 前端压缩），无需新建存储。

**FR-B-015** 🟡 系统应支持在正文任意块之间插入图片，不限于结尾。

### 4.3 后台管理界面

**FR-B-016** 🔴 后台左侧导航 `GROWTH` 或 `SYSTEM` 分组下应新增「Articles」入口，与现有 Content 并列（Content 继续管页面导语，Articles 管文章）。

**FR-B-017** 🔴 文章列表页应展示：标题、slug、栏目、状态、发布时间、更新时间。支持按状态筛选（All / Published / Draft）。

**FR-B-018** 🔴 文章编辑页应包含：标题、slug（可手改）、摘要、封面图（上传 + 预览）、栏目选择、SEO title / description、正文编辑器、保存草稿、发布 / 下架。

**FR-B-019** 🔴 正文编辑器采用**分块编辑**：每块一个控件（类型下拉 + 内容输入），可上移/下移/删除/在下方插入新块。不提供富文本悬浮工具栏。

**FR-B-020** 🔴 当编辑页有未保存改动时，离开页面前应弹出浏览器原生确认提示。

**FR-B-021** 🟡 编辑页应实时展示字数与预计阅读时长（按 200 词/分钟），作为写作节奏参考。

**FR-B-022** 🟡 保存时应记录审计日志（操作人、动作、文章 id），与现有一致。

**FR-B-023** 🟢 编辑页应提供「预览」——在新标签页打开该文章的前台渲染效果（草稿也可预览，走带临时 token 的预览地址）。

### 4.4 前台列表

**FR-B-024** 🔴 前台应提供文章列表页，展示已发布文章，按 `publishedAt` 倒序。

**FR-B-025** 🔴 列表项应展示：封面图、栏目、标题、摘要、日期。

**FR-B-026** 🔴 当文章总数超过 9 篇时，列表应分页，每页 9 篇。

**FR-B-027** 🟡 列表应支持按栏目筛选（`/journal?section=materials`）。

**FR-B-028** 🟡 顶栏导航应新增「Journal」入口，位置在 Gifts 之后；页脚已有的 `Field Notes` 一并改为指向新列表页。

**FR-B-029** 🟢 列表页顶部应展示一段栏目介绍文案（复用现有 `pages.journal.intro`，仍可在 Content 里改）。

### 4.5 前台详情

**FR-B-030** 🔴 前台应提供文章详情页，按 slug 访问。

**FR-B-031** 🔴 详情页应展示：栏目、标题、发布日期、封面图、正文、文末 CTA（引导去看某个集合或商品）。

**FR-B-032** 🔴 当文章不存在、或状态为草稿时，详情页应返回「文章不存在」页，而不是白屏或首页。

**FR-B-033** 🟡 详情页文末应有「下一篇 / 上一篇」导航。

**FR-B-034** 🟢 详情页应展示预估阅读时长。

### 4.6 搜索可见性（SEO）

**FR-B-035** 🔴 每篇文章必须有唯一的、可被爬虫当作独立 URL 抓取的地址（具体要求见 SDS，取决于 Q-01 决策）。

**FR-B-036** 🔴 每篇文章的 HTML 响应中，`<title>`、`<meta name="description">`、`<link rel="canonical">`、`og:title`、`og:description`、`og:image`、`og:type=article` 应在**服务端返回的 HTML 里就存在**，而不是等 JS 执行完才写入。

> 理由：Google 能执行 JS，但抓取预算有限、社交平台爬虫（Facebook / X / WhatsApp 分享预览）**完全不执行 JS**。分享链接没有 og 图，等于内容营销少了半个传播环。

**FR-B-037** 🔴 文章详情页应输出 `BlogPosting` 结构化数据（JSON-LD）：headline、datePublished、dateModified、image、author、publisher。

**FR-B-038** 🔴 `sitemap.xml` 应包含所有已发布文章的 URL，且 `lastmod` 取 `updatedAt`。

**FR-B-039** 🟡 文章列表页应输出 `Blog` + `ItemList` 结构化数据。

### 4.7 与现有页面体系的关系

**FR-B-040** 🔴 博客上线后，`pages.journal` 不再承载文章正文，只保留「栏目标题 + 导语 + SEO 描述」三项，继续在后台 Content 里可改。

**FR-B-041** 🔴 现有 3 篇写死的文章（Why PVD is not plating / Reading a tide glass / Where the 1% went）应迁移为真实的 3 条文章记录，正文内容保持原文，日期沿用原文标注的日期。

**FR-B-042** 🟡 原有 `#/pages/journal` 地址应重定向到新的列表地址，避免旧链接 404（若该地址已被外部引用）。

## 9 待确认问题（评审时请逐条给结论）

**Q-01（✅ 已定：选 B，2026-11-15）文章 URL 用什么形态？**

| 选项 | 形态 | SEO 效果 | 代价 |
|---|---|---|---|
| A | 沿用 hash：`/#/journal/why-pvd` | ❌ 几乎为零 | 小，纯前端 |
| B | 独立路径：`/journal/why-pvd`，服务端返回预渲染 meta 的 HTML | ✅ 正常收录 | 中，需服务端加路由分支 + meta 注入 + 前端接管渲染，约 1 天 |
| C | 全站迁 history 路由 | ✅ 全站受益 | 大，需重做所有链接、重定向旧 hash 地址，约 3–4 天，风险高 |

**我的建议：选 B。** 只为博客开独立路径，其余保持 hash 不动。这是用最小代价拿到 SEO 收益的做法——商品页以后可以按同一套路逐个迁移。

> **结论（2026-11-15）**：采用 B。设计细节见 `02-系统设计/博客模块-SDS-v1.0.md`，其中 §6.3 明确了一个取舍：博客页内的点击是**整页跳转**（约 200ms），代价是换来"不做 pushState 状态机"。若评审不接受这一点，需追加 1.5 天。

**Q-02 正文字段用哪种输入方式？**

- A：分块编辑（推荐）——每块一个控件，结构清晰、渲染安全、不依赖第三方库
- B：Markdown 文本域 + 自写渲染器——写起来快，但要自己实现渲染器，且运营要学语法
- C：原始 HTML——不推荐，等于开 XSS 入口

**Q-03 栏目先定几个？**
建议 3 个，与现有三篇文章对应：`Materials`（材质）/ `Studio`（幕后）/ `Giving`（1% 去哪了）。后续可在后台增删。

**Q-04 文章是否需要「封面图」？**
建议需要。列表页没有图会非常单调，且 og:image 必须有图。

**Q-05 是否现在就把 3 篇旧文迁移过去？**
建议迁移，否则新旧两套内容并存更乱。

**Q-06 定时发布要不要做？**
建议不做。单人运营，写完点发布即可，多一个定时器就多一个失败点。
