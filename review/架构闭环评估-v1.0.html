1评估方法

闭环评估不看功能列得全不全，只看一件事：从一个状态走到下一个状态时，上一状态留下的东西有没有人接手。库存占了没人放、券用了没退、订单完成了但报表还算它——这些都是"看起来能跑、跑一段就出错"的典型。

具体做法是把 12 条主链路画成状态图，对每一对相邻状态问三个问题：

  1. 触发者是谁——用户操作、定时任务、支付回调，还是人工？触发者不存在，链路就是死的。
  2. 副作用谁负责——库存、优惠、预算、通知、归因，每一样都要有明确的责任方。
  3. 异常出口在哪——失败、超时、重复调用时，状态往哪走？没有出口的状态就是死状态。
说明：这里的"断点"不是 bug，而是文档层面没有定义的地方。原型能跑通是因为演示数据不会有退款、换货、部分退款这些分支；真实运营第一个月就会遇到。

2闭环矩阵

#链路关键状态闭环断在哪
L1浏览 → 加购 → 结算 → 支付 → 发货 → 签收pending → paid → fulfilling → fulfilled → completed闭环—
L2支付失败 → 重试 / 放弃pending → pending（保留）/ cancelled闭环—
L3超时未付 → 取消 → 释放库存pending → cancelled闭环—（定时任务负责）
L4全额退款paid / fulfilled → refunding → refunded有断点券未释放、预算未回退（B2）
L5部分退款订单状态不变，售后单记录金额有断点报表口径未定义（B3）
L6换新（颜色保证）生成 $0 换新单有断点$0 单污染订单数与 AOV（B1）
L7退货 → 入库售后单 completed有断点回补策略只有"人工决定"（B4）
L8评价：邀评 → 提交 → 审核 → 展示pending → published有断点评价后退货如何处理（B5）
L9优惠：券 / 补贴 / 赠品 / 免邮结算时计算，写入 Adjustments闭环—
L10弃购：触发 → 邮件 → 恢复 / 转化stage 0→1→2→3 / 9有断点转化判定与小订单竞态（B6）
L11账户：注册 → 登录 → 订单 → 注销active → deleted_marked有断点注销后自动化仍在发信（B7）
L12归因：UTM → 订单 → 报表cookie → Order.channel有断点未同意用户的分母口径（B8）

另有两条不在主链路但同样需要闭合：批量改价与进行中活动的冲突（B9）、结算过程中的价格变动（B10）。

3十处断点

B1 换新单会污染订单报表 影响账务

现状
SDD 7.4 规定换新"生成一张 $0 换新发货单"。但它和真实订单同表，订单数 +1、GMV +0、AOV 被拉低
影响
如果一个月换新 20 单、真实订单 500 单，AOV 会被低估约 4%。更麻烦的是"订单数"这个指标失去意义——它同时包含销售与售后
方案
Order 增加 orderType（sale / exchange / reship / gift），所有报表默认只统计 sale；换新单在后台单独一个页签，不计入销售报表
落地
FR-A-062、SDD Order 表加字段

B2 退款后优惠券与活动预算不释放 影响账务

现状
全额退款后，CouponRedemption 记录还在、Promotion.spent 不减少、GiftRule.usedCount 不减少。文档里没有任何一句提到要回退
影响
① 用户用券下单后退款，perUserLimit 已消耗，他就不能再用这张券了——这是最容易被投诉的一条；② 活动预算被已退款的订单占掉，活动提前熔断；③ 赠品使用次数虚高
方案
退款完成时按规则回退：券的使用次数回退、CouponRedemption 标记 revoked（不物理删，留痕）；活动 spent 回退；赠品 usedCount 回退。但 perUserLimit 的判定要把已 revoked 的记录排除，否则回退无效
落地
FR-A-063、BR-23、SDD 7.4 补步骤

B3 部分退款后 GMV 该算多少 影响报表

现状
AfterSale 有 partial 类型与金额，订单状态不变（仍 completed），订单 total 不变
影响
GMV 虚高。一个订单 $143 退 $58，报表仍记 $143。月退 15% 的话，GMV 高估 15%——这个数字会直接影响"要不要加投放"的判断
方案
引入净营收（netRevenue）= total − 已退款金额，报表同时展示 GMV 与净营收；投放 ROI 一律用净营收算，因为退掉的钱没有毛利
落地
FR-A-064、SDD 报表口径

B4 退货入库只有"人工决定" 影响库存

现状
SDD 7.4 写"库存是否回补由人工决定（默认不回补，避免二次销售瑕疵品）"
影响
默认不回补是对的，但"人工决定"没有落点——后台没有这个操作入口，也没有字段记录"这件退回来的货去哪了"。三个月后盘点，账实必然不符
方案
售后单增加 restockDecision（restock / scrap / return_to_supplier）与 restockedQty。决定必须显式记录，不能留空；选择 restock 时才回补 onHand 并写库存流水
落地
FR-A-065、SDD AfterSale 加字段

B5 用户评价完又退货 影响口碑

现状
邀评在签收后 10 天，退货窗口 30 天。中间有 20 天窗口，用户可能先给好评再退货
影响
评价区出现"这条评价来自已退货订单"，对其他消费者是误导。但直接删评价又违反"低分保护"的精神（虽然这是高分）
方案
不删除，加标注：订单退款后评价保留，但前台显示"Verified purchase · Later returned"。该评价仍计入评分——因为用户确实买过、戴过、有这个体验。这条规则要写进评价条款，避免用户觉得被"改评价"
落地
BR-24、FR-S-171

B6 弃购转化判定与新订单的竞态 影响体验

现状
定时任务每 30 分钟扫一次；stage 转换靠 lastSeenAt 判断
影响
用户在第 23 小时 59 分下单，任务在第 24 小时整扫到，邮件仍会发出——用户刚付完钱就收到"你的购物车还在等你"，非常尴尬
方案
发信前二次校验：查该 email 在最近 2 小时内有已支付订单 → 跳过并置 stage 9。这个校验必须放在发信那一刻，不能只在扫描开始时
落地
FR-S-172、SDD 7.6 补校验

B7 注销账户后自动化还在给他发信 影响合规

现状
注销时清 PII、revoke session，但没有停止营销自动化
影响
用户注销后还收到生日提醒与弃购邮件，在 GDPR 下属于"删除请求未被完整执行"，是可以投诉的
方案
注销时：MarketingConsent.marketingOptIn = false、birthdayOptIn = false、AbandonedCart 全部置 stage 8（放弃）、未发送的 EmailLog 标记 skipped。交易类邮件仍可发（若有在途订单）
落地
FR-S-173、SDD 7.5 注销流程补步骤

B8 归因报表的分母口径 影响决策

现状
未同意 Cookie 的用户不采集渠道，订单 channel 记为 direct
影响
如果 40% 用户拒绝，direct 被虚高、各渠道被低估，CAC 全部算高、ROI 全部算低，可能导致错误地砍掉本来有效的渠道
方案
报表页固定显示归因覆盖率（有渠道来源的订单 / 总订单）。覆盖率低于 70% 时，CAC 与 ROI 旁加"参考值"标记，并提示"按已归因部分计算"。不做按比例摊派——摊派出来的数字是编的
落地
FR-A-052 补充、SDD 7.8 补口径

B9 批量改价与进行中活动打架 影响毛利

现状
v2.1 加了批量改价（FR-A-054），但没规定与进行中活动的关系
影响
活动是"原价 8 折"，运营批量把原价从 $82 降到 $68，活动价自动变成 $54.4，可能低于成本线。BR-17 有"不得低于成本线"的保护，但那是在结算时拦截，活动已经挂着，用户看到的折扣价是错的
方案
批量改价前做冲突预检：列出受影响的进行中活动与改后的最低成交价，低于成本线时阻止并说明；允许"改价同时暂停相关活动"的一步操作
落地
FR-A-054 补充、FR-A-066

B10 结算过程中的价格变动 影响体验

现状
购物车存 productId + 变体 + 数量，价格实时读取商品当前价
影响
用户在结算页停留 10 分钟期间运营改了价，用户点 Pay 时金额变了——支付金额与用户看到的金额不一致，这在支付环节是严重的信任问题，也可能引发拒付（chargeback）
方案
进入结算页时生成价格快照并锁定 30 分钟（写入 checkoutSession）；支付时校验快照与当前价，不一致则不自动改价，而是提示"价格已更新，请确认后继续"。这是唯一正确的处理方式——不能静默改价
落地
FR-S-174、BR-25、SDD CheckoutSession

结论：没有整块缺失的模块。所有缺口都在模块之间的接缝上——这正是闭环评估该发现的东西。功能清单是横向排列的，而订单生命周期是纵向流动的，接缝问题只有按流程走才会暴露。

5定稿决定

补充 16 条需求与 4 条业务规则后，FRD / SDD 定稿为 v2.2。以下是几个必须现在定、以后改代价很大的架构决定：

决定内容为什么现在定
订单类型分离orderType 字段区分 sale / exchange / reship / gift，报表只算 sale上线后再加需要回填历史数据，且历史报表无法追溯修正
净营收口径所有投放决策用 netRevenue，不用 GMV口径一旦确定，后续所有报表与对外数字都基于它；中途改会推翻此前的投放判断
价格锁定结算页锁定价格 30 分钟，变动时提示而非静默改价涉及支付金额，上线后修改等于改动支付流程，风险高
归因不摊派只报覆盖率，未归因部分单列摊派算法一旦写进报表，后续所有 ROI 都建立在估算上，难以纠正
评价不因退货删除保留评价 + 标注"Later returned"涉及评价信任度，事后删评价会引发"品牌在美化评分"的质疑

6实施顺序

依赖关系决定顺序，不能按"哪个容易先做"排：

1 Cookie 同意条→2 归因采集→3 归因报表
1 订单类型字段→2 净营收口径→3 投放决策
1 邮件同意与日志→2 弃购邮件→3 邀评邮件→4 客户群发
阶段内容不可跳过的原因
P0 基础Cookie 同意、邮件同意与日志、订单类型字段、价格锁定这四项是其他功能的前置：没有同意就没有归因，没有日志就没有频次控制，没有类型就没有正确报表
P1 交易主干商品 / 集合 / 结算 / 支付 / 订单 / 库存 / 账户没有这些就没有订单，其余全部无意义
P2 营销与售后优惠券 / 补贴 / 赠品 / 退款 / 换货 / 退货入库依赖 P1 的订单与库存
P3 增长弃购 / 邀评 / 归因报表 / 批量操作 / 库存预警依赖 P0 的同意与日志、P1 的订单数据
一个容易被忽略的顺序问题：Cookie 同意条看起来是"上线前补的合规项"，实际上它在 P0——因为归因采集依赖它，而归因报表是投放决策的依据。如果先上投放、后补同意条，前两个月的渠道数据全部作废，等于白跑一轮测试。
